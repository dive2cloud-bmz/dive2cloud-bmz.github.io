Agent 安全与访问控制：多租户环境下的工具与数据权限隔离

今日目标：把「Agent 能调什么工具、能访问什么数据」从「提示词里的口头叮嘱」变成「可审计、可回滚、可强制执行的访问控制策略」，并以 PostgreSQL 行级安全（RLS）与后端 API 权限模型为锚点建立直觉。

🚀 核心洞察：为什么 Agent 的权限不能靠「叮嘱」

PostgreSQL DBA 有一句口头禅：「不要相信应用层，权限要在数据库层收口。」 放到 AI Agent 场景里同样成立——LLM 本质上是一个「会幻觉、会串台、会被注入」的通用推理层，它不应该天然拥有任何数据访问或工具调用能力。

但现实中我们经常看到这样的设计：

这种方式至少有三处致命缺陷：

  1. 提示词不是访问控制策略：LLM 可能被越狱、被间接提示注入，或单纯因为上下文太长而「忘记」约束。
  2. 没有最小权限原则：一旦工具注册到 Agent，它理论上就拥有了调用权，区别只是「想不想」。
  3. 多租户场景下无法审计：同一个 Agent 进程服务多个租户，如果不在调用链路里嵌入 tenant_id 与 user_id，事后无法判断一次 SELECT * FROM orders 查的是谁的数据。

今天的核心洞察是：Agent 的安全边界应当像微服务架构中的 IAM（Identity and Access Management）一样，由独立的授权层在工具调用前强制执行。 我们需要的不是「更长的 system prompt」，而是「面向 Agent 的 RLS + RBAC + 审计日志」。

🧠 核心概念：从「身份」到「授权」的五层模型

为了把问题讲清楚，我画了一个 Agent 访问控制的分层模型。

1. 身份层：谁在用 Agent

和任何后端系统一样，Agent 首先需要回答「谁在请求」。

  • User Identity：自然人用户，对应 user_id。
  • Tenant Identity：企业/组织/空间，对应 tenant_id。多租户系统的核心隔离维度。
  • Service Identity：Agent 本身作为一个服务账号，对应 service_account。
  • Session Identity：一次对话会话，对应 session_id，用于临时授权与会话范围控制。

在 Agent 里，我们可以在每次请求开始时把当前租户、用户、角色写入一个线程本地或上下文变量中，后续所有工具调用都自动携带这个上下文。

3. 策略层：RBAC + ABAC + ReBAC 的混合

后端工程师对 RBAC（基于角色的访问控制）很熟悉，但 Agent 场景里通常需要三种模型混用：

模型 英文全称 适用场景 类比后端
RBAC Role-Based Access Control 按岗位分配工具包，如客服只能读订单 PostgreSQL 角色 + 默认权限
ABAC Attribute-Based Access Control 按属性动态判断，如「工作时间才能调用退款」 策略引擎（OPA/Casbin）
ReBAC Relationship-Based Access Control 按数据关系判断，如「只能访问我部门的文档」 图数据库 / 共享表权限

4. 工具层：工具描述不是能力清单，而是契约

每个工具都应该显式声明：

  1. 所需权限 / scope（如 orders:read）
  2. 是否需要人工确认（human-in-the-loop）
  3. 是否可自动重试（幂等性）
  4. 数据隔离字段（必须传入 tenant_id）

5. 审计层：没有审计日志的权限都是耍流氓

🔗 后端桥接：把 PostgreSQL 的权限直觉搬到 Agent

作为 RDS PostgreSQL 工程师，我们对下面这套机制非常熟悉。让我们把每一个数据库概念映射到 Agent 访问控制。

1. 行级安全（RLS）≈ 工具调用的数据范围

PostgreSQL RLS 的核心思想是：即使用户能访问一张表，每次查询也自动追加一个谓词过滤。

Agent 工具的对应做法是：在每个工具执行前，自动把 tenant_id / user_id 注入到查询条件里，而不是让 LLM 自己拼 SQL。

2. Schema 隔离 ≈ 工具命名空间

多租户 PostgreSQL 有两种常见模式：

  • Schema-per-tenant：每个租户一个 schema，天然隔离。
  • Row-level tenant_id：所有租户共用表，通过 RLS 隔离。

3. 连接池 / 会话变量 ≈ Agent 上下文传播

RDS 里我们用 SET LOCAL 设置会话变量，确保同一条连接上的后续查询都带上租户信息。Agent 场景里，我们把同样的信息放进 contextvars 或 OpenTelemetry baggage 里，让每个工具调用都能拿到。

4. 审计触发器 ≈ 工具调用拦截器

PostgreSQL 用触发器或 pgaudit 记录变更。Agent 里我们用工具调用拦截器 / middleware。

5. GRANT / REVOKE ≈ 动态策略更新

数据库里角色权限可以动态 GRANT 和 REVOKE。Agent 的策略引擎也应当支持运行时热更新，而不是每次改完代码重新部署。这通常通过 OPA（Open Policy Agent）或 Casbin 实现。

📰 技术雷达：Agent 安全与访问控制的最新动态

1. OpenAI 引入「Function-level 权限」方向

OpenAI 在 2024-2025 年的多次更新中强调了 Structured Outputs + Tool 定义即契约 的趋势。虽然官方尚未提供原生的 RBAC 层，但行业共识是：工具 schema 未来可能原生支持 required_scopes 字段，供网关进行预授权。

2. OWASP LLM Top 10 2025

最新版中，「过度代理（Excessive Agency）」 位列前三。其核心建议就是：

  • 为每个 Agent 配置最小权限工具集。
  • 在工具调用前进行人机确认（Human-in-the-loop）。
  • 记录完整调用链以便审计。

3. OPA / Cedar / Casbin 在 Agent 网关中的采用

  • Open Policy Agent (OPA)：微服务 IAM 的老玩家，越来越多 Agent Gateway（如 Langfuse、Portkey）开始集成 OPA 做工具级授权。
  • Cedar（AWS）：基于 Rust 的策略语言，强调形式化验证，适合金融/医疗等高合规场景。
  • Casbin：轻量级，支持 RBAC/ABAC/ReBAC，社区活跃，适合中小企业快速落地。

4. 开源项目关注

  • invariantlabs.ai：专注于 LLM Agent 的安全与一致性检测，支持追踪工具调用序列并检测越权模式。
  • langchain-core Tool Calling：正在向更严格的 Annotated 输入验证演进，减少 LLM 传参错误。
  • PydanticAI：基于 Pydantic 的 Agent 框架，天然强调依赖注入与上下文安全，值得关注。

5. 论文与标准

  • 《Agent 安全：从提示注入到访问控制》（Google DeepMind, 2024）：提出 「Tool Guardrails」 三层架构——Schema、Policy、Runtime。
  • NIST AI Risk Management Framework 1.0：建议对 AI 系统的「行动能力」进行显式授权与持续监控。

今日小结

  1. Agent 的安全不能依赖提示词，而要在工具调用前建立独立的授权层。
  2. 多租户隔离要像 PostgreSQL RLS 一样，把 tenant_id / user_id 作为不可伪造的上下文注入每个工具。
  3. RBAC + ABAC + ReBAC 混合策略可以覆盖岗位、属性、关系三类授权需求。
  4. 审计日志是事后溯源与合规的底线，必须记录「谁、在什么会话、调用了什么工具、是否被允许」。
  5. 微实战中的 tool_guard 装饰器是一个最小可复用的设计模式，可以直接搬到真实项目里。
