别再让评测脚本裸跑：设计可扩展的 Agent 评测平台与 bad case 运营闭环

本文目标阅读时长：20 分钟。适合已经写过 evaluate.py、跑过几个 LLM-as-Judge 脚本，却发现「评测结果散在 Excel 里、bad case 修完又复发、线上出了问题才想起来补评测」的后端工程师。

🚀 核心洞察：从 PostgreSQL 慢查询日志到 Agent 评测平台

作为 RDS PostgreSQL 后端工程师，你对下面这套流程一定不陌生：

  1. log_min_duration_statement = 100ms，慢查询被自动捕获；
  2. pg_stat_statements 聚合 top SQL；
  3. 把慢 SQL 丢进待办队列，分析执行计划、加索引、改写法；
  4. 灰度发布后，再跑一轮 EXPLAIN ANALYZE 做回归验证；
  5. 把典型案例沉淀到「SQL Review Checklist」，防止同类问题再次进入生产环境。

这套机制之所以有效，是因为它形成了一个可观测 → 可定位 → 可修复 → 可回归 → 可预防的闭环。遗憾的是，很多 AI 应用的评测至今还停在第一步：写个 evaluate.py，在本地跑一遍，把 F1、Accuracy、GPT-4 Judge 分数截个图发到群里，任务结束。

当模型、Prompt、工具、RAG 知识库、Agent 链路中任意一环发生变更，你根本没法回答三个灵魂问题：

  • 这次改动让哪些指标变好了？哪些变差了？（可量化）
  • 上一个版本的 bad case，这个版本真的修好了吗？（可回归）
  • 为什么线上用户投诉的问题，评测集里完全没有覆盖？（可预防）

今天的主题就是把后端工程师熟悉的「慢查询治理」思路迁移到 Agent 评测领域，搭建一套**可扩展的评测平台（Evaluation Platform）**和 bad case 运营体系。它不需要你立刻采购商业工具，核心思想是：把评测从「一次性脚本」升级为「持续运行的数据基础设施」。

🧠 核心概念：评测平台的五层架构

1. 为什么脚本不够了？

脚本的问题不是「不准」，而是不可持续。对比一张表就能看清楚：

维度 本地 evaluate.py 评测平台
数据集管理 硬编码在 test_cases.json 版本化、标签化、支持采样与分层
执行调度 串行、本地跑 异步队列、并发控制、失败重试
指标计算 自定义函数，口径不统一 插件化 Judge、指标注册中心
结果存储 stdout / Excel 结构化落库、可追踪到单次调用
回归验证 靠人眼 diff 自动对比基线、告警阈值
bad case 运营 群里截图 工单流转、标签归因、修复闭环

如果只用脚本，你得到的是「一次体检报告」；如果做平台，你得到的是「持续健康监测 + 病历档案 + 治疗方案跟踪」。

2. 五层参考架构

数据采集层不要只盯着人工写 case。线上真实 trace 是更宝贵的数据源：用户的原始问题、Agent 的思考链（如果可导出）、调用的工具与参数、最终输出、用户反馈（👍/👎）。把它们脱敏后回流到评测池，才能做到「线上问题驱动评测集生长」。

数据集管理层要回答：这个数据集是哪个版本的？覆盖了多少意图类别？有没有重复？是否包含已知的 hard cases？推荐参考 Hugging Face datasets 的版本化思路，以及 DVC/ lakeFS 的数据版本控制理念。

评测执行层的核心是可复现。同一份数据集 + 同一套配置 + 同一个模型版本，两次跑出来的结果必须一致。要做到这一点，需要：固定随机种子、隔离环境（Docker/Sandbox）、缓存外部调用（VCR、LLM 调用缓存）、记录依赖版本（模型名、Prompt 版本、工具 schema）。

指标与裁判层是平台的大脑。不要把所有指标都塞给一个 GPT-4 Judge。建议拆成三层：

  1. 硬性规则：JSON schema 校验、正则匹配、SQL 可执行性检查、输出长度限制；
  2. 语义裁判：Embedding 相似度、BERTScore、LLM-as-Judge（ Rubric + Few-shot + Chain-of-Thought）；
  3. 业务裁判：用户满意度、转化率、任务完成率、人工终审。

结果与可视化层要支持「跨版本对比」。后端同学可以联想 pgbench 的 report：TPS、Latency P50/P95/P99、随时间变化曲线。评测报告也一样：总体通过率、各维度分数分布、错误类型饼图、单次 case 的详细 trace。

Bad Case 运营层是今天最强调的部分。它的目标是把「评测失败」变成「产品改进工单」。

3. Bad Case 生命周期

标签体系建议按「错误根因」设计，而不是按「现象」。例如：

  • model_hallucination：模型编造不存在的事实或工具参数；
  • prompt_ambiguity：Prompt 没有明确约束输出格式或边界条件；
  • tool_schema_mismatch：工具定义与实际 API 不一致；
  • retrieval_noise：RAG 召回到了无关文档；
  • planning_error：多步计划顺序或依赖关系错误；
  • user_intent_misclassify：用户真实意图被分类器误判。

标签打得越细，后期的 pareto 分析越有价值。你会发现 80% 的 bad case 可能集中在 2-3 个根因上，集中火力解决它们，比广撒网有效得多。

4. LLM-as-Judge 的工程化要点

把 GPT-4/Claude 当裁判看似简单，实则暗藏陷阱：

偏见（Position Bias）：模型倾向于给放在第一个的答案更高分。解决方案：交换答案顺序跑两次取平均，或设计成强制单选并随机排序。

长度偏见（Length Bias）：模型可能偏爱更长的回答。解决方案：在 rubric 中明确「简洁得分」维度，或增加长度惩罚项。

自我增强（Self-Preference）：模型可能更偏爱自己生成的答案。解决方案：使用第三方模型做裁判，或匿名化模型来源。

评分尺度漂移：不同日期、不同 temperature、不同 Prompt 版本会导致分数不可比。解决方案：固定裁判 Prompt 版本，引入锚点 case（anchor set）做标准化。

🔗 后端桥接：用 PostgreSQL/后端概念类比 AI 评测

把 AI 概念翻译成熟悉的后端词汇，会大幅降低设计难度。

1. 评测集 ≈ 测试数据库 + 索引

评测集里的每一条 case 就像数据库里的一行测试数据。为了高效覆盖不同场景，你需要：

  • 主键：case_id，全局唯一；
  • 索引：按 intent、difficulty、标签、来源建立索引，方便分层采样；
  • 约束：必须有 input、必须有期望输出或评分标准、不能有重复；
  • 版本控制：评测集的变更要走 PR Review，避免「随便删 case 让指标好看」。

2. 评测运行 ≈ CI Pipeline / 压测任务

一次 eval run 就像一次 CI build：

  • 触发条件：代码提交、模型版本更新、Prompt 变更、定时任务；
  • 执行环境：Docker 容器，保证可复现；
  • 产物：报告、日志、覆盖率、错误列表；
  • 门禁：关键指标低于阈值时阻断发布。

你可以直接把评测任务接入现有的 CI/CD 系统（GitHub Actions / GitLab CI / Jenkins），让 Agent 应用也拥有「单元测试 → 集成测试 → 线上监控」的完整质量关卡。

3. Bad Case 队列 ≈ 死信队列（DLQ）

线上系统用 DLQ 存放处理失败的消息，Agent 评测平台也用类似机制存放失败 case：

  • 失败原因要标准化，方便聚合；
  • 支持重试（fix 后重新评测）；
  • 超过重试次数或长期未处理要告警；
  • 最终要形成「错误模式库」，类似 PostgreSQL 的 pg_stat_statements 知识库。

4. 指标 ≈ 数据库执行指标

AI 评测指标 PG 对应概念 说明
Pass Rate 查询成功率 通过的 case 占比
Per-Dimension Score 各维度耗时 定位短板
Regression Gap 性能回退 新版本比基线差多少
Confidence Interval p50/p95/p99 指标波动范围
Anchor Set 基准 SQL 用于校准的标准 case

5. LLM-as-Judge ≈ 可配置的规则引擎

把 Judge Prompt 想象成数据库里的「检查约束（CHECK constraint）」或触发器：定义了什么算通过、什么算失败。但它比普通约束更灵活，因为它可以处理自然语言的语义。工程上要做的是：把 Prompt 版本化、参数化、可审计，而不是散落在各个脚本里。

📰 技术雷达：评测与 bad case 运营工具生态

开源/半开源工具

  • Promptfoo：偏 Prompt 与模型对比，支持 red teaming、断言规则、CI 集成，适合把评测脚本迁到平台化的第一步。
  • LangSmith / Langfuse / Phoenix (Arize)：偏 trace 可观测与在线评测，能把线上 trace 直接转为评测 case。
  • Weave (Weights & Biases)：实验跟踪 + 评测 + 模型注册一站式，适合研究团队。
  • Inspect (UK AI Safety Institute)：结构化评估框架，支持多模型、多 judge、沙箱执行，安全与对齐评测场景很强。
  • OpenEvals (OpenAI)：官方推出的评估库，提供常见任务的参考实现和 Judge 模板。

值得关注的研究方向

  1. Judge 的 Judge（Meta-Evaluation）：如何评估裁判本身是否稳定、无偏见。最新工作集中在使用一致性、交换测试、人工对齐度来校准 judge。
  2. 合成数据生成 for Eval：用模型生成对抗性 case、边界 case，降低人工标注成本，但要警惕分布漂移。
  3. 持续学习中的 Catastrophic Forgetting：Agent 修复一批 bad case 后，另一批 case 可能退化。需要在平台里维护「锚点集」做回归。
  4. Multi-turn Evaluation：单轮问答评测已不够，Agent 评测需要支持多轮对话状态、工具调用链、人类模拟用户（User Simulators）。

一条实践建议

不要试图一次性搭建完美的评测平台。推荐分三步走：

  1. Week 1：把现有 evaluate.py 的结果写入数据库，至少能看到历史趋势；
  2. Week 2-4：接入真实线上 trace，建立 bad case 标签与工单流转；
  3. Month 2+：引入多 Judge、A/B 回归、自动告警、与 CI/CD 打通。

写在最后

评测平台不是「AI 团队专属的数据玩具」，而是 Agent 应用的质量基础设施。它和后端工程师熟悉的监控、CI、慢查询治理、DLQ 体系在本质上是同一套思想：把问题显式化、结构化、流程化。

当你下次再写 evaluate.py 时，不妨多问一句：

这个脚本跑出来的失败 case，一个月之后还会有人记得修复吗？

如果答案不确定，就是时候开始搭建你的评测平台了。
