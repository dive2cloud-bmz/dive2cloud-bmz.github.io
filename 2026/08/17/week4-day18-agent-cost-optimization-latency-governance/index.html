Agent 成本优化与延迟治理：像调优 PostgreSQL 一样精打细算 LLM 调用

AI-Learning Agent Cost-Optimization Production-Engineering Week-4 Latency Token-Budget

更新日期:   2026-08-17

阅读次数:  

今日一句话：Agent 的每一次 LLM 调用都是一次数据库事务——有 I/O、有计算、有并发、有预算上限；后端工程师已经习惯了为 SQL 做执行计划优化和容量规划，现在要把同一套思维搬到模型调用上。

🚀 核心洞察（2 min）

过去三周，我们完成了 Agent 的”功能建设”：记忆、工具调用、ReAct 规划、多 Agent 编排、LangGraph 状态持久化、可观测性。今天进入一个新的维度——生产经济学（Production Economics）。一个 Agent 能不能真正上线，不只看它能不能答对问题，还要看它答得够快、够便宜、够可控。

作为 RDS PostgreSQL 后端工程师，你对下面这套工作方法论应该非常熟悉：

  • 慢查询优化：用 EXPLAIN ANALYZE 找到瓶颈，加索引、改写法、调参数。
  • 连接池与并发控制：避免连接打满，用 pgbouncer、事务隔离级别、锁超时控制资源争抢。
  • 容量规划：根据 QPS、数据增长、IO 吞吐预估实例规格和存储。
  • 预算治理：statement_timeout、shared_buffers、work_mem 都是系统层面的”预算”。

Agent 系统的成本与延迟治理，本质上是同一套思路在 LLM 上的映射：

数据库系统 Agent 系统
SQL 执行计划 LLM 调用链路与推理步骤
索引 / 分区 向量索引 / Prompt 缓存 / RAG 检索
连接池 模型客户端并发与限流
慢查询日志 Token 追踪与延迟分布
语句超时 Token 预算与最大步数
读写分离 大小模型路由（Route to Small/Large Model）

今天的核心目标，是把 Agent 从”每次调用都烧钱”的豪车模式，切换到”按需调度、按质付费”的精益模式。我们会覆盖 Token 经济学、延迟拆解、缓存策略、模型路由、并行化、流式输出、预算熔断 七个杠杆点，并给出一个可运行的成本感知 Agent 路由器。

🧠 核心概念（10 min）

1. LLM 调用成本不是黑盒：Token 经济学

大模型 API 的计费单位通常是 Token，1 Token 约等于 0.75 个英文单词或 0.4 个汉字。计费分为输入（prompt）和输出（completion）两部分，输出通常更贵。以常见定价为例（价格会波动，仅用于建立数量级直觉）：

模型层级 输入 / 1M tokens 输出 / 1M tokens 适用场景
轻量模型（如 GPT-4o-mini） $0.15 $0.60 分类、摘要、简单意图识别
主力模型（如 GPT-4o / Claude 3.5 Sonnet） $2.50 - $3.00 $10.00 - $15.00 复杂推理、代码生成、Agent 决策
旗舰模型（如 GPT-4.5 / Claude 3 Opus / o1） $15.00+ $60.00+ 高难度数学、深度分析、多步推理

一个客服 Agent 平均每次对话调用 3-5 次 LLM（意图识别 → 检索改写 → 答案生成 → 工具校验 → 回复润色）。如果每次输入 4K tokens、输出 1K tokens，使用主力模型，单次对话成本约为：

看起来不贵，但乘上 100 万通对话就是 $120,000。这还没有算重试、幻觉导致的无效调用、以及用户故意构造的长上下文攻击。

Token 成本的三大来源：

  1. System Prompt 与上下文重复传递：每次调用都要把角色设定、工具描述、历史对话重新塞进去。
  2. 过度推理（Over-thinking）：模型生成了解释性文字、冗余步骤、反复自我纠正。
  3. 错误恢复开销：解析失败、工具调用失败后的重试会重复消耗上下文。

对应的优化方向非常明确：减少不必要调用、压缩上下文、按任务难度选模型、把可缓存部分固化下来。

2. Agent 延迟拆解：时间花在哪里？

Agent 的端到端延迟不是简单的”模型生成时间”，它包括多个串行和并行阶段。用一个典型的 RAG Agent 调用链来说明：

每个阶段的典型耗时（假设云 API、无缓存）：

阶段 典型耗时 优化杠杆
意图识别 100-300 ms 小模型、缓存、本地部署
查询改写 200-500 ms 小模型、模板化
向量检索 20-100 ms 索引优化、top-k 裁剪
重排序 50-300 ms 轻量 reranker、缓存
上下文组装 10-50 ms 预计算、摘要代替全文
LLM 生成 500 ms - 5 s 模型选择、流式输出、输出长度限制
工具执行 可变 并行化、超时控制、异步化

最慢的两个环节通常是 LLM 生成 和 工具执行。LLM 生成延迟主要取决于模型大小、输出长度和推理框架；工具执行延迟则取决于下游 API 的响应时间。一个关键观察是：Agent 的延迟具有复利效应——每增加一次 LLM → Tool → LLM 的循环，总延迟几乎线性增长。因此减少调用轮次，比单次调用加速更有效。

3. Prompt 缓存：把热数据放进 Shared Buffer

Prompt 缓存（Prompt Caching）是 2024-2025 年各大模型厂商推出的重要成本优化特性。它的原理很简单：如果本次请求的 prompt 前缀与某次已处理过的 prompt 前缀完全相同，模型可以复用之前的 KV Cache，只对新增部分计费。

对 Agent 来说，最适合缓存的部分包括：

  • System Prompt：角色设定、安全策略、输出格式要求。
  • 工具描述（Tool Schema）：一长串 JSON Schema 描述。
  • 静态上下文：产品文档、知识库摘要、用户画像。
  • 历史对话前缀：多轮对话中前面已经处理过的轮次。

缓存命中率每提高 10%，整体输入成本可能下降 5-15%。设计 Agent 时，应该把静态内容放在 prompt 前面，动态内容放在后面，并保持格式稳定，避免因为时间戳、随机 ID 导致前缀无法命中。

4. 模型路由：Query Planner for LLM

不是每个任务都需要旗舰模型。一个经验丰富的后端工程师不会在查询所有表时都开 SET enable_seqscan = off，而是让优化器根据代价选择执行路径。同理，Agent 也需要一个模型路由器（Model Router），根据任务难度、成本预算、延迟要求选择模型。

常见的路由策略：

策略 说明 适用
难度分级路由 先用小模型分类任务难度，再决定用大模型 客服、问答
置信度路由 小模型输出置信度低时升级到大模型 分类、实体抽取
成本预算路由 根据用户配额或剩余预算选模型 SaaS 多租户
延迟 SLA 路由 要求高响应速度时选轻量模型或本地模型 实时场景
回退路由 大模型失败/超时时降级到小模型或静态答案 韧性

一个朴素但有效的模式是 Cascade（级联）：先用便宜模型尝试，如果答案质量不达标再调用贵模型。它的成本期望是 P(小模型成功) × 小模型成本 + P(失败) × (小模型成本 + 大模型成本)。只要小模型成功率足够高，整体成本会显著低于全部用大模型。

5. 调用链并行化：减少串行等待

很多 Agent 步骤之间其实没有依赖，可以并行执行。例如：

  • 用户意图识别与敏感词检测可以并行。
  • 多路检索（向量检索 + 关键词检索 + SQL 查询）可以并行。
  • 多个工具调用在不依赖彼此结果时可以并行（OpenAI 的 tool_choice 支持一次返回多个 tool_call）。

在后端，我们用 asyncio.gather、线程池、CompletableFuture 做并发；在 Agent 中，LangGraph 的 Send 和 RunnableParallel、LlamaIndex 的 ParallelToolCalls 都提供了类似的抽象。关键是把”数据依赖”梳理清楚：只有当步骤 B 真的需要步骤 A 的输出时，才串行；否则并行。

6. 流式输出与首 Token 时间

对于交互式 Agent，用户感知到的延迟往往不是”总生成时间”，而是”首 Token 时间（Time to First Token, TTFT）”。流式输出（Streaming）可以在模型开始生成第一个 token 时就返回给用户，显著改善体验，即使总生成时间不变。

但流式也有代价：

  • 更难做结构化输出校验（必须等完整 JSON 才能 parse）。
  • 缓存收益可能降低（因为响应无法预计算）。
  • 中间状态管理更复杂。

因此通常采用混合策略：决策/工具调用用非流式保证结构正确，最终回复用流式提升体验。

7. Token 预算与熔断：给 Agent 戴上 statement_timeout

没有预算控制的 Agent 就像一个没有 statement_timeout 的数据库：一个异常请求可能把成本拖垮。预算治理需要三层防线：

防线 控制对象 触发动作
单次调用预算 单条 prompt + completion tokens 截断、拒绝、换小模型
累计会话预算 整个对话的 tokens 提示用户、转人工、结束对话
最大步数 Agent 循环轮次 强制退出、返回最佳中间结果
时间预算 端到端延迟 超时降级、返回缓存答案

预算控制不是简单的”省钱”，而是服务质量保障（QoS）。它确保少数恶意或异常请求不会牺牲整体用户体验。

🔗 后端桥接（3 min）

把 Agent 成本与延迟治理映射到 PostgreSQL / 后端概念，能帮助建立稳定的直觉。

1. Token ≈ 数据库 Page I/O

数据库调优的核心指标之一是 I/O 次数——读了多少页、写了多少页。LLM 调优的核心指标是 Token 数——读了多少输入 token、写了多少输出 token。两者都是稀缺资源：

  • 减少 I/O：加索引、裁剪 SELECT *、用覆盖索引。
  • 减少 Token：Prompt 压缩、检索 top-k 裁剪、输出长度限制、缓存静态前缀。

2. Prompt 缓存 ≈ Shared Buffers / Query Plan Cache

PostgreSQL 的 shared_buffers 缓存热数据页，减少磁盘 I/O。Planner 也会缓存执行计划。Prompt 缓存则是复用已经计算过的 attention KV，避免对相同前缀重复做前向传播。两者的命中率都是关键优化指标。

3. 模型路由 ≈ 查询优化器选择执行路径

优化器根据统计信息选择走索引扫描还是顺序扫描。模型路由器根据任务特征选择轻量模型还是旗舰模型。都是一种基于代价的决策（Cost-Based Decision）。

4. 流式输出 ≈ PostgreSQL 游标（Cursor）

游标不是一次性返回所有行，而是分批返回，降低客户端等待时间。流式 LLM 输出同理，都是把”大结果集”拆成小块交付。

5. Token 预算 ≈ statement_timeout / resource queue

PostgreSQL 的 statement_timeout 防止单个查询占用连接过久；pgBouncer 的池大小限制并发连接数。Agent 的 Token 预算和最大步数，对应地防止单个请求消耗过多模型资源。

6. 工具并行调用 ≈ 并行顺序扫描 / 并行 workers

PostgreSQL 可以把一个大扫描拆成多个并行 workers。Agent 可以把多个无依赖的工具调用并行化。两者都遵循同一个前提：任务可分解且无共享状态冲突。

📰 技术雷达

1. Prompt Caching 成为主流降本手段

OpenAI、Anthropic、Google 在 2024 年下半年陆续推出官方 Prompt Caching，折扣通常在 50% 左右。2025 年，更多开源模型（如 vLLM、SGLang）也支持了 prefix caching。对于长上下文 Agent，这是性价比最高的优化之一。

2. LiteLLM Proxy：Agent 的 pgbouncer

LiteLLM 正在从”统一 SDK”演变为”模型网关”，支持：

  • 多模型负载均衡与故障转移。
  • 按项目/用户/密钥的成本追踪与预算限制。
  • 缓存、速率限制、流式透传。

对于需要为多个 Agent 或团队统一管控模型访问的企业，LiteLLM 的角色很像数据库领域的连接池与访问代理。

3. 投机解码（Speculative Decoding）降低延迟

vLLM、TensorRT-LLM、SGLang 等推理框架已经支持投机解码：用一个小草稿模型快速生成候选 token，再由大模型并行验证。在代码生成、结构化输出等场景，可提升 1.5-3 倍吞吐。

4. DSPy 与自动提示优化

DSPy 把 prompt 工程变成了”可优化的程序”，通过自动编译和微调少量示例来提升小模型表现。其意义在于：让小模型在更多任务上达到原本需要大模型才能达到的准确率，从而扩大级联路由的收益窗口。

5. 模型上下文协议（MCP）与工具生态标准化

Anthropic 推动的 MCP（Model Context Protocol）正在让工具、资源、提示的标准化描述成为可能。长期来看，标准化的工具描述将降低 Agent 集成成本，但也意味着 Prompt 中工具 schema 的体积会增长，Prompt 压缩与缓存将更加重要。

今日小结

今天我们完成了 Agent 生产经济学的第一课：

  • Token 是 Agent 的 I/O，延迟是 Agent 的查询执行时间。优化它们和优化数据库一样，需要度量、拆解、分层治理。
  • Prompt 缓存 是降低输入成本的第一杠杆，相当于给 LLM 加了一层 shared buffer。
  • 模型路由与级联 让任务按需使用计算资源，避免”杀鸡用牛刀”。
  • 并行化、流式输出、预算熔断 是保障延迟与稳定性的标准手段。
  • 后端工程师的既有技能（索引、查询计划、连接池、超时控制）可以直接映射到 Agent 成本与延迟治理上。
