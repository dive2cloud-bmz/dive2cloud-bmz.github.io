Week4 Day27｜转型后第一课：把 26 周学习成果变成可演示的 AI 工程作品集

目标：把过去 26 天积累的 RAG、Agent、Production Engineering、System Design 知识，沉淀成一份能打开面试、能说服团队、能自己反复打磨的 AI 工程作品集，并拿到一份 30 天落地计划。

🚀 核心洞察：作品集是后端工程师转型 AI 的最强杠杆

作为从 RDS PostgreSQL 后端工程师转型 AI 应用工程师的你，已经走过 26 天的密集学习。你掌握了 Embedding、Chunking、Vector DB、ReAct、LangGraph、Guardrails、Eval Pipeline、System Design。但所有这些知识在面试桌上、在项目评审会上、在招聘官的 30 秒简历扫描里，都需要一个可验证的载体。

这个载体就是作品集（Portfolio）。

后端工程师的优势在这里会被放大：你习惯写可运行的代码、设计 schema、考虑并发与容错、做监控与回滚。这些工程素养恰恰是当前 AI 应用市场最稀缺的。很多算法出身的候选人能调模型，但做不出一个能上线、能观测、能迭代的系统。你的作品集应该证明：你不只是会调用 OpenAI API，你能把一个 LLM 原型变成生产级服务。

今天的核心洞察是：AI 工程作品集不是简历的附件，它就是简历本身。 一份好的作品集应该让面试官在 5 分钟内相信：这个人能独立设计、实现并交付一个 AI 功能。

🧠 核心概念：AI 工程作品集的构成与评价标准

1. 作品集的三个层次

不是所有的 GitHub 仓库都能叫作品集。AI 工程作品集至少应该包含三个层次：

层次 内容 面试官关注什么 后端类比
L1: Demo 层 一个能跑起来的应用、Notebook 或 CLI 能否快速理解问题与解决方案 可运行的 PoC
L2: 工程层 清晰的模块拆分、测试、CI/CD、部署文档 代码质量、可维护性、可扩展性 生产服务
L3: 决策层 设计文档、选型理由、评估结果、失败案例分析 技术判断力、迭代思维 技术方案评审

大多数初学者的作品集停留在 L1：一个漂亮的 Gradio 界面，能聊天、能上传 PDF。这很好，但不足以证明你能进工程团队。真正拉开差距的是 L2 和 L3：你是否考虑过错误处理？是否评估过不同 retrieval 策略的效果？是否记录过为什么选这个向量数据库而不是另一个？

3. 选题策略：从后端经验中寻找差异化

不要跟风做”第二个 ChatPDF”。你的差异化来自 PostgreSQL / 后端背景。以下是几个有高辨识度的选题方向：

选题方向 结合后端经验 技术栈示例
PostgreSQL + pgvector 企业知识库 利用你对 RDS、索引、备份、权限的理解 FastAPI, SQLAlchemy, pgvector, LangChain
LLM 驱动的数据库运维助手 把慢查询分析、索引建议、锁诊断自动化 LangGraph, PostgreSQL system catalog, React
多租户 Agent 服务平台 用 schema-per-tenant / row-level security 做隔离 FastAPI, PostgreSQL RLS, LangGraph, Redis
可观测的 LLM 网关 类似 API Gateway，但专门路由和监控模型调用 FastAPI, Redis, Prometheus, OpenTelemetry
RAG 评估流水线 把 CI/CD 思维带入模型效果迭代 GitHub Actions, Ragas, Weights & Biases

这些选题的共同点是：它们不是”玩具”，而是可以被真实业务场景接纳的原型。面试官看到这种项目，会立刻联想到你在团队里能做什么。

4. 作品集的叙事框架：STAR for Engineers

每个项目都需要一个清晰的叙事。建议采用工程化的 STAR 框架：

  • Situation（场景）：我为什么要做这个项目？解决什么真实问题？
  • Task（任务）：核心挑战是什么？是准确率、延迟、成本，还是可扩展性？
  • Action（行动）：我尝试了哪些方案？为什么选最终这个？关键代码在哪里？
  • Result（结果）：量化指标是什么？Recall@K、P95 延迟、Token 成本、用户满意度？

以一个”PostgreSQL 慢查询诊断 Agent”为例：

S：RDS PostgreSQL 实例经常出现慢查询，DBA 需要反复查看 pg_stat_statements、执行计划、索引状态，耗时且容易遗漏。
T：构建一个 Agent，能自动收集诊断信息、分析根因、给出优化建议，并在高置信度时直接生成 ALTER INDEX 或 VACUUM 建议。
A：使用 ReAct 循环调用 5 个工具（查询 pg_stat_statements、获取执行计划、检查索引使用率、分析表统计信息、检索内部知识库），并用 LangGraph 管理状态；用 pgvector 存储历史案例用于 few-shot 提示；用 Guardrails 校验所有生成的 SQL。
R：在 50 个真实慢查询上，Agent 正确识别根因的比例达到 78%，平均诊断时间从 15 分钟降到 40 秒；对高置信度建议人工复核后执行，无生产事故。

🔗 后端桥接：作品集 ≈ 可运行的技术方案 + 持续迭代的 Schema

作为后端工程师，你可以把作品集理解为一个数据库 schema 的进化过程。

1. 项目 README 就是 ERD 的说明文档

在后端项目里，新成员第一件事通常是看 ERD 和 API 文档。在 AI 工程项目里，README 承担同样的职责：它告诉别人”这个系统解决什么问题、输入输出是什么、数据如何流动”。一个好的 README 应该像数据库设计文档一样，先讲领域模型，再讲查询路径。

2. 评估指标就是 AI 系统的 SLA

后端系统有 QPS、P99、可用性、一致性指标。AI 系统同样有指标，只是维度不同：

后端指标 AI 工程对应指标 含义
QPS / 吞吐量 Tokens/sec, Requests/sec 系统处理能力
P99 延迟 TTFT, TBT, End-to-end latency 响应速度
可用性 模型降级成功率、Fallback 覆盖率 故障时的兜底能力
一致性 输出结构化稳定性、事实一致性 结果是否可预期
慢查询 长 Chain-of-Thought、高 Token 消耗调用 需要优化的调用

在作品集中展示这些指标，会让面试官觉得你是在做工程，而不是做实验。

3. Prompt 版本管理 ≈ Schema 迁移

后端工程师熟悉数据库 schema 迁移：每次变更都要可回滚、可审计、可兼容。Prompt 和模型配置也需要同样的管理。你可以用文件命名约定或工具（如 LangChain Hub、Weights & Biases Prompts）来版本化 prompt：

每次迭代都记录变更原因和评估结果，就像在数据库迁移脚本里写 up 和 down 一样。

4. Agent 状态机 ≈ 工作流引擎

LangGraph 的状态机模型，本质上和后端的工作流引擎（如 Temporal、Camunda、Airflow）没有本质区别：定义状态、定义转移条件、定义副作用、处理异常。你可以把 Agent 的每一步想象成一个数据库事务：要么成功推进状态，要么回滚到上一个 checkpoint。

这种类比能让你在面试中快速建立共识。当面试官问”LangGraph 是怎么工作的”，你可以说：”它就像一个轻量级的工作流引擎，状态是显式的，转移由 LLM 或函数决定，并且每个步骤都可以持久化以便恢复。”

📝 设计决策

  1. 为什么选 PostgreSQL + pgvector？
    利用现有 RDS 运维经验，减少基础设施复杂度；pgvector 支持 ivfflat/hnsw 索引，能满足中等规模检索需求。

  2. 为什么用 LangGraph 管理 Agent 状态？
    显式状态机让调试和回归测试更容易，也便于实现 human-in-the-loop。

  3. 如何保证输出安全？
    所有生成的 SQL 先经过 SQL parser 校验，再进入只读执行器做试运行，最后才允许写入操作。

📰 技术雷达：AI 工程招聘、工具与社区动态

1. 招聘市场信号

2026 年 AI 应用工程师岗位持续分化。几个明显趋势：

  • “全栈 AI 工程师” 需求增长：企业不再只需要会调模型的人，而是需要能把模型封装成产品的人。后端工程师转型有天然优势。
  • RAG 岗位门槛提高：单纯的向量检索已经不够，岗位开始要求评估体系、多路召回、Agentic RAG。
  • Agent 基础设施 成为热点：LangGraph、AutoGen、CrewAI 等框架的实战经验成为加分项。
  • AI 可观测性 专业化：专门做 LLM Trace、Eval Platform、Guardrails 的工程师需求上升。

2. 值得关注的开源项目

  • LangGraph Platform：LangChain 推出的部署与监控一体化平台，支持远程可调用图、持久化、人机协同。
  • OpenInference：Arize AI 主导的 LLM 可观测性标准，兼容 OpenTelemetry。
  • Ragas v0.2：新增 Agentic RAG 评估指标，支持多轮对话和工具调用评估。
  • pgvector v0.8：持续优化 HNSW 索引性能，增加更多距离函数和并行构建支持。
  • PydanticAI：Pydantic 团队推出的 Agent 框架，强调类型安全和结构化输出。

3. 论文与思想

  • 《The AI Engineering Workflow》（新兴实践总结）：强调 AI 工程应该像软件工程一样有版本管理、评估流水线和回滚机制。
  • 《Agentic RAG: A Survey》：系统梳理了从单轮 RAG 到多步 Agentic RAG 的演进路径。
  • 《LLM-as-a-Judge》相关研究：如何降低人工标注成本，同时保证评估质量。

4. 社区建议

  • 在 GitHub 上维护一个 ai-engineering-playground 仓库，记录每周小实验。
  • 参与 LangChain / LangGraph 的 GitHub Discussion，回答新手问题能快速建立影响力。
  • 在内部做一场”AI 工程入门”分享，是最好的巩固知识方式。

✅ 今日行动清单

  1. 选择 1 个作品集项目：从本章选题方向里挑一个最贴近你后端经验的。
  2. 运行 README 生成器：用上面的脚本生成项目骨架文档。
  3. 搭建最小可运行版本：不要追求完美，先让核心流程跑通。
  4. 写入 3 个量化指标：哪怕只是”Recall@5 = 0.72”也比”效果很好”有说服力。
  5. 发布到 GitHub：公开仓库，完善 README，让别人能 5 分钟跑起来。
