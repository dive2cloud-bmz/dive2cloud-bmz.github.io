Week4 Day25｜模拟面试与 Capstone 复盘：把 RAG-Agent 项目讲成可落地的工程故事

目标：用一次完整的模拟面试，把过去 24 天学到的 RAG、Agent、LangGraph、生产工程知识串成一段可运行、可复盘的工程叙事。

🚀 核心洞察：面试不是考试，而是”证明你能交付”

作为从 RDS PostgreSQL 后端转型 AI 应用工程师的工程师，你最大的优势不是懂多少 LLM 论文，而是能把 AI 系统当成一个需要持久化、可观测、可回滚、可扩展的分布式服务来设计和落地。面试官想听的，不是你背了多少 RAG 名词，而是你能否回答三个问题：

  1. Why this design？ 为什么选这个架构，而不是直接调用 OpenAI API？
  2. How does it fail？ 系统会在哪里失败，你怎么发现、怎么兜底？
  3. How do you know it works？ 你用什么指标、什么数据、什么流程证明它在变好？

今天这篇不是面经罗列，而是把过去三周的 RAG-Agent 学习路径打包成一个可讲述、可运行、可复盘的 Capstone 项目，并模拟一次 45 分钟的系统设计 + 代码复盘面试。

🧠 核心概念：AI 应用工程师面试的四个考察维度

1. 从 STAR 到 SOAR：讲项目经验的叙事框架

传统的 STAR（Situation-Task-Action-Result）适合描述已知任务，但 AI 项目往往处于高度不确定的探索状态。建议用 SOAR 框架：

维度 含义 面试中应给出的证据
Situation 业务背景与痛点 “客服团队每天收到 3000+ 工单，80% 是重复政策问题”
Objective 可量化的目标 “把首次响应时间从 4 小时降到 30 秒，同时保持 90% 以上的回答准确率”
Action 你做了什么关键决策 “我们没选纯 prompt 方案，而是用 RAG + Agent，因为知识库需要动态更新”
Result 结果与反思 “端到端延迟从 8s 降到 1.2s，但发现 rerank 阶段是瓶颈，后续加了 ColBERT”

关键技巧：结果里一定要包含”我学到了什么”和”如果重来我会怎么改”。这能证明你有工程判断力，而不是只会执行。

3. Capstone 复盘的五个技术维度

一个能拿得出手的 Capstone 项目，至少要在以下五个维度有可量化的思考：

维度 你需要回答的问题 常见反模式
检索质量 Recall@K 是多少？Chunk 策略怎么影响结果？ 只说”用了 FAISS”，不提评估
生成可控性 如何减少幻觉？怎么做引用溯源？ 完全依赖模型自律
Agent 可靠性 Tool 失败怎么重试？状态如何持久化？ 状态存在内存里，重启就丢

可观测性 如何追踪一次用户请求的完整链路？ 只有日志，没有 trace 和指标

4. 模拟面试常见问题库

系统设计类：

  • “设计一个面向 10 万日活用户的智能客服系统。”
  • “如果用户问了一个知识库里没有的问题，你怎么办？”
  • “RAG 的检索结果和 LLM 生成结果冲突时，你信任谁？”

代码/工程类：

  • “请实现一个带重试和退避的 Tool Calling 函数。”
  • “你如何用 pgvector 实现混合检索（向量 + 全文）？”
  • “Agent 状态存储在 PostgreSQL 里，表结构怎么设计？”

行为/经验类：

  • “你作为后端工程师，转型 AI 应用工程师的最大挑战是什么？”
  • “讲一个你解决过的最复杂的线上问题。”
  • “如果模型输出不稳定，你怎么向业务方解释？”

🔗 后端桥接：用 PostgreSQL 概念理解 AI 系统

这个章节是把你的后端背景变现为面试优势的关键。

1. Embedding ≈ 行序列化，但丢失了部分语义精度

在 PostgreSQL 里，一行数据是结构化的、可精确查询的。Embedding 是把文本/图像/代码压缩成一个稠密向量，相当于一种”有损序列化”。它能回答”这句话和哪句话最像”，但无法回答”这句话精确等于什么”。因此 RAG 系统通常需要向量检索 + 关键词过滤 + 后处理校验三层。

2. 向量索引 ≈ B-tree 索引，但语义近似代替了精确排序

B-tree 帮你按值快速定位；HNSW / IVFFlat 帮你按向量距离快速找邻居。两者的核心差异是：B-tree 返回的是精确排序，而向量索引返回的是近似最近邻。这意味着向量检索后通常要加一次重排（Rerank），就像 PostgreSQL 的执行计划里有时会先走索引再回表过滤。

3. Agent State ≈ 事务状态机

LangGraph 里的 State 本质上是一个有向图上的状态机。你可以把它想象成 PostgreSQL 里一个带状态字段的工单表：

LangGraph 的 checkpoint 就是这个表的自动化版本。它的价值在于：你可以像调试数据库事务一样，回放和分支 Agent 的执行过程。

4. Tool Calling ≈ 存储过程 + RPC

LLM 的 Tool Calling 机制，本质上是让模型根据上下文决定调用哪个外部函数。这和 PostgreSQL 的存储过程、或者后端服务之间的 RPC 调用非常相似：

概念 PostgreSQL / 后端 LLM Tool Calling
接口契约 Schema / Protocol Function Schema（JSON）
调用决策 应用代码显式调用 LLM 根据 prompt 隐式决策
参数校验 类型检查 / 序列化 JSON Schema 校验
失败处理 重试 / 熔断 / 降级 RetryPolicy / Fallback Tool
权限控制 ROLE / ACL Tool Whitelist + 输入过滤

📰 技术雷达

1. LangGraph v0.2：更原生的 checkpoint 与人机协作

LangGraph 在 2024 下半年持续强化 checkpoint 持久化能力，新增 SqliteSaver / PostgresSaver 等官方实现。对于 PostgreSQL 后端背景的工程师来说，这意味着 Agent 状态管理可以复用你熟悉的事务、备份、审计机制，而不是重新造一套状态存储。

2. 评估框架：从离线指标到在线 A/B

RAG 评估正在从单一的 NDCG/Recall 向端到端业务指标演进。例如 LangChain 的 LangSmith、OpenAI 的 SimpleEval、以及开源的 RAGAS 都在强调：评估不能只测检索，要测答案正确性、引用忠实度、用户满意度。

3. 小型模型 + 长上下文：RAG 的边界在移动

Gemini 1.5 Pro 和 Claude 3.5 Sonnet 的上下文窗口已经突破 100K token，部分场景下”全上下文注入”可以替代复杂 RAG。但面试中的正确回答是：上下文窗口解决的是”能读多少”，RAG 解决的是”读什么最相关”。两者不是替代关系，而是分层关系。

4. 生成式 UI：Agent 不仅返回文本，还返回组件

Vercel 的 AI SDK、OpenAI 的 “function calling with UI” 方向都在探索：Agent 的输出可以是结构化数据，前端根据 schema 自动渲染表单、图表、按钮。这对后端工程师的启示是：Agent 的接口设计要从”返回字符串”升级为”返回结构化事件流”。

写在最后

转型 AI 应用工程师的 6 个月旅程，不是要你成为一个prompt 工程师，而是要你成为一个能把 AI 能力工程化、产品化、可运维化的人。你今天能讲清楚 RAG-Agent 系统的数据流、失败模式、成本结构和评估方法，就已经具备了高级 AI 应用工程师的核心素养。

下一次面试，试着用这一句话开场：

“我过去做 PostgreSQL 后端，关注的是数据如何被可靠地存储和查询；现在我做 AI 应用，关注的是如何让模型在正确的时间、以正确的成本、调用正确的工具，拿到正确的上下文。”

这句话本身，就是一次漂亮的转型叙事。
