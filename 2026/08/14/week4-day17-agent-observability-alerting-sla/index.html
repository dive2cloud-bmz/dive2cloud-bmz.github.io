像运维数据库一样运维 Agent：可观测性、告警与 SLA 设计

目标阅读时长：20 分钟 ｜ 关键词：Agent Observability、SLO、OpenTelemetry、LangSmith、Tracing、告警

🚀 核心洞察

作为曾经的 RDS PostgreSQL 后端工程师，我对「可观测性」的第一反应从来不是漂亮的 Dashboard，而是凌晨三点被 PagerDuty 吵醒时，能否在 30 秒内定位一条慢 SQL 的根因。数据库的运维哲学非常简单：每一个请求都必须可追踪、每一个异常都必须可度量、每一次超时都必须可解释。

当我们把这套哲学迁移到 AI Agent 时，会发现一个令人不安的事实：Agent 比数据库更难观测。数据库的输入输出是结构化的 SQL 和结果集，而 Agent 的输入是模糊的自然语言，输出是决策链、工具调用序列和一段可能胡言乱语的文本。数据库的性能瓶颈通常是 I/O 或锁等待，而 Agent 的瓶颈可能是模型幻觉、工具选择错误、上下文窗口溢出，甚至是提示词中一个逗号的位置。

今天的核心洞察是：Agent 可观测性不是「给 LLM 加日志」，而是给一段自主决策流程建立完整的遥测体系。 这个体系必须回答四个问题：

  1. Trace（追踪）：Agent 从接收到请求到给出最终答案，中间经历了哪些步骤？
  2. Metric（指标）：每一步的延迟、成本、成功率、质量分数如何？
  3. Log（日志）：模型原始输出、工具参数、状态变化是否完整留存？
  4. Alert（告警）：哪些信号说明 Agent 正在「生病」，需要人工介入？

如果你曾为 PostgreSQL 配置过 pg_stat_statements、auto_explain、慢查询告警和 P95 延迟 SLO，那么你已经掌握了 Agent 可观测性 70% 的思维模型。剩下的 30%，是把「SQL 执行计划」换成「Agent 执行轨迹」，把「查询耗时」换成「端到端推理耗时 + Token 成本」。

🧠 核心概念

1. Agent 可观测性的三支柱与扩展维度

传统微服务可观测性由三大支柱构成：日志（Logs）、指标（Metrics）、追踪（Traces）。这三个维度对 Agent 同样适用，但远远不够。Agent 是一个语义计算系统，它的健康状况不仅取决于请求是否成功返回，还取决于返回内容是否正确、是否安全、是否经济。

我们可以把 Agent 可观测性扩展为 「三支柱 + 三维度」：

维度 传统微服务 AI Agent 关键问题
Logs 应用日志、错误堆栈 提示词、模型输出、工具调用参数、状态快照 这次调用到底发生了什么？
Metrics QPS、P99 延迟、错误率 Token 消耗、LLM 调用次数、工具成功率、幻觉分数 系统整体健康吗？
Traces 请求链路、RPC 调用 Agent 思考-行动循环、多 Agent 协作链 请求为什么慢？错在哪一步？
Cost 基础设施成本 单请求模型成本、缓存命中率 这个回答花了多少钱？
Quality 业务成功率 回答相关性、事实性、用户满意度 回答对用户有用吗？
Safety 安全事件数 提示注入尝试、越权工具调用、敏感信息泄露 系统有没有被攻击或误导？

这六个维度共同构成了 Agent 的完整可观测性视图。漏掉任何一个维度，都可能在生产环境中付出惨痛代价。比如只监控延迟和错误率，你可能会发现某个 Agent 的响应很快、也没有报错，但用户满意度却持续下降，因为它正在稳定地产生「看似合理但完全错误」的答案。

2. Traces：把 Agent 的「黑盒推理」变成「执行计划」

Agent 的核心执行单元是「思考 → 行动 → 观察」的循环。每一次循环都应该被记录为一个 Span，整个请求则是一个 Trace。这比传统 RPC 追踪更复杂，因为 Agent 的调用图不是静态的：它可能调用 0 个工具，也可能调用 10 个工具；可能在某一步进入人类确认流程，也可能因为条件判断而走向不同的分支。

  • span.kind: llm, tool, retriever, memory_read, memory_write, human
  • llm.model_name: 模型名称，如 gpt-4o
  • llm.prompt_tokens, llm.completion_tokens, llm.total_tokens
  • llm.temperature, llm.max_tokens
  • tool.name, tool.input, tool.output, tool.duration_ms
  • error.type, error.message, error.stacktrace（如果失败）

这种细粒度的追踪让事后分析成为可能。当用户投诉「Agent 昨天给了我一个错误答案」时，你可以像回放 PostgreSQL 的 pg_stat_statements 一样，精确找到那一次的完整 Trace。

3. Metrics：为 Agent 设计 RED + COST 指标体系

微服务领域常用的 RED 指标（Rate, Errors, Duration）可以无缝迁移到 Agent，但需要额外补充 COST 维度，因为 LLM 是按 Token 计费的。

RED 指标：

  • Rate: 单位时间内的 Agent 请求数，按 Agent 类型、模型、用户分层。
  • Errors: Agent 执行失败率，包括工具调用失败、LLM API 错误、解析错误、异常退出等。
  • Duration: 端到端延迟，以及每个阶段（首次 Token 时间、推理时间、工具调用时间、总时间）的延迟。

COST 指标：

  • Cost per request: 单次请求的平均/分位成本。
  • Cost per 1k successful answers: 每千次成功回答的总成本。
  • Token efficiency: 完成同类型任务所需 Token 数的趋势。
  • Cache hit rate: 提示词缓存、Embedding 缓存、工具结果缓存的命中率。

质量指标：

  • Response relevance: 回答与用户问题的相关性，可用 Embedding 余弦相似度或小型分类模型打分。
  • Faithfulness: 回答是否忠实于检索到的上下文，可用 RAGAS 等框架评估。
  • User feedback: 显式反馈（点赞/点踩）和隐式信号（是否追问、会话是否继续）。
  • Tool selection accuracy: Agent 是否选择了正确的工具，可通过人工标注或自动评估。

把这些指标汇集成一个 Dashboard，就能像监控 PostgreSQL 的 pg_stat_database 一样监控 Agent 的健康状况。

4. 告警：滞后指标 vs 领先指标

告警设计是运维中最容易犯错的地方。太多告警会导致「告警疲劳」，太少告警会错过真实故障。Agent 系统的告警应该区分两类指标：

滞后指标（Lagging Indicators）：反映已经发生的问题，通常用于事后复盘。

  • 错误率突增
  • P99 延迟超过阈值
  • 用户投诉量上升
  • 单请求成本异常升高

领先指标（Leading Indicators）：反映潜在风险，通常用于提前干预。

  • 首次 Token 时间（TTFT）持续变长，预示模型 Provider 可能拥塞
  • 工具调用失败率在单次请求内多次重试，预示工具服务不稳定
  • 提示注入攻击特征增加，预示安全风险上升
  • 上下文长度接近模型上限的比例升高，预示即将出现截断或成本激增

5. SLA 与 SLO：从「能跑」到「承诺」

SLA（Service Level Agreement）是对用户的承诺，SLO（Service Level Objective）是内部目标。对于 Agent 系统，建议定义四类 SLO：

SLO 类型 示例目标 测量方式
可用性 月度可用性 ≥ 99.9% 健康检查 + 端到端探活
延迟 p95 端到端延迟 ≤ 5s APM Trace 分位统计
成本 单次请求成本 ≤ $0.05 Token 用量 × 模型单价
质量 用户满意度 ≥ 4.0/5 显式评分 + 隐式行为

定义 SLO 时要注意可测量性和可行动性。比如「Agent 回答正确率 ≥ 90%」听起来很好，但如果没有自动评估 pipeline，这个 SLO 就是不可执行的。更好的做法是先用人工标注建立基准，再逐步引入自动评估。

此外，SLO 需要配套错误预算（Error Budget）。如果某个月的错误预算在一周内耗尽，就应该触发熔断：暂停新功能发布、冻结模型升级、集中修复稳定性问题。这和数据库发布大版本前的「变更冻结窗口」是同一个逻辑。

6. 主流工具链选型

目前 Agent 可观测性工具链正处于快速演化期，主要玩家包括：

工具 核心定位 优势 适用场景
LangSmith LangChain 生态官方 与 LangChain/LangGraph 深度集成，开箱即用 全 LangChain 栈项目
Langfuse 开源 LLM 可观测性 自托管、OpenTelemetry 兼容、成本透明 需要数据驻留的中大型企业
Phoenix (Arize) 开源 LLM 评估与追踪 强大的评估集、RAG 评估、Embedding 可视化 重视模型评估和 RAG 质量
OpenLLMetry OpenTelemetry 封装 标准 OTel 语义、 vendor 无关 已有 Prometheus/Grafana/Tempo 栈
Weights & Biases ML 实验与模型管理 模型训练追踪、Prompt 版本管理 模型迭代频繁的场景

对于后端工程师来说，最值得关注的是 OpenTelemetry + Prometheus/Grafana/Tempo/Jaeger 这套标准云原生可观测性栈。它让你可以用同一套基础设施同时监控 Agent、微服务和数据库，避免引入额外的孤岛系统。

🔗 后端桥接：用 PostgreSQL 思维理解 Agent 可观测性

把 Agent 看成一台「语义数据库」，很多抽象会立刻变得亲切。

1. Agent Trace ≈ PostgreSQL EXPLAIN ANALYZE

PostgreSQL 的 EXPLAIN ANALYZE 会告诉你一条 SQL 的执行计划、每一步的代价和实际耗时。Agent 的 Trace 就是它的「执行计划」：

PostgreSQL Agent
EXPLAIN ANALYZE Trace/Span 树
查询计划节点（Seq Scan, Index Scan, Hash Join） LLM 调用、Tool 调用、Memory 读写
actual time=.. rows=.. duration_ms, token_count, input/output
成本估算（cost=..） 预估成本与实际 Token 消耗

当你优化 Agent 时，第一步总是「打开 Trace」，就像优化 SQL 时第一步总是打开 EXPLAIN ANALYZE。

2. Tool Call ≈ Stored Procedure 调用

PostgreSQL 的 stored procedure 接受参数、执行逻辑、返回结果。Agent 的工具调用完全类似：

对 stored procedure 你会监控调用次数、平均执行时间、错误率；对 Tool Call 你也应该监控完全相同的指标。区别在于 Tool Call 的输入输出是非结构化的自然语言，因此还需要额外的输入合法性校验和输出模式校验。

3. State Checkpoint ≈ WAL / 事务日志

LangGraph 的 checkpoint 机制把 Agent 状态持久化到存储中，这相当于 PostgreSQL 的 WAL（Write-Ahead Log）。两者都用于：

  • 崩溃恢复：从最近 checkpoint 恢复状态
  • 审计：回放历史状态变化
  • 并发控制：管理多会话状态隔离

不同之处在于，WAL 记录的是物理页面变更，而 Agent checkpoint 记录的是语义状态变更。但持久化、可回放、可审计的目标是一致的。

4. Token 预算 ≈ 连接池预算

PostgreSQL 的连接池限制了同时运行的查询数量，防止资源耗尽。Agent 的 Token 预算则限制了单次请求和全局的 Token 消耗，防止成本失控和上下文窗口溢出。

超过预算时，Agent 应该像连接池耗尽时一样优雅降级：返回简化答案、切换到更小模型、或提示用户缩小问题范围。

5. SLO ≈ 查询延迟 SLA

你给 PostgreSQL 设定的「P95 查询延迟 < 100ms」SLO，和给 Agent 设定的「P95 端到端延迟 < 5s」本质相同。两者都需要：

  • 持续采集分位延迟
  • 区分慢查询/慢 Agent 的根因
  • 建立告警和自动降级策略

唯一区别是 Agent 的延迟组成更复杂：它包括网络、模型推理、工具调用、向量检索、状态持久化等多个阶段。

📰 技术雷达

  1. OpenTelemetry LLM Semantic Conventions GA 在即：OpenTelemetry 社区正在推进 LLM 调用的语义约定标准化，预计 2024-2025 年成为官方推荐。这意味着未来所有 LLM 框架（LangChain、LlamaIndex、Haystack）的遥测数据格式将趋于统一，便于跨框架、跨模型比较。

  2. LangSmith 推出在线评估与数据集管理：LangSmith 近期强化了在线评估（Online Evaluation）功能，支持基于规则、LLM-as-judge 和自定义评估器对生产流量进行持续评分。对于没有自研评估平台的小团队，这是快速建立质量 SLO 的捷径。

  3. Langfuse 开源多模态 Tracing 与 Prompt 管理：Langfuse 新增了多模态输入输出追踪和 Prompt 版本管理，进一步缩小与 LangSmith 的功能差距。对于需要自托管、数据合规要求高的企业，Langfuse 仍是首选。

  4. Grafana LLM Plugin 与 k6 负载测试结合：Grafana 生态开始拥抱 LLM 可观测性，结合 k6 可以对 Agent 进行负载测试并同步采集延迟、Token 成本和质量指标。这为建立真实的 SLO 基线提供了工程化路径。

  5. Prompt 注入检测进入商业产品：多家安全厂商（如 HiddenLayer、Prompt Security、Lakera）推出了针对 Agent 的实时提示注入检测和响应产品。对于面向外部用户的 Agent，安全可观测性将成为 SLA 的硬性组成部分。

总结

今天的主题把后端工程师最熟悉的「数据库运维思维」迁移到了 AI Agent 的可观测性设计。核心要点如下：

Agent 可观测性需要从 Logs、Metrics、Traces 扩展到 Cost、Quality、Safety 六个维度；Trace 是 Agent 的「执行计划」，必须细粒度记录 LLM、Tool、Memory 的每一次交互；RED + COST 指标体系是监控 Agent 健康和成本的基础；告警要区分滞后指标和领先指标，避免告警疲劳；SLA/SLO 必须可测量、可行动，并配套错误预算机制；OpenTelemetry 是后端工程师最自然的选型，能与现有云原生可观测性栈无缝集成。
