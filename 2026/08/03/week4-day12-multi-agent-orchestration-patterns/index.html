从单兵到编队：Multi-Agent 编排的架构模式与 LangGraph 实战

🚀 核心洞察：当 Agent 数量超过一个，架构比模型更重要

过去两周，我们把单个 Agent 的能力拆解到了极致：Function Calling 让它能调用外部工具，ReAct 让它边想边做，Plan-and-Execute 让它先谋后动，ToT 让它多路探索。但真实世界里的复杂任务——比如「完成一次完整的需求评审到代码合并」——很难靠一个 Agent 独立完成。

作为后端工程师，你一定熟悉这个场景：当业务逻辑膨胀到一个人写不完时，我们会把系统拆成多个微服务；当一次操作涉及多个服务时，我们会引入编排层（Orchestrator）来协调调用顺序、处理失败回滚、保证最终一致。Multi-Agent 系统本质上是一样的：每个 Agent 是一个具备特定能力的「服务」，而编排层决定它们什么时候被调用、如何交换信息、出错时怎么恢复。

今天我们要回答的核心问题是：如果把一群 Agent 当成一个分布式系统来设计，常见的架构模式有哪些？各自适合什么场景？以及如何用 LangGraph 把它们落地成可运行的代码。

🧠 核心概念：Multi-Agent 编排的全景地图

1. 编排到底在编排什么？

Multi-Agent Orchestration 不是简单地把多个 LLM 调用串起来，它要管理三件事：

维度 要解决的问题 后端类比
任务路由 一条用户请求该交给哪个 Agent 处理？ API Gateway / 负载均衡
状态流转 Agent 之间如何共享上下文和中间结果？ 共享存储 / 消息队列
执行控制 串行、并行、条件分支、循环怎么表达？ 工作流引擎 / 状态机

一个设计良好的编排层，能让 Agent 团队像一支训练有素的工程团队：每个人知道自己的职责，也知道该在什么时候把接力棒交给谁。

2. 三种经典编排模式

模式一：Supervisor（监督者模式）

一个中心 Supervisor Agent 负责理解用户意图、拆解任务、选择下一个该执行的 Worker Agent，Worker 只与 Supervisor 通信。

优点：结构清晰、调试简单、适合任务阶段明确的场景。
缺点：Supervisor 成为单点瓶颈，所有上下文都要经过它，长链路时上下文膨胀明显。

适合场景：代码审查、报告生成、客服工单分诊。

模式二：Swarm（蜂群模式）

Agent 之间平级协作，通过「交接（Handoff）」把对话控制权从一个 Agent 转移到另一个。没有永远的中心节点，谁适合当前任务，谁就接管。

优点：更接近真实客服或销售团队的协作方式，灵活自然。
缺点：交接边界需要精心设计，否则容易陷入无限传递。

适合场景：客户支持、销售线索跟进、多领域咨询。

模式三：Hierarchical Teams（分层团队模式）

Supervisor 下面再挂 Supervisor，形成树状结构。顶层负责整体目标，中层负责子项目，叶子节点负责具体执行。

优点：可扩展性强，适合大规模复杂任务，责任边界清晰。
缺点：层级过多会增加延迟，顶层 Supervisor 可能看不到一线细节。

适合场景：大型项目交付、跨部门协作、复杂研究任务。

3. 状态管理：Multi-Agent 系统的共享内存

无论哪种模式，Agent 之间都需要共享状态。LangGraph 通过 StateGraph 提供一个显式的共享状态对象，所有节点都可以读写它。

一个好的状态设计要遵循三个原则：

  1. 最小够用：只放必要的上下文，避免把整块对话历史塞给每个 Agent。
  2. 类型清晰：用 TypedDict 或 Pydantic 定义字段，避免运行时拼写错误。
  3. 写入隔离：每个 Agent 尽量只写自己负责的字段，减少冲突。

4. Handoff：控制权交接的艺术

Handoff 是 Swarm 模式的核心。它回答的问题是：当前 Agent 什么时候应该把任务交给别人？

常见触发条件：

触发条件 说明
能力边界 当前 Agent 发现自己没有处理该子任务的工具
用户意图转移 用户话题从账单切换到技术支持
任务完成 当前阶段结束，需要进入下一阶段
错误恢复 当前 Agent 多次失败，需要升级处理

Handoff 时通常要传递的最小信息包括：用户原始请求、当前已完成的中间结果、下一位 Agent 需要关注的上下文。

🔗 后端桥接：用分布式系统的眼光看 Agent 编排

作为 PostgreSQL 后端工程师，你已经接触过大量与 Multi-Agent 编排概念相通的系统。下面这张对照表能帮你快速建立直觉：

AI 概念 后端概念 类比说明
Agent 微服务 每个 Agent 有独立职责和接口（Prompt + Tools），像一个个微服务
Supervisor API Gateway / 编排服务 统一入口，负责路由和聚合
Shared State 共享数据库 / Redis 多个 Agent 通过共享状态交换信息
Handoff 消息队列 + 路由键 一个服务处理完后把消息路由到下一个服务
Tool Call RPC / HTTP 调用 Agent 调用外部能力的标准接口
RePlan Saga 补偿 / 重试策略 执行失败时调整计划，保证最终一致
Long-running Task 异步工作流 复杂任务不适合同步阻塞，需要状态持久化

特别值得展开的是 Saga 模式。在分布式事务中，Saga 把一个长事务拆成多个本地事务，每个本地事务提交后通过「补偿操作」来回滚之前的步骤。Multi-Agent 的长链路任务非常相似：如果 Reviewer 发现 Coder 的代码有严重问题，不应该从头再来，而是只让 Coder 修正相关部分，然后继续后续流程。这就是 Agent 版本的 Saga：不是全量回滚，而是局部重试 + 状态前进。

另一个值得类比的点是 PostgreSQL 的查询优化器。优化器会根据统计信息生成执行计划，决定是走索引还是全表扫描、是 Nested Loop 还是 Hash Join。Multi-Agent 的 Supervisor 也类似：它根据当前状态（用户请求、已收集信息、可用 Agent 能力）生成一个「执行计划」，然后在执行中根据反馈动态调整。

📰 技术雷达

开源框架动态

  • LangGraph 0.2.x：新增 create_react_agent、create_supervisor 等高层 API，大幅降低了多 Agent 系统的样板代码。LangGraph Studio 也进入公测，可以可视化调试 Agent 执行路径。
  • OpenAI Swarm：OpenAI 发布的实验性多 Agent 框架，主打轻量级 Handoff，适合构建客服、销售等对话型 Multi-Agent 系统。
  • AutoGen v0.4：微软重构后的版本引入了 AgentChat 和 Core 两层架构，更强调可扩展性和可观测性。
  • CrewAI： continues to focus on「角色 + 任务 + 工具」的声明式编排，适合快速搭建研究报告、内容生成类工作流。

值得关注的研究方向

  • Agent 间的显式通信协议：如何让 Agent 像微服务一样定义清晰的接口契约，而不是靠 Prompt 里的自然语言约定。
  • 多 Agent 系统的可观测性：当一条请求经过五六个 Agent 后，如何追踪完整调用链、定位是哪一步产生了错误。
  • 成本感知的编排策略：不同 Agent 可以使用不同模型（Planner 用 GPT-4o，Executor 用 GPT-4o-mini），如何在效果与成本之间自动权衡。

小结

Multi-Agent 不是把多个 LLM 简单拼在一起，而是用系统设计的思路解决「谁做什么、何时交接、状态如何共享」的问题。Supervisor 模式适合阶段清晰的任务，Swarm 模式适合对话式协作，Hierarchical Teams 适合大型复杂项目。

作为后端工程师，你最大的优势不是 Prompt 写得花，而是已经习惯了分布式系统中的拆分、编排、状态共享和故障恢复。把这些思维迁移到 Agent 设计上，你会发现 Multi-Agent 系统并没有想象中那么神秘——它本质上是一群有语言能力的微服务，而你是它们的架构师。
