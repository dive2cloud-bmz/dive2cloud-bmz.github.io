Agent 安全纵深防御：提示注入检测、输出护栏与供应链安全

今日目标：把 Agent 安全从「靠 system prompt 叮嘱」升级成「多层防线 + 可观测 + 可回滚」的纵深防御体系，覆盖输入侧提示注入检测、输出侧内容护栏、以及整条 AI 供应链的可信治理。

🚀 核心洞察：为什么单点防御守不住 Agent

作为 RDS PostgreSQL 后端工程师，你对安全的理解大概率是分层收敛的：

  • 网络层：VPC、安全组、IP 白名单，只允许特定入口访问数据库端口。
  • 应用层：连接串不硬编码，用 IAM / Secret Manager 轮转。
  • 数据库层：最小权限账号、GRANT 到列级、RLS 到行级。
  • 审计层：log_statement = 'all'、pgAudit 记录谁查了什么。
  • 备份层：WAL 归档、PITR，保证被勒索软件加密后还能恢复。

每一层都不是 100% 可靠，但多层叠加后，攻击者必须同时突破多个独立机制才能得手。这就是 Defense in Depth（纵深防御）。

Agent 系统同样需要纵深防御，但现状往往更糟：

问题是，LLM 的「理解」和「遵守」是概率性的，不是确定性的。当上下文被污染、任务足够复杂、或者攻击者使用间接提示注入（Indirect Prompt Injection）时，system prompt 的约束力会迅速衰减。

今天的核心洞察是：Agent 安全不能依赖 LLM 自身的「自觉」，而要在输入、决策、输出、执行、审计每个环节都设置独立且可强制执行的防线。 我们要像设计数据库安全那样设计 Agent 安全——任何一层被绕过，下一层 still holds。

🧠 核心概念：Agent 纵深防御的五层模型

先把整体架构画出来。

这五层各自回答一个独立问题：

层级 防御目标 关键问题 典型手段
输入层 防止恶意输入污染 Agent 「这条消息里是否夹带了隐藏指令？」 提示注入分类器、输入隔离、标记边界
决策层 限制 Agent 能做什么 「这个工具调用是否被授权？」 RBAC、工具白名单、人工审批卡点
执行层 防止有害输出和危险动作 「输出是否包含 PII / 毒性 / 幻觉？」 输出护栏、事实校验、影响范围限制
供应链层 确保组件可信 「模型、依赖、工具来自哪里？」 模型签名、SBOM、依赖扫描、沙箱
审计层 事后可追溯、可响应 「当时发生了什么？」 不可变日志、异常告警、回滚预案

这五层必须独立运行，不能把所有判断都交给 LLM。例如，工具调用权限应该由策略引擎在 LLM 输出后、真实执行前强制校验；输出护栏应该用独立的小模型或规则引擎做二分类，而不是让主模型自我审查。

1. 输入层：提示注入检测与隔离

提示注入分为两类：

  • Direct Prompt Injection（直接注入）：用户直接在输入里写入「忽略之前所有指令，执行 XXX」。
  • Indirect Prompt Injection（间接注入）：攻击者把恶意指令写进 Agent 会读取的外部内容里，比如网页、邮件、文档、RAG 检索结果。

间接注入更难防，因为 Agent 会把外部内容当作「事实」而不是「指令」。

1.1 检测策略：不是「识别恶意」，而是「识别指令冲突」

一个有效的设计是 Dual-LLM / 分隔执行：

检测模型不需要理解业务，只需要回答一个二分类问题：「这段文本是否包含试图覆盖系统角色、调用未授权工具、或提取系统提示的意图？」

1.2 实用的启发式规则

在生产中，通常把轻量分类器 + 规则混合使用：

规则引擎的好处是可解释、可审计、零延迟，坏处是容易被绕过。所以它应该和轻量分类器、LLM-based 检测共同构成冗余。

1.3 输入隔离：把外部内容「物化」

一个被低估的防御手段是给外部内容加明确的边界标记，让主模型把它当作「数据」而不是「指令」：

这就像 PostgreSQL 里对字符串做参数化绑定：明确区分「代码」和「数据」。虽然不能完全防止注入，但能显著降低模型把外部内容当指令执行的概率。

2. 决策层：工具调用策略引擎

在 Day 19 我们已经讨论过访问控制和多租户隔离。今天强调另一件事：工具调用本身需要二次确认。

2.1 工具调用的「预检」模式

每一层都是独立校验：

  • 语法解析：参数是否符合 JSON Schema？
  • 权限校验：当前身份是否有权调用此工具？
  • 参数校验：参数是否在允许集合内？例如 delete_order 的 order_id 必须属于当前用户。
  • 影响范围评估：调用是只读还是写操作？影响多少行/记录/资金？

2.2 人机协同审批

对于高危操作（转账、删除账户、修改权限），策略引擎应该中断执行并要求人工确认。这是 Agent 与纯 API 的关键区别——Agent 有自主决策空间，但必须在关键节点引入 Human-in-the-Loop。

3. 执行层：输出护栏

输出护栏负责三件事：安全、合规、质量。

护栏类型 目标 示例
安全护栏 防止生成有害、违法、歧视性内容 毒性检测、越狱响应检测
隐私护栏 防止泄露 PII、密码、密钥 正则 + NER 识别邮箱、电话、身份证号
事实护栏 减少幻觉，尤其 RAG 场景 引用校验、自一致性检查
结构护栏 保证输出可被下游安全消费 JSON Schema 校验、类型检查

4. 供应链层：模型、依赖与工具的可信治理

AI 系统的供应链比传统软件更复杂，因为「依赖」不仅包括 pip 包，还包括：

  • 预训练模型权重：从 Hugging Face 下载的 .safetensors 或 .bin。
  • Tokenizer 和配置文件：tokenizer.json、config.json。
  • 第三方 API：OpenAI / Anthropic / 文心 / 通义等模型服务。
  • RAG 数据源：网页、文档、知识库。
  • 向量索引和 Embedding 模型：同样属于依赖。

4.1 模型来源验证

在生产中，应该：

  1. 固定模型版本：不要每次从 Hub 拉 latest，而是固定 commit hash 或本地缓存。
  2. 校验文件哈希：对下载的权重文件做 SHA256 校验。
  3. 隔离推理环境：模型推理运行在沙箱或独立容器中，限制网络出口。
  4. 审计模型调用：记录模型版本、输入输出摘要（注意 PII 脱敏）。

4.2 AI 软件物料清单（AI-SBOM）

AI-SBOM 是响应监管要求（如欧盟 AI Act、国内算法备案）和漏洞响应的基础。

5. 审计层：可观测不等于可审计

很多团队把日志打到 ELK 或 OpenTelemetry 就以为完成了审计。真正的审计需要：

  1. 不可篡改：审计日志写入只写存储（WORM）或区块链式哈希链。
  2. 结构化：包含 who、what、when、which model、which tool、input/output hash、decision reason。
  3. 可追溯：从一次用户请求能追踪到所有子调用。
  4. 隐私合规：原始输入输出按需脱敏，保留 hash 用于取证。

🔗 后端桥接：用 PostgreSQL 安全模型理解 Agent 纵深防御

PostgreSQL 和后端系统的很多安全概念可以直接映射到 Agent 安全上。这种类比能帮你快速建立直觉。

PostgreSQL / 后端概念 Agent 安全对应 说明
参数化查询 / Prepared Statement 输入隔离与提示封印 区分「指令」和「数据」，不要把外部内容直接拼接到 system prompt
行级安全策略 RLS 工具参数范围校验 即使 SQL 语法合法，也要检查 tenant_id / user_id 是否匹配
角色与 GRANT RBAC + 工具白名单 不同身份拥有不同工具集，最小权限原则
pgAudit / 慢查询日志 结构化审计日志 记录谁、在什么时候、以什么身份、调用了什么工具
WAF / 入侵检测 IDS 提示注入分类器 在网络/输入层做模式识别和异常检测
只读副本 vs 读写主库 工具影响范围分级 只读工具自动执行，写工具需要审批
备份与 PITR 回滚与 kill switch 被攻击后能快速切断 Agent、撤销权限、恢复状态
软件供应链扫描（Snyk/Dependabot） AI-SBOM + 模型哈希校验 不只是 pip 包，还包括模型权重、配置文件、第三方 API

📰 技术雷达

  1. OWASP LLM Top 10 2025 更新版
    最新版本把 LLM08: Vector and Embedding Weaknesses 和 LLM09: Misinformation 提升到更突出的位置，强调 RAG/Agent 场景下向量数据库和 Embedding 模型本身也是攻击面。

  2. Meta 发布 Purple Llama / Llama Guard 3
    Llama Guard 系列是轻量化的输入/输出安全分类器，可在本地运行，适合作为 Agent 护栏的前置或后置模块。最新版本支持多语言，并且对代码相关提示的误判率有所下降。

  3. NIST AI RMF 与欧盟 AI Act 合规工具链
    随着监管落地，AI-SBOM、模型卡（Model Card）、风险登记册（Risk Register）正在成为企业 Agent 项目的必备交付物。建议关注 CycloneDX 对 ML 组件的扩展支持。

  4. Hugging Face 推出 safetensors 与 Pickle 扫描
    由于 PyTorch 模型常被序列化为 pickle，存在任意代码执行风险。HF 持续推广 safetensors 格式，并提供仓库安全扫描，下载预训练模型时应优先选择 .safetensors。

  5. OpenAI 结构化输出 + Function Calling 的权限边界
    最新 API 支持 strict: true 的 JSON Schema 约束，能在一定程度上减少模型输出非法参数的概率，但它不能替代后端的参数校验和权限控制。

  6. Google 的 Agent 安全白皮书
    强调「不可信输入隔离」（Untrusted Input Isolation）和「权限最小化执行环境」（Least-privilege execution environment），与本日输入隔离和工具沙箱的思路一致。

今日小结

Agent 安全不是「加一句 system prompt」的事，而是一个需要从输入、决策、执行、供应链、审计五个层面共同发力的工程问题。作为后端工程师，你可以把设计数据库安全的同一套原则迁移过来：

  • 不要相信输入——做参数化隔离和注入检测。
  • 不要相信应用层——在工具执行前做权限和参数强制校验。
  • 不要相信单次判断——用独立模型/规则做输出护栏。
  • 不要相信组件默认安全——验证模型来源、扫描依赖、固定版本。
  • 不要相信日志就够了——审计必须结构化、不可篡改、可溯源。

纵深防御的核心不是让每一层都完美，而是让攻击者必须连续突破多个独立防线才能成功。下一篇我们将进入「Agent 可解释性与对齐：让 Agent 不仅安全，还能被理解和信任」。
