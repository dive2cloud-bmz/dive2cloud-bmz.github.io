混合检索实战：在 PostgreSQL 中融合 Dense、Sparse 与 BM25

在上一篇 Week 5 Day 1 中，我们把 RAG 检索链路从头到尾调优了一遍：从 query 改写、向量索引选型，到重排序与评估指标。今天我们把视野再拉大一点——单一检索范式已经无法满足真实企业知识库的需求。无论是产品 SKU、故障单号、法律条文编号，还是内部缩写与专有名词，纯语义向量检索都可能在“关键词精确匹配”上翻车。而混合检索（Hybrid Retrieval）正是解决这个问题的主流工程方案。

这篇文章会带你从 Dense Embedding、Sparse Embedding 到 BM25 三种召回通道出发，最后在 PostgreSQL + pgvector 的单一数据库里把它们跑通，并用 RRF（Reciprocal Rank Fusion）做结果融合。作为从 RDS PostgreSQL 转型 AI 应用工程师的后端开发者，你会发现：这套方案和你熟悉的索引组合、执行计划、窗口函数几乎没有本质区别，只是检索单元从“行/词”变成了“向量/token”。

🚀 核心洞察：为什么单一向量检索不够？

一个真实的“翻车”场景

假设你正在为公司内部运维知识库做 RAG。用户问：

“PG-2024-0912 这个告警该怎么处理？”

纯向量检索会怎么做？它把这句话编码成一个 768 维或 1024 维的稠密向量，然后在向量空间里找最近邻。但问题在于：

  • “PG-2024-0912” 是一个精确 ID，嵌入模型在预训练阶段大概率没见过这个具体编号。
  • 即使模型把“PG”识别为 PostgreSQL 的缩写，它也很难把编号和某一篇特定文档绑定。
  • 如果知识库里有另一篇文档也讲 PostgreSQL 告警，只是编号不同，向量相似度可能非常接近，导致错误召回。

这就是 Dense Retrieval 的“精确匹配盲区”：它擅长语义泛化，却弱于罕见词、ID、缩写、产品型号、法律条款号等“符号级”匹配。

三种召回范式的互补性

召回方式 擅长什么 不擅长什么 后端类比
Dense（语义向量） 同义改写、概念泛化、长尾语义 精确 ID、缩写、罕见词、数字 语义近似查询
Sparse（稀疏向量，如 SPLADE） 关键词扩展 + 语义相关性 推理成本略高、索引稀疏 带权重倒排索引
BM25（词袋 + TF-IDF） 精确词匹配、长文档排序成熟 无法理解同义词、需分词 PostgreSQL tsvector + ts_rank_cd

混合检索的核心思想很简单：让三种通道各自发挥长处，再用融合算法把结果合并。就像我们在 PostgreSQL 里不会只用 B-tree，而是根据查询模式组合 B-tree、GIN、GiST、BRIN 一样。

核心公式直觉

混合检索通常不是简单地把三种分数加权相加，因为它们的分数尺度不同：

  • Dense 相似度：通常落在 [0, 1] 或 [-1, 1]（cosine）。
  • BM25：无固定上界，受文档长度和词频影响。
  • Sparse：可能是对数几率或内积，范围差异很大。

2. Sparse Retrieval：给关键词加上语义翅膀

Sparse Retrieval 的代表是 SPLADE（Sparse Lexical and Expansion Model）。它不再像传统倒排那样只用文档里出现的词，而是让模型“扩展”出相关但未必出现的词。

Sparse 向量的优势：

  • 保留关键词精确匹配能力（“PG-2024-0912”只要出现过就会命中）。
  • 通过模型扩展，获得一定的语义泛化能力。
  • 对长尾词和罕见词比 Dense 更稳健。

pgvector 在 0.7/0.8 版本后已经开始支持 sparsevec 类型，意味着我们可以在 PostgreSQL 里直接存储和检索 SPLADE 类的稀疏向量。

BM25 的强项：

  • 对精确词和常见关键词非常可靠。
  • 长文档惩罚、词频饱和等机制经过几十年验证。
  • 在 PostgreSQL 中原生支持，无需额外服务。

BM25 的弱项：

  • 无法理解同义词（“慢查询” vs “性能问题” vs “SQL 优化”）。
  • 对分词质量高度依赖，中文尤其如此。

关键点：

  1. 多路召回并行：三路召回可以并发执行，互不影响。
  2. Top-K 截断：每路只返回 Top-K（例如 100），避免融合阶段爆炸。
  3. Rank Fusion：用 RRF 或加权融合合并结果。
  4. 可选 Reranker：对融合后的 Top-K’ 再用 Cross-Encoder 做精排。

5. RRF：最实用的融合算法

Reciprocal Rank Fusion 由 Cormack、Clarke 和 Buettcher 在 2009 年提出，公式极简：

  • r_d：文档 d 在当前通道结果中的排名（从 1 开始）。
  • k：平滑常数，通常取 60。

为什么 k=60 是经验值？当排名很大时，1/(60 + r) 衰减较慢，可以给排在 100 名左右的文档一定分数；当排名很小时，前几名的分数差异也不会被拉得太大。

RRF 的优点：

  • 不需要训练，零超参调优成本。
  • 对分数尺度不敏感，天然适合多路异构结果。
  • 实现简单，可以在 SQL 里用窗口函数完成。

RRF 的缺点：

  • 只利用了排名，没有利用原始分数。如果某一路的置信度普遍很低，它仍然会被平等对待。
  • 无法动态学习各路权重（除非改用加权 RRF 或 Logistic Regression 融合）。

6. 加权融合与可学习融合

如果你已经有标注数据，可以考虑更精细的融合：

  • Weighted Sum：score = w1 * norm(dense) + w2 * norm(sparse) + w3 * norm(bm25)。需要先对各路分数做 min-max 或 z-score 归一化。
  • Logistic Regression / LambdaMART：用查询-文档对的标注训练一个排序模型，输入是三路特征。
  • LLM 作为融合器：把各路候选丢给 LLM，让它根据相关性重新排序（成本较高，适合高价值场景）。

对于从零开始构建的后端工程师，先用 RRF，再逐步升级到加权或学习排序，是最稳妥的路径。

2. 向量索引 ≈ B-tree / GIN / GiST 的高维版本

PostgreSQL 有多种索引，各有适用场景：

PG 索引 适用场景 向量索引对应
B-tree 精确值、范围查询 无（向量不精确匹配）
GIN 数组、全文检索 稀疏向量索引、倒排索引
GiST 几何、范围、全文 早期向量索引
BRIN 大块有序数据 不常用
HNSW / IVFFlat 近似最近邻 pgvector 向量索引

HNSW 就像在多维空间里建了一张“高速公路网”，牺牲了 100% 精确率，换取亚秒级检索。对于 RAG 来说，召回前 10 里有 9 个正确通常已经足够，因为后面还有 Reranker。

5. 多路召回 ≈ 多副本 / 多缓存读取

在高并发后端系统里，我们经常同时读缓存、读本地索引、读主库，最后合并结果。混合检索也是一样：

  • 向量索引：像 Redis 缓存，命中快但可能 miss 精确语义。
  • BM25：像主库查询，精确但缺少语义泛化。
  • Sparse：像本地 Bloom Filter，介于两者之间。

最终融合层就像你写的一个 merge_results() 函数，决定给用户返回什么。

📰 技术雷达

1. pgvector 0.8：稀疏向量进入主战场

pgvector 在 0.7 版本引入 sparsevec 类型，0.8 继续优化索引和距离函数。这意味着 PostgreSQL 正在从“只能做稠密向量检索”演进为“真正的多模态检索数据库”。对于已经在使用 RDS PostgreSQL 的团队，这可以显著降低引入 Milvus/Pinecone 的复杂度。

2. BGE-M3：一个模型同时输出 Dense + Sparse + ColBERT

BAAI 的 BGE-M3 是近期最受关注的多模态检索模型之一：

  • 支持 100+ 种语言。
  • 同时输出 Dense Embedding、Sparse Embedding 和 ColBERT 多向量表示。
  • 在 MS MARCO、Miracl 等基准上表现强劲。

它让“一个模型三路召回”成为可能，简化了部署，但推理成本也相对更高，需要在精度和延迟之间做权衡。

3. ColBERT v2：延迟交互模型的工程化

ColBERT 属于“延迟交互模型”（Late Interaction）：查询和文档分别编码成多个 token 级向量，在检索阶段再做细粒度交互。相比 Bi-Encoder，它的精度更高；相比 Cross-Encoder，它的检索效率更高。ColBERTv2 和 ColBERT-PLAID 进一步优化了索引和查询速度，适合对质量要求极高的搜索场景。

4. RRF 之外：Learned Fusion 回归

学术界开始重新审视“可学习融合”。例如 Google 的 《RankGPT》 和混合检索领域的多篇论文指出，当有足够标注数据时，用一个小型排序模型（如 LightGBM）融合三路分数，通常优于固定权重的 RRF。但 RRF 依然是冷启动和无监督场景的首选。

5. 开源生态

  • Qdrant：原生支持 Dense + Sparse 混合检索，REST/gRPC 接口友好。
  • Elasticsearch：8.x 版本的 semantic_text 和 text_expansion 让稠密+BM25 混合检索开箱即用。
  • Vespa：在 Yahoo、Spotify 等场景中大规模使用，支持张量检索、BM25、 learned ranking。
  • RAGFlow / Dify：国内流行的 RAG 低代码平台，已经内置混合检索和 Reranker 节点。

今日小结

混合检索不是玄学，而是工程上的“多路召回 + 排名融合”。对 PostgreSQL 工程师来说，它几乎可以完全映射到你已经熟悉的数据库概念：向量索引就是高维 GIN/GiST，BM25 就是 ts_rank_cd，RRF 就是窗口函数排名聚合。

  1. 理解 Dense、Sparse、BM25 三路召回的互补性。
  2. 掌握 RRF 融合算法及其工程实现。
  3. 在 PostgreSQL + pgvector 中跑通 Dense + BM25 混合检索。
  4. 了解 pgvector sparsevec、BGE-M3、ColBERT 等最新技术动向。
