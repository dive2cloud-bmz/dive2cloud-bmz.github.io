Week4 Day28｜转型后实战：30 天搭建 PostgreSQL + pgvector 企业知识库原型

目标：把 26 天学习的 RAG、Agent、Production Engineering 知识沉淀为一个可演示、可上线、可扩展的企业级知识库原型。本篇是 30 天实战的第一天，聚焦架构设计、数据建模与可运行的最小版本。

🚀 核心洞察：企业知识库不是「能搜到」，而是「敢上线」

很多 RAG 教程停在了 similarity_search(query) 能返回结果的那一刻。但企业知识库的真正门槛在于：你敢不敢把它挂到生产环境，让真实用户查询真实文档？

作为从 RDS PostgreSQL 转型而来的工程师，你对这个问题的理解比纯算法背景的人更深。你知道生产系统需要：

  • 多租户隔离，避免 A 部门看到 B 部门的文档；
  • 权限模型，确保同部门内不同角色只能访问授权内容；
  • 可观测性，知道每次检索用了多久、花了多少 token、命中了哪些 chunk；
  • 可回滚的 schema 与数据 pipeline，文档更新后 Embedding 必须同步更新；
  • 成本可控，向量索引不是建完就完，HNSW 的 m/ef_construction 选错了会让存储和查询双崩。

PostgreSQL + pgvector 的价值恰恰在这里：它把「关系型数据库的运维成熟度」和「向量检索的语义能力」合二为一。你不需要为了向量检索额外维护一套 Milvus/Pinecone 集群，就能把知识库建立在已经很熟悉的 RDS 上。

今天的核心洞察是：企业级知识库的竞争点不是 Retrieval 准确率，而是工程可信度。 准确率可以通过调 prompt、换模型、加 rerank 提升；但工程可信度需要在数据建模、权限、监控、回滚这些后端基本功上花功夫。

🧠 核心概念：企业知识库的 5 个设计维度

1. 数据模型：从文档到 Chunk 的三层结构

企业知识库的数据模型通常分为三层：

层级 表名 职责 类比
文档层 documents 存储原始文档元数据（标题、作者、版本、ACL） 关系表主表
片段层 chunks 存储切分后的文本及指向文档的外键 订单明细表
向量层 chunk_embeddings 存储 Embedding 向量，与 chunks 1:1 或 1:N 物化视图/索引表

为什么要把向量和文本分开？三个原因：

  1. 模型可替换：换 Embedding 模型时，只需重建 chunk_embeddings，不影响 chunks 的文本内容；
  2. 维度可变化：不同模型输出维度不同（如 OpenAI text-embedding-3-small 是 1536，bge-large 是 1024），分开存储避免改主表；
  3. 审计友好：可以记录「这个 chunk 是用哪个模型、哪个版本、什么时候生成的」，和 schema 迁移一样可追溯。

2. 多租户隔离：三种策略的权衡

企业知识库几乎都是多租户的。常见策略有三种：

策略 实现方式 优点 缺点 适用场景
数据库级隔离 每个租户一个数据库 最强隔离，可独立备份 运维复杂，成本高 大客户 / 合规要求极高
Schema 级隔离 每个租户一个 schema 隔离较好，共用连接池 跨租户查询复杂 中型 SaaS
行级隔离（RLS） 单表 + tenant_id + PostgreSQL RLS 最简单，扩展性最好 需要仔细设计策略 中小规模 / 快速迭代

对 30 天原型来说，行级隔离 + RLS 是最务实的选择。它让你用同一份 schema、同一套查询逻辑服务多个租户，同时通过策略保证租户不可越权。

4. 索引策略：HNSW vs IVFFlat，别再用默认参数

pgvector 主要支持两种近似最近邻索引：

索引 构建成本 查询速度 召回率 推荐场景
IVFFlat 低 快 依赖 lists 参数 静态数据集、预算有限
HNSW 高 更快 更高，依赖 m/ef_construction 动态更新、追求高召回

HNSW 的核心参数：

  • m：每个节点在图上的最大连接数。越大图越稠密，召回越高，但索引体积和构建时间也越大；
  • ef_construction：构建时搜索的候选集大小。越大构建越慢，但图质量越好；
  • ef_search：查询时搜索的候选集大小，可在会话级别动态设置。

一个经验公式：

  • 数据集 < 100k：m=16, ef_construction=64
  • 数据集 100k-1M：m=24-32, ef_construction=128-256
  • 数据集 > 1M：m=48-64, ef_construction=256-512

5. Ingestion Pipeline：文档更新必须同步 Embedding

企业文档是活的：合同会修订、产品手册会更新、政策会迭代。每次文档更新，必须回答三个问题：

  1. 旧的 chunk 要不要删除？
  2. 新的 chunk 如何重新切分？
  3. 哪些依赖旧知识的检索结果会失效？

🔗 后端桥接：把 AI 概念翻译成 PostgreSQL 语言

作为后端工程师，理解新知识最快的方式是把它映射到熟悉的事物上。

1. Embedding ≈ 行的「语义序列化」

普通的数据库行是结构化的：每一列有明确类型和含义。Embedding 则是把一段文本的语义信息压缩成一个固定长度的浮点数组。你可以把它理解为一种特殊的序列化格式：

就像你不会把所有 JSON 都解析成 100 个列一样，你也不会把 Embedding 拆开存。pgvector 的 vector 类型就是为此设计的。

2. 向量索引 ≈ B-tree 索引的「近亲」

B-tree 适合做精确匹配和范围查询，因为它按值排序。向量索引则适合近似匹配，因为高维空间里没有绝对的「大小」。HNSW 和 IVFFlat 都是近似最近邻索引，它们牺牲一点点精度来换取极大的速度提升，这和 PostgreSQL 的 BRIN 索引「用近似边界框加速大范围扫描」是类似的工程思想。

3. Reranking ≈ SQL 的二次排序

后端开发中，我们经常先用一个粗粒度索引快速缩小范围，再用精确计算二次排序。向量检索 + Rerank 也是同样的道理：

4. Multi-Tenant RLS ≈ 连接池里的动态 schema

RLS 让你在同一条数据库连接上切换租户视角，就像在后端服务里用 SET LOCAL 动态切换上下文一样。它避免了你为每个租户维护独立连接池，是一种非常「后端友好」的隔离方案。

5. Chunk 版本管理 ≈ Schema 迁移

每次换 Embedding 模型或 chunk 策略，都相当于对知识库做了一次「schema 迁移」：

  • 旧 Embedding 可以保留作为 rollback 选项；
  • 新 Embedding 用新的 model_version 标记；
  • 评估通过后再逐步淘汰旧版本。

这种思维和 Alembic / Flyway 管理数据库迁移完全一致。

📰 技术雷达：pgvector 与 RAG 基础设施最新动态

1. pgvector 生态进展

  • pgvector 0.8.x：持续优化 HNSW 索引构建速度，支持 hnsw.ef_search 会话级动态调整，新增更多距离函数实现。
  • pgvectorscale / timescale：Timescale 推出的 pgvector 扩展增强版，针对超大规模向量数据做性能优化，适合已有 TimescaleDB 用户。
  • rds_pgvector：主流云厂商 RDS PostgreSQL 已普遍内置 pgvector，云上部署成本进一步降低。

2. RAG 框架与评估

  • LangChain v0.3：更强调模块化与可观测性，与 LangGraph 的集成更紧密。
  • Ragas v0.2：新增对 Agentic RAG 和多轮对话的评估指标，支持工具调用链路追踪。
  • LlamaIndex 2026 路线：强化 “Agentic RAG” 与 “Knowledge Graph RAG”，把向量检索和图推理结合。

3. 企业级安全与治理

  • LLM Guardrails 标准：越来越多企业要求 RAG 系统具备输出事实校验、敏感信息过滤、SQL/代码生成审计。
  • RAG 审计与合规：金融、医疗行业开始要求记录每次检索的源文档、chunk 范围、模型版本，以满足可解释性要求。

4. 值得跟进的 GitHub 项目

  • pgvector/pgvector：官方扩展，必读。
  • langchain-ai/langgraph：状态机 + 持久化，适合把 RAG 升级为 Agent。
  • explodinggradients/ragas：RAG 评估事实标准之一。
  • microsoft/promptflow：微软的 LLM 应用开发流水线工具，适合企业落地。
