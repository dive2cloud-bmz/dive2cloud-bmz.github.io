从 PDF 到向量库：文档解析与 Chunk 策略的工程师实战

🚀 核心洞察：RAG 不是从 Embedding 开始，而是从“把文档读对”开始

很多后端工程师刚接触 RAG 时，会下意识地把重心放在向量数据库、Embedding 模型、重排序这些“看起来更像 AI”的环节。但真正落地过企业知识库的人都知道：检索质量的上限，往往被最前端的文档解析和分块环节锁死。一份扫描版 PDF 被读成乱码、一张表格被拆成碎片、一段跨页的段落被拦腰截断，后面无论用多么先进的 reranker，都很难把答案救回来。

作为 PostgreSQL DBA/后端工程师，你其实对这一页并不陌生。我们在数据库里常说“garbage in, garbage out”——数据入库前的 ETL 质量，决定了后续所有查询和分析的可信度。RAG 的文档解析与 Chunk 策略，本质上就是 AI 时代的 ETL：把各种异构、非结构化、版式复杂的“原材料”，清洗、拆分、标注成模型能够理解并可靠检索的“结构化片段”。

今天这篇文章，我们就把视角沉到 RAG 流水线的最底层，聊聊如何把 PDF、Word、扫描件、网页、幻灯片等任意格式文档，稳定、可复现、可评估地转化为向量库中的可检索片段。

🧠 核心概念：文档解析与 Chunk 的完整链路

1. 为什么解析是 RAG 的第一道防线

RAG 的完整链路可以抽象为：

如果 B 阶段输出的文本已经丢失段落结构、表格关系、列表层级，那么 C 阶段的 chunk 就会像被随机切分的磁带；D 阶段的 Embedding 再先进，也只能在语义碎片中找近似。企业中常见的失败案例包括：

  • 扫描件未做 OCR：PDF 里看起来有字，但实际是图片，直接解析得到空字符串或乱码。
  • 表格被压平：原本二维的表格被解析成一串没有列关系的纯文本，导致“第 3 行第 2 列的值”无法被准确定位。
  • 页眉页脚混入正文：每页都重复的“公司名称 ©2025”被当成正文分块，污染检索。
  • 跨页段落被截断：一段完整的技术说明跨了两页，按页切分后前后语义断裂。
  • 多栏布局顺序错乱：学术论文的两栏内容被按列而不是按阅读顺序拼接。

这些问题的共同点是：解析不是简单的“把文字抠出来”，而是要把文档还原成带有结构和语义的中间表示。

2. 文档解析全景：格式、工具与陷阱

企业里的文档通常是“八国联军”：Office 文档、扫描 PDF、工程图纸、网页、Markdown、PPT、邮件、图片。不同格式需要不同的解析策略。下面这张表总结了常见格式和对应的处理要点。

文档格式 常见挑战 推荐策略 代表工具
文本型 PDF 字体编码异常、多栏布局、页眉页脚 基于布局的解析，保留阅读顺序 PyMuPDF、pdfplumber、Unstructured
扫描型 PDF / 图片 无文本层，需 OCR OCR + 版面分析，识别表格和段落 Tesseract、PaddleOCR、Surya、marker
Word / DOCX 样式、目录、批注、修订 按 XML 结构解析，保留标题层级 python-docx、Unstructured
HTML / Markdown 标签噪音、脚本、导航栏 清洗 HTML，按 DOM 语义分块 BeautifulSoup、trafilatura、 readability-lxml
PPT / PPTX 每页独立、图形化、备注 按幻灯片+演讲者备注组织 python-pptx、Unstructured
Excel / CSV 二维表、多 Sheet、公式 保持表头+行关系，生成结构化文本 pandas、openpyxl
邮件 / EML 嵌套引用、附件、HTML 正文 提取正文，附件递归解析 email-parser、Unstructured

工具层面，近几年出现了专门面向 LLM 的解析器，它们不再只返回纯文本，而是返回带有坐标、类型、层级关系的“文档对象模型”（Document Object Model, DOM）。例如：

  • Unstructured：把文档拆成 Title、NarrativeText、Table、ListItem 等语义元素，支持 partition 系列函数。
  • Marker：主打“LLM-ready”的 PDF 解析，对学术论文和扫描件效果好，输出 Markdown。
  • Docling（IBM 开源）：提供统一的文档解析 API，支持 PDF、DOCX、PPTX、HTML 等，输出包含版面信息的 JSON。
  • LlamaParse：闭源服务，对复杂表格、多栏、扫描件支持较强，与 LlamaIndex 生态集成好。

选择解析器时，不要只看 demo 效果，要关注四个工程指标：

  1. 召回率（Recall）：原始文档中有多少关键信息被成功提取。
  2. 精确率（Precision）：提取的内容中有多少是真实正文，而非页眉、页脚、水印。
  3. 结构保持度：标题、段落、表格、列表的层级关系是否保留。
  4. 吞吐量与成本：每页解析耗时、是否需要 GPU、是否按页收费。

3. Chunk 的本质：在“语义完整”与“检索粒度”之间找平衡

解析之后，我们得到的是一篇很长的连续文本。直接把整篇文档塞进 Embedding 模型，既会超出上下文窗口，也会降低检索精度。Chunk 的核心目标是把长文档切成若干语义独立、信息密度适中、便于检索的小块。

但这并不是一个“平均切”的问题。Chunk 过大，会稀释主题，导致检索时把不相关的内容也带进来；Chunk 过小，会丢失上下文，让模型看到一个孤立的名词而不知道它属于哪个产品、哪个版本。常见的 Chunk 策略有：

策略 原理 优点 缺点 适用场景
固定字符数 每 N 个字符一切 简单、可预测、易于实现 容易切断句子，丢失语义 对质量要求不高、快速原型
递归字符切分 优先按段落、句子切，再按字符兜底 保持自然语言边界 对代码、表格边界处理一般 通用文档、知识库
语义切分 用 Embedding 相似度检测主题转折 chunk 边界符合语义 计算成本高，需要额外模型 长文档、法律/医学文本
Agentic / 结构切分 按标题、章节、表格等文档结构切 保留完整上下文和层级 依赖解析器的结构输出质量 手册、论文、规范文档
混合策略 对不同类型元素用不同切分规则 最贴合实际文档结构 实现复杂，需要维护规则 企业级复杂知识库

在工程实践中，递归字符切分 + 结构边界保护通常是性价比最高的起点。LangChain 的 RecursiveCharacterTextSplitter 就是这一思路的代表：它按 ["\n\n", "\n", ". ", " ", ""] 的优先级递归切分，优先保证段落和句子不被破坏。

4. 元数据与上下文保持：让 chunk 记得自己来自哪里

切分之后，每个 chunk 必须携带足够的元数据，否则检索出来就是一段没有上下文的“孤儿文本”。这些元数据至少应包括：

  • 来源标识：文档 ID、文件路径、URL、版本号。
  • 位置信息：页码、章节标题、段落序号、父 chunk ID。
  • 类型标签：正文、表格、代码、标题、列表项。
  • 时间戳：文档创建时间、更新时间，用于处理过期知识。
  • 访问控制：部门、角色、密级，用于多租户场景下的权限过滤。

在向量库中，这些元数据通常以 JSONB 或普通字段存储，检索时可以先做元数据过滤，再做向量相似度搜索。例如 pgvector 支持：

5. 表格、图片与版式：RAG 里的“硬骨头”

表格和图片是文档解析中代价最高、收益最大的两类元素。

表格有两种主流处理方式：

  1. 文本化：把表格转成 Markdown 表格或 CSV-like 文本，再按行或按单元格切分。优点是简单，缺点是跨行语义和大单元格容易断裂。
  2. 结构化存储：把表格解析成 JSON / DataFrame，单独建表或作为 chunk 的附属字段。检索时可以做 SQL 式的精确查询，而不是依赖向量相似度。

对于关键业务表格（如价格表、配置表、SLA 表），推荐采用第二种：把表格行作为独立记录存入关系表，同时把表格摘要作为 chunk 存入向量库。这样既能回答“某个 SKU 的价格是多少”这类精确问题，也能回答“这款产品的定价策略是什么”这类语义问题。

图片的处理通常需要多模态能力：

  • 如果图片是图表、流程图、架构图，可以用 VLM（如 GPT-4V、Qwen-VL）生成文字描述，再把描述文本作为 chunk。
  • 如果是扫描件中的文字图，可以用 OCR 提取后并入正文。
  • 如果图片只是装饰性元素，可以在解析阶段识别并丢弃，避免污染知识库。

6. 评估解析与 Chunk 质量：没有度量就无法优化

解析和 Chunk 策略不能“凭感觉”定稿，必须建立评估流水线。建议从三个维度设指标：

解析质量指标

  • 字符召回率：人工标注关键片段，看解析器是否完整提取。
  • 结构召回率：标题、表格、列表是否被正确识别为对应类型。
  • 噪音率：页眉、页脚、水印、页码被误判为正文的占比。

Chunk 质量指标

  • 边界正确率：chunk 是否在没有切断句子/段落的情况下结束。
  • 主题一致性：单个 chunk 内是否围绕单一主题（可用句子间 Embedding 相似度衡量）。
  • 上下文覆盖率：针对一组问答对，判断答案是否落在某个 chunk 内（Recall@K）。

端到端指标

  • 检索命中率：正确答案所在 chunk 是否出现在 Top-K 检索结果中。
  • 答案忠实度：LLM 生成的答案是否能在原始 chunk 中找到依据。

建议先从端到端指标入手，发现 bad case 后再反向定位是解析问题还是 Chunk 问题。这种“从结果反推”的调试思路，和后端排查线上 Bug 非常像：先看现象，再分层定位。

🔗 后端桥接：用 PostgreSQL 的直觉理解文档解析与 Chunk

作为 PostgreSQL 后端工程师，你已经在日常工作中大量接触过文档解析和 Chunk 所要解决的问题，只是没有把它们对应起来。下面是几组直观的类比。

原始文档 ≈ 一条带 TOAST 的大行

PostgreSQL 中，超过 2KB 的字段会被压缩后存入 TOAST 表，主表只保留指针。PDF、Word 文档就像这些 TOAST 行：它们体积大、结构复杂、不能直接用于检索。解析的第一步，就是把 TOAST 里的二进制大对象还原成可用的结构化数据。

文档解析器 ≈ COPY / FDW

当我们把外部数据导入 PostgreSQL 时，会用 COPY 做批量导入，或用 postgres_fdw 做外部表映射。文档解析器扮演的正是这个角色：它把异构的外部文档（PDF、Word、网页）转换成统一的内部表示（文本 + 元数据 + 结构）。解析质量差，就像 CSV 的列错位，后续所有查询都会出错。

Chunk ≈ 规范化后的行

数据库设计强调规范化（normalization）：把大宽表拆成多张关联的小表，减少冗余、提高查询效率。Chunk 就是把一篇“大宽文档”规范化为多个“小语义行”。每个 chunk 只围绕一个主题，便于 Embedding 和检索。

元数据 ≈ JSONB 列

pgvector 的 chunk 表通常会有 metadata jsonb 字段，存储文档 ID、页码、章节、类型等。这和你在 PostgreSQL 中用 JSONB 存储半结构化日志、配置、审计字段完全一致。检索时先用 JSONB 上的 GIN 索引过滤，再用向量索引排序，是典型混合索引策略。

Embedding ≈ 函数式索引 / 表达式索引

Embedding 向量的本质，是把“content”字段通过一个函数（Embedding 模型）映射成一个高维向量，然后在这个向量上建近似索引（ivfflat/hnsw）。这和 PostgreSQL 的表达式索引非常像：CREATE INDEX ON table USING btree (lower(email))。区别只在于索引类型和距离函数。

Chunk 重叠 ≈ 填充因子（Fillfactor）与冗余

为了让相邻 chunk 保留上下文，我们经常让 chunk 之间有一定重叠（overlap）。这类似于数据库表的 fillfactor：留下一些冗余空间，换取后续更新或查询时的局部性。Overlap 不是免费的，它会增加存储和 Embedding 成本，需要像调 fillfactor 一样按场景权衡。

父 Chunk ID ≈ 外键

当我们把大 chunk 再细分为小 chunk（例如按段落切分）时，通常会让小 chunk 保留 parent_chunk_id。这就像关系表里的外键：子记录可以通过外键快速找到父记录的完整上下文，避免孤立信息。

📰 技术雷达

  • Docling（IBM，2024 开源）：一个统一的文档解析框架，支持 PDF、DOCX、PPTX、HTML、图片等，输出包含版面结构的 JSON 和 Markdown。对于希望自建解析能力、避免依赖闭源 API 的团队，Docling 是当前最值得跟进的选项之一。
  • Marker（Vik Paruchuri）：专注于学术 PDF 和扫描件，能把复杂的双栏论文转成干净的 Markdown，对公式、表格、参考文献的处理优于传统工具。
  • Surya：多语言 OCR 和版面分析工具，支持 90+ 种语言，对中文、日文、韩文等 CJK 文档效果较好，可作为扫描件解析链路的第一环。
  • LlamaParse（LlamaIndex）：闭源但效果领先，尤其擅长复杂表格和多栏文档。适合快速验证，长期大规模使用需评估成本。
  • Unstructured：生态最成熟，提供 partition、chunking、staging 等完整工具链，支持本地和云端 API，是企业构建解析流水线的稳妥选择。
  • ChunkViz / Chunkviz 等可视化工具：帮助开发者直观查看 chunk 边界和重叠情况，快速调优 chunk_size 和 overlap。
  • 最新论文动向：2024-2025 年学术界开始关注“Document Understanding for RAG”，即从版面、表格、图表、多模态角度提升 RAG 的召回和忠实度。代表性方向包括视觉文档编码器（如 ColPali）、多模态检索（MMRAG）和结构化 chunk 表示（如 Markdown/JSON hybrid）。

今日小结：文档解析和 Chunk 策略是 RAG 的“地基工程”。它不像 Embedding 模型那样有明确的准确率数字，却决定了整个系统的上限。作为 PostgreSQL 后端工程师，你可以把这套流程理解为 AI 时代的 ETL + 规范化 + 索引构建。下一篇我们将进入“Embedding 模型选型与微调”，看看如何把已经切分好的 chunk 更高效地映射到向量空间。
