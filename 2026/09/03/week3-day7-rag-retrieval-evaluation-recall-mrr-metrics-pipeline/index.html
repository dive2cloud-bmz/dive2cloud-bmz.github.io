RAG检索评估实战：从Recall到MRR的指标体系与自动化评测流水线

RAG 能跑起来靠向量库和 Prompt，能被信任靠可量化的检索指标、可复现的评测数据，以及驱动迭代的 Bad Case 闭环。

🚀 核心洞察（2 min）

从 PostgreSQL 后端转向 AI 应用工程，你最熟悉的场景之一是给数据库做基准测试：pgbench 测 QPS、EXPLAIN ANALYZE 看执行计划、P99 衡量稳定性。RAG 检索评估回答的是同一个问题——“这个系统在生产负载下表现如何？”

  • 检索质量是 RAG 的天花板。LLM 再强，错误文档进入上下文也会被误导。
  • 指标必须服务于决策。Recall@K、MRR、NDCG、Hit Rate 各有场景，选择取决于优化目标是覆盖、首位准确率还是整体排序。
  • 评估必须自动化、可回归、可沉淀。写进 CI、生成趋势图、沉淀到可观测平台，才能让每次索引调整都有数据支撑。

🧠 核心概念（10 min）

1. 检索评估指标

设查询 q 的黄金文档集合为 G，检索器返回 Top-K 列表 R_K。

Recall@K：|G ∩ R_K| / |G|。衡量黄金文档中被召回的比例，适合必须覆盖所有证据的场景。缺陷是只关心存在性，不惩罚排序差。

MRR：首个相关文档排名的倒数均值。RAG 通常只取 Top-1/Top-3，MRR 比 Recall 更贴近真实体验。

NDCG@K：同时考虑文档相关性和排序位置，适合有强弱相关之分的场景。

Hit Rate@K：Top-K 中至少命中一个相关文档的查询比例，适合向业务方汇报。

实践组合：Recall@K 保覆盖，MRR 保首位，NDCG 保整体排序。

2. 评测数据集构建

正例对收集：最理想来自真实用户查询。无流量时可用 LLM 反向生成问题，或人工标注，关键是 query distribution 贴近真实用户。

困难负采样：用通用 Embedding 召回 Top-N 去掉正例，或用 BM25 取高匹配但无答案的文档，或让 LLM 改写“看起来相关但答案不同”的段落，避免指标虚高。

数据泄漏防护：严格按文档划分训练/验证/测试；评测只用训练未见过的问题和文档；记录数据版本。

3. 向量检索 + 重排序联合评估

RAG pipeline 分检索、重排、生成三阶段，推荐分阶段指标 + 端到端指标。

  • 检索器：Recall@K、MRR@K，评估向量索引和 Embedding。
  • 重排序器：固定检索候选，看 NDCG@K、MRR@K 提升。注意重排窗口，只重排前 20 个时 Recall@100 与它无关。
  • 生成器：用 RAGAS 的 faithfulness、answer_relevance、context_relevance 和人工评估。

贡献度分解：检索器收益看重排前指标；重排器收益看固定检索后重排前后差；生成器收益看上下文不变时端到端质量提升。就像后端优化不能只看总延迟，而要看数据库、RPC、序列化各占多少。

4. Bad Case 分析

常见归因：

  • Embedding 失败：查询和答案在向量空间中距离远。
  • 索引失败：Chunk 切分不合适，关键信息被截断或分散。
  • 语义冲突：查询有歧义，系统只召回一种语境。
  • 数据缺失：答案不在知识库中。

每次评测除平均分，还应输出每个查询的 Top-K 结果，看正确答案排第几、前面是什么文档、共同特征是什么。对应对策：微调模型、调整 Chunk、引入查询澄清、补充文档。这对应后端的慢查询优化：先找慢 SQL，再分析执行计划，最后决定加索引或改写查询。

🔗 后端桥接（3 min）

PostgreSQL 维度 向量检索对应项
QPS / TPS 每秒检索查询数
P99 延迟 向量检索 + 重排序总延迟
执行计划 索引选择（IVF / HNSW / Flat）
命中率 Recall@K
慢查询日志 高延迟 + 低 Recall 的查询样本
容量规划 索引内存、向量维度、文档增长曲线

给 pgvector 做压测可用 pgbench 自定义脚本或 Python 并发。HNSW 的 ef_search 较小时会牺牲召回换速度，这就是 Recall-Latency Trade-off。

可用 pgvector + SQL 聚合搭建轻量仪表盘：建表记录 (run_id, retriever, reranker, k, recall, mrr, ndcg, latency_ms)，跑完写入再用 GROUP BY 做趋势分析。可把 recall@5 和 mrr@5 推送到 Prometheus/Grafana，与生产监控联动。

🛠️ 微实战（5 min）

在 RAG Demo 中加入检索评估脚本，构造 50 组 query-doc 对，计算 Recall@5 与 MRR，并输出 Top-5 错误样本供人工复核。

步骤 1：准备数据集
整理 50 组 (query, relevant_doc_id) 正例对，并为每个查询准备 5～10 个困难负样本。确保评测问题不在训练语料中。以 JSONL 保存，字段包括 query_id、query、positive_ids、negative_ids。

步骤 2：实现指标函数

步骤 3：跑通主循环

步骤 4：人工复核
打开 bad_cases_top10.json，看正确答案排第几、前面是什么文档，按 Embedding 失败、Chunk 问题、查询歧义、数据缺失归类，产出至少一个可落地优化动作。

步骤 5：接入 CI
把脚本放入 scripts/eval_retrieval.py，修改 Embedding、索引或重排逻辑后自动运行，设定阈值如 Recall@5 >= 0.75、MRR@5 >= 0.60，不满足则失败。

📰 技术雷达

RAGAS：端到端 RAG 评估事实标准，提供 faithfulness、answer_relevancy、context_relevancy、context_recall，适合快速验证，但调用 LLM 成本不低。

Arize AI 与 LangSmith：把追踪、评估、监控整合一体。LangSmith 适合 LangChain 用户，Arize 更强调模型可观测性与实验对比。

稀疏-密集混合检索：纯向量在缩写、专有名词、ID 查询上容易失效，BM25 更稳定。主流方案是向量负责语义泛化，BM25 负责精确匹配，再融合。评估时要分别看两路贡献。
