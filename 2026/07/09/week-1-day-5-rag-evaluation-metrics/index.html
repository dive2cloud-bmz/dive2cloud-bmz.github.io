从Recall到RAGAS：RAG系统评估全景

🚀 核心洞察（2分钟）

如果你维护过 PostgreSQL 或任何后端存储系统，应该对“没有指标就没有优化方向”这句话深有体会。我们会盯着 EXPLAIN ANALYZE 看索引是否命中、顺序扫描是否过多、缓存命中率是否健康。进入 RAG 时代，这套思维同样适用，但评估对象从“查询计划”变成了“检索 + 生成”的端到端链路。

很多团队搭建 RAG 原型时，第一步往往是选一个向量数据库、调一个 Embedding 模型，然后肉眼挑几个 query 看答案“像不像”。这种方式能跑通 demo，却无法支撑生产迭代。RAG 的真实瓶颈常常不在“能不能召回”，而在“检索到了但生成没用”“答案看着对但其实 hallucination”“上下文里明明有答案却被模型忽略”。

今天的核心洞察可以一句话概括：RAG 评估必须从“向量相似度”这种静态信号，升级到“答案是否忠实、是否相关、是否利用了上下文”这种端到端信号。 对 PG/Backend 工程师来说，这就像从只看索引扫描次数，升级到看事务最终是否满足业务一致性。

🧠 核心概念（10分钟）

1. 检索指标：Recall@K、MRR、NDCG

检索是 RAG 的第一道关卡。无论后面的 LLM 多强大，如果关键上下文没进候选集，答案就不可能好。检索评估通常假设我们有一个“相关文档集合”作为 ground truth，然后看系统召回的结果与它有多接近。

Recall@K

Recall@K 衡量的是：在排名前 K 的结果里，系统找回了多少真正相关的文档。公式很直接：

它适合关心“不漏”的场景，比如医疗、法律、合规问答。缺点是它只看有没有，不看排序。一个把最相关文档排在第 K 位的系统，和一个把最相关文档排在第 1 位的系统，Recall@K 可能完全一样。

MRR（Mean Reciprocal Rank）

MRR 关注的是“第一个相关文档出现的位置”。它的计算方式是：对每个查询，取第一个相关文档排名的倒数，然后求平均。

MRR 对排名敏感，适合对话式检索或单答案场景。比如用户问“怎么给 PostgreSQL 加字段”，第一个结果就是正确文档的体验，远好于第五个结果才出现。

NDCG（Normalized Discounted Cumulative Gain）

NDCG 是更精细的指标。它允许你给不同文档打上“相关度分数”（比如 0、1、2、3），并且越靠前的位置权重越高。公式分两步：

2. 生成指标：Faithfulness、Answer Relevance、Context Precision

检索指标只回答了“有没有找对材料”，生成指标则要回答“模型有没有用好材料”。RAG 里最常见的三个生成维度是：忠实性（Faithfulness）、答案相关性（Answer Relevance） 和 上下文精确率（Context Precision）。

Faithfulness（忠实性）

Faithfulness 衡量生成答案是否被检索到的上下文所支持，也就是有没有“幻觉”。基本思路是把答案拆成若干声明（claims），然后检查每个声明是否能从上下文中推断出来。

比如：

  • 上下文：PostgreSQL 14 引入了 multirange 类型。
  • 答案：PostgreSQL 14 支持 multirange 类型，且该特性在 PostgreSQL 15 中被移除。
  • 分析：第一句被支持，第二句是幻觉。Faithfulness = 0.5。

生产环境里，这个判断通常由另一个 LLM 来完成，也就是所谓的 LLM-as-a-Judge。

Answer Relevance（答案相关性）

Answer Relevance 衡量答案是否回应了用户的问题。一个忠实但答非所问的答案， relevance 会很低。常见做法是：把答案改写成多个潜在问题，再看这些问题与原问题的语义相似度。

这对客服、问答系统尤其重要。用户问“怎么退款”，系统回答“我们的退款政策很完善”——虽然没幻觉，但 relevance 不高。

Context Precision（上下文精确率）

Context Precision 衡量的是：检索到的上下文里，有多少是真正相关的。它和检索的 Precision 很像，但站在生成端看。

如果模型拿到 10 个 chunk，只有 3 个相关，剩下的都是噪声，那么即使 LLM 很强，也可能被干扰。这个指标提醒我们：不要只调 top_k，还要关注 top_k 的质量。

下面这张表对比了三个生成指标：

指标 评估对象 高分含义 常见陷阱
Faithfulness 答案 vs 上下文 答案没有幻觉 上下文本身错误会导致“伪忠实”
Answer Relevance 答案 vs 问题 回答了用户想问的 容易给“兜圈子”的答案打高分
Context Precision 上下文 vs 问题 噪声少 需要人工或模型标注相关性

3. 自动化框架：RAGAS 与 ARES

手动计算上述指标在大规模数据集上不现实，因此社区出现了几个自动化评估框架。这里重点介绍 RAGAS 和 ARES。

RAGAS

RAGAS（Retrieval-Augmented Generation Assessment）是一个专门面向 RAG 的开源评估框架。它不需要人工标注答案，而是利用 LLM 来自动打分。核心指标包括：

  • faithfulness：答案是否忠实于上下文
  • answer_relevancy：答案是否与问题相关
  • context_precision：上下文是否精确
  • context_recall：上下文是否覆盖了 ground truth 答案
  • context_entity_recall：实体级别的召回
  • answer_correctness：与标准答案的对比

ARES

ARES（Automatic RAG Evaluation System）是另一种思路。它通过少量人工标注数据训练一个轻量级评分模型，然后用这个模型批量打分。相比 RAGAS 每次调用大模型，ARES 更适合高频评估场景。

ARES 的核心步骤：

  1. 准备一个“黄金数据集”，包含 query、上下文和人工标注的相关性/忠实性标签。
  2. 用这份数据微调一个 BERT 或类似的小模型，让它学会打分。
  3. 在评估新系统时，直接用这个小模型输出分数。

这就像后端系统里：先用小样本日志训练一个异常检测模型，再把它部署到线上实时打分。

4. 人工评估与 A/B 测试设计要点

自动化指标再好，也无法完全替代人工判断。原因有三：

  1. LLM-as-a-Judge 本身可能带有偏见，尤其是当评判模型和生成模型来自同一家厂商时。
  2. 某些业务维度难以量化，比如语气是否友好、格式是否符合规范。
  3. 自动化指标只能告诉你“分数变高”，但不知道用户实际体验是否变好。

因此，生产环境里通常采用“自动化指标 + 人工抽检 + A/B 测试”的三层评估体系。

人工评估设计要点

  • 制定清晰的评估标准：把“好答案”拆成可操作的维度，比如准确性、完整性、简洁性、安全性。
  • 多人标注 + 一致性校验：至少两名标注员独立打分，计算 Cohen’s Kappa 或 Fleiss’ Kappa。
  • 盲评：标注员不知道答案来自哪个系统版本，避免先入为主。
  • 抽样策略：不要只抽高分或低分样本，按分数分层抽样，才能发现系统性问题。

A/B 测试设计要点

  • 随机分桶：用户请求按 user_id 或 session_id 哈希到不同版本。
  • 核心指标：业务指标优先，比如用户满意度、转化率、停留时长；技术指标辅助，比如平均延迟、token 消耗。
  • 样本量计算：提前用统计公式估算需要多少样本才能达到显著性，避免过早下结论。
  • 防止数据泄漏：同一用户的多次请求应始终落在同一桶内，否则体验会不稳定。

🔗 后端桥接（3分钟）

把 RAG 评估映射回你熟悉的 PG/Backend 世界，会有三条清晰的类比。

第一，检索指标就像 SQL 执行计划指标。 Recall@K 类似于“索引扫描返回了多少目标行”，MRR 类似于“第一个命中行出现在结果集的哪个位置”，NDCG 则像带了权重排序的 ORDER BY 效果评估。你调 Embedding 模型和重排策略，就像调索引类型和查询计划；最终要看的是业务查询的端到端耗时和命中率。

第二，Faithfulness 类似于事务一致性检查。 在后端，你会用外键、约束、幂等设计来保证“写进去的数据不会自相矛盾”。在 RAG 里，Faithfulness 就是保证“说出来的话有出处、不自相矛盾”。区别在于，数据库约束是确定性的，而 Faithfulness 需要靠 LLM 或人工来近似判断。

第三，RAGAS/ARES 类似于可观测性平台。 就像后端系统会用 Prometheus、Grafana、链路追踪来监控延迟和错误率，RAG 系统也需要一套评估框架来持续监控“检索质量”和“生成质量”。LangSmith、Phoenix、Langfuse 这些工具，本质上就是 RAG 时代的 APM。

📰 技术雷达

RAG 评估领域正在快速演进，以下几个方向值得持续关注：

LLM-as-a-Judge 的标准化：越来越多团队意识到，用 LLM 给 LLM 打分虽然方便，但存在位置偏见、 verbosity 偏见和模型同质化风险。2026 年，社区正在探索更稳定的评判协议，比如多模型投票、对抗性提示校准、以及针对特定领域的评判微调。

多跳检索评估：简单 RAG 只查一次向量库，但复杂问题需要多次检索并组合信息。Multi-hop QA 的评估不仅要答案对，还要检索路径对。HotpotQA、2WikiMultiHopQA 等数据集正在成为标准 benchmark。

离线/在线指标联动：离线指标高分不等于线上体验好。新一代可观测平台（如 LangSmith、Phoenix、Langfuse、OpenTelemetry for LLM）正在把离线评估、在线日志、用户反馈打通，形成完整的反馈闭环。

端到端 RAG 优化器：除了评估，业界也在探索自动优化 RAG 配置的工具，比如自动选择 chunk 大小、top_k、重排策略，甚至自动改写查询。评估指标在这里充当目标函数，驱动整个系统自我迭代。

小结

RAG 评估不是一件“做完一次就结束”的事，而是贯穿系统生命周期的持续工作。从 Recall@K 到 RAGAS，从自动化指标到人工 A/B 测试，每一层都在回答一个不同的问题：检索准不准、生成真不真、用户满不满意。对 PG/Backend 工程师来说，最自然的迁移是把评估当作数据库监控来做：先定义指标，再建表收集，最后基于数据迭代。只有这样，RAG 系统才能从“能跑”走向“可靠”。
