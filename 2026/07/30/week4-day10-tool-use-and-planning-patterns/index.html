Agent 的规划与工具调用（01）：从 Function Calling 到工具编排

🚀 核心洞察：工具让 Agent 长出双手，规划让它知道先伸哪只手

前四个星期，我们从 RAG 的检索与评估，走到 Agent 的记忆系统。今天开启一个新系列：Agent 的规划与工具调用（Planning & Tool Use）。

为什么把这两个话题放在一起？因为单独看它们都不够完整：

  • Function Calling / Tool Use 解决的是「Agent 能做什么」——让它可以查天气、调 API、跑 SQL、发邮件。
  • Planning 解决的是「Agent 该按什么顺序做」——面对一个复杂目标，它要先查什么、再算什么、最后做什么决策。

作为 PostgreSQL 后端工程师，你每天打交道的就是这两件事的合体：查询优化器规划执行路径，执行器调用索引扫描、JOIN、排序等「工具」来完成 SQL。一个只会调用索引但不懂查询计划的执行器，和一个只会画执行计划但调不了任何算子的优化器，都跑不出一条完整 SQL。Agent 也一样。

今天的核心直觉是：Tool Use 给 Agent 提供了原子能力，Planning 把这些能力编排成可完成复杂目标的流程。真正有用的 Agent，不是工具多，而是知道在正确的时间调用正确的工具，并在执行中持续修正计划。

🧠 核心概念：规划与工具调用的全景地图

1. Tool Use 的本质：把 LLM 从文本生成器变成系统调用入口

Function Calling（OpenAI 术语）或 Tool Use（Anthropic/Google 术语）的核心机制是：LLM 输出一段结构化文本（通常是 JSON），说明它想调用哪个外部函数、传什么参数。外部系统执行后，把结果再喂回 LLM，由 LLM 决定下一步。

这个过程看起来简单，但已经让 LLM 从「只读知识库」变成「可操作外部系统的入口」。它和纯 RAG 的最大区别在于：RAG 让模型读到信息，Tool Use 让模型改变外部状态。

2. 规划（Planning）的层次：从单步决策到全局战略

不是所有任务都需要规划。查个天气不需要，但规划一次跨城出差就需要。我们可以把规划能力分成三个层次：

层次 代表方法 核心思想 适合场景
无显式规划 单步 Function Call、ReAct 每步根据当前状态决定下一步 工具少、链路短、反馈密集
一次性规划 Chain-of-Thought、Plan-and-Solve、LLM+P 先输出完整计划，再执行 步骤可预先拆解、目标明确
搜索式规划 Tree of Thoughts (ToT)、LATS、RAP 探索多条计划路径，评估后选优 高价值、复杂、需要试错
动态重规划 Plan-and-Execute + Reflection 先规划，执行中根据反馈调整 长周期、环境动态变化

我们在 Week 2 Day 2 详细聊过 ReAct，Week 2 Day 3 拆过 Plan-and-Execute + Reflection。今天把它们放到更大的坐标系里，重点看 Tool Use 如何与不同规划策略配合。

3. 工具调用的关键设计决策

把 Tool Use 做到生产可用，至少需要回答六个问题：

3.1 工具描述怎么写？

LLM 只能看到你给它的 description 和 parameters schema。描述写得好不好，直接决定它会不会调错工具。一个好的工具描述应该包含：

  • 做什么：一句话说清楚功能。
  • 什么时候用：明确触发条件，减少误调用。
  • 参数语义：每个字段代表什么、单位、取值范围。
  • 返回什么：让 LLM 知道如何利用返回结果。

3.2 顺序调用还是并行调用？

现代 LLM（GPT-4o、Claude 3.5 Sonnet、Gemini 1.5）都支持并行工具调用。如果多个工具之间没有依赖，并行可以显著降低总延迟。

判断依赖的经验法则：

  • 需要前一步结果作为下一步输入 → 顺序。
  • 彼此独立（查多个城市的天气、查多个表的结构） → 并行。
  • 部分依赖（先查航班列表，再对每条航班查价格） → 先并行查列表，再批量查详情。

3.3 工具结果怎么回传给 LLM？

常见做法是把工具返回直接塞进消息历史。但生产里要注意：

  • 截断：API 返回可能很大，要控制长度。
  • 格式化：统一成 LLM 易读的格式（Markdown 表格、JSON）。
  • 错误包装：HTTP 500 要转成 LLM 能理解的文本，而不是抛异常中断。
  • 来源标注：特别是 RAG + Tool 混合场景，要标明信息来自工具还是知识库。

3.4 如何防止工具滥用？

LLM 可能：

  • 反复调用同一个工具（循环调用）。
  • 调用不该调用的写操作（删除数据）。
  • 编造参数（hallucinated arguments）。

防护手段：

风险 防护手段
循环调用 设置单轮最大工具调用次数、去重检测
越权写操作 工具白名单、权限 ACL、人工确认节点
参数幻觉 JSON Schema 校验、参数范围检查、枚举限制
超时挂死 工具调用超时、熔断、降级

这些我们在 Week 3 Day 2（输出安全与工具白名单）和 Week 3 Day 6（Guardrails）已经系统讨论过，今天把它们和规划层结合起来看。

3.5 规划失败时怎么办？

再精妙的计划也可能失败。规划层的错误处理通常分三级：

  1. 工具级重试：单个工具调用失败（网络抖动），按指数退避重试。
  2. 步骤级重规划：某一步结果不符合预期，替换为替代步骤。
  3. 全局级回退：整个计划走不通，向用户说明已完成的步骤和卡住的点，请求澄清。

4. 三种典型架构模式

基于 Planning + Tool Use 的交互方式，可以把 Agent 架构抽象为三种模式：

  • 模式 A（ReAct）：灵活、延迟低、适合工具密集短链路。缺点是长程任务容易短视。
  • 模式 B（Plan-and-Execute）：稳定、可审计、适合可预先拆解的任务。缺点是计划僵化，意外处理能力弱。
  • 模式 C（ToT / LATS）：能力强、适合高价值复杂决策。缺点是 Token 消耗高、延迟大。

生产系统往往不是三选一，而是分层使用：外层用 Plan-and-Execute 把控全局，内层用 ReAct 执行每个子任务，关键决策点用 ToT 做搜索。

🔗 后端桥接：PG 查询优化器就是最经典的 Planner + Tool Executor

作为后端工程师，你对 Planning + Tool Use 并不陌生。PostgreSQL 的执行流程本身就是一个鲜活的例子：

对应到 Agent：

Agent 概念 PostgreSQL 类比 说明
Planner 查询优化器 根据目标（SQL）和统计信息生成执行计划
Tool 扫描/Join/排序算子 完成计划中的原子操作
Tool Description 算子成本估算 + 能力说明 优化器要知道哪种算子适合哪种条件
Tool Result 算子返回的元组流 上层算子消费下层结果
并行工具调用 并行顺序扫描 / 并行哈希 Join 无依赖的子任务同时执行
动态重规划 运行时重新选择计划 / 自适应查询优化 统计信息不准时调整执行策略
工具超时/熔断 statement_timeout / 资源队列 防止单个查询拖垮系统

另一个贴切的类比是微服务编排：

  • Planner 就像 BFF（Backend for Frontend）或编排服务，根据用户请求决定调用哪些下游服务。
  • Tool 就是各个微服务：用户服务、订单服务、库存服务、支付服务。
  • 并行工具调用 就像并发发起多个无依赖的 RPC。
  • Tool Schema 就像 OpenAPI/Swagger 定义，编排层按契约传参。
  • 错误处理 就像 Saga 模式：某个服务失败时，触发补偿或回滚。

甚至可以把 Agent 的 Tool Use 理解为带自然语言接口的存储过程：用户用自然语言描述想要什么，Planner 把它翻译成一系列工具调用（类似 PL/pgSQL 里的函数调用），Executor 按顺序或并行执行，最后汇总结果返回。

这个类比的价值在于：你不需要把 Agent 看成黑魔法。它的底层问题——编排、依赖管理、错误恢复、性能优化——都是你已经在分布式系统和数据库里解决过的问题。迁移的只是交互界面（自然语言）和某些新概念（向量、语义相似度、LLM 不确定性）。

📰 技术雷达

行业动态

  • OpenAI 结构化输出（Structured Outputs）：2024 年底推出的 response_format: { "type": "json_schema" } 让 Planner 输出可解析的计划步骤变得稳定，减少了过去靠正则或 prompt 约束的脆弱性。
  • Anthropic 的 Model Context Protocol（MCP）：MCP 正在推动工具生态标准化。通过统一协议，Agent 可以无缝接入 Postgres、Slack、GitHub 等外部系统，而不用为每个服务写适配器。
  • Google Gemini 原生多模态工具调用：Gemini 已经支持把图像、音频作为工具输入或输出的一部分，Tool Use 正从纯文本走向多模态。
  • LangGraph ToolNode：LangGraph 把工具调用封装成图节点，支持循环、持久化、人机协同审批，是生产级 Agent 编排的事实标准之一。

论文推荐

  • Toolformer: Language Models Can Teach Themselves to Use Tools（Meta, 2023）：首次系统展示了让 LLM 自学何时调用 API，是 Tool Use 方向的开山之作。
  • Reasoning with Language Model is Planning with World Model（2023, LLM+P）：把规划问题建模为在世界模型中搜索，启发了很多后续工作。
  • Tree of Thoughts: Deliberate Problem Solving with Large Language Models（Yao et al., 2023）：用树搜索扩展 CoT，让 LLM 能探索多条推理路径。
  • Language Agent Tree Search Unifies Reasoning, Acting, and Planning（Zhou et al., 2024, LATS）：把 ReAct、规划、树搜索统一到一个框架里，是复杂 Agent 的重要参考。

开源项目

  • LangGraph：把 Planning + Tool Use 建模为状态图，内置持久化、断点、人工审批。
  • smolagents（Hugging Face）：极简 Code Agent / Tool Agent，适合快速验证规划+工具编排想法。
  • AutoGen：微软多 Agent 框架，支持 Plan-and-Execute、角色分工、工具共享。
  • CrewAI：面向角色的 Agent 团队编排，可以用类似项目管理的方式定义规划与工具调用。
  • MCP Servers 生态：越来越多的官方/社区 MCP Server 让 PostgreSQL、Docker、浏览器等系统可以直接被 Agent 调用。

今日小结

今天我们开启了「Agent 的规划与工具调用」系列的第一篇。核心收获有三点：

  1. Tool Use 提供原子能力，Planning 负责编排能力。两者结合，Agent 才能从「会查天气」升级到「能帮你规划一次完整出差」。
  2. 规划不是越复杂越好。ReAct、Plan-and-Execute、ToT / LATS 各有适用场景，生产系统通常是分层组合使用。
  3. 后端工程师的已有直觉高度可迁移。PG 查询优化器、微服务编排、RPC 调用、Saga 事务，都能在 Agent 的 Planner 和 Executor 里找到对应物。

下一篇我们会继续深入：ReAct、Plan-and-Execute、ToT 在代码里到底怎么选、怎么实现，以及如何用 LangGraph 把这些模式沉淀成可维护的状态图。
