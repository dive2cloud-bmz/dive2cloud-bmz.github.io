Agent 可观测性与审计日志架构：像监控慢查询一样监控 LLM 调用

今日一句话：Agent 的每一次思考、每一次工具调用、每一次 token 消耗，都是一次分布式事务；如果你不能追踪它，就不能优化它，更不能在出问题时复盘它。

🚀 核心洞察（2 min）

过去两周，我们从 RAG 的检索与重排走到了 Agent 的工具调用、ReAct 推理、多智能体协作与安全护栏。但一个 Agent 系统真正从 demo 走向生产，差的不只是准确率和 prompt 技巧，而是可观测性（Observability）与审计能力。

作为 RDS PostgreSQL 后端工程师，你对以下场景应该非常熟悉：

  • 线上出现慢查询，你需要 pg_stat_statements 定位执行计划、耗时分布、调用频次。
  • 某个应用账号越权访问，你需要 pgAudit 或审计表还原完整 SQL 链路。
  • 一次事务异常回滚，你需要日志中的 transaction_id、query_id、session_id 把多个服务的日志串起来。

Agent 系统同样需要这三样东西：

  1. Metrics（指标）：每次 LLM 调用的延迟、token 数、成本、成功率，就像监控 SQL 的 QPS、RT、rows fetched。
  2. Traces（追踪）：一次用户请求如何在 Planner、LLM、Tool、Memory、Reranker 之间流转，就像一次 HTTP 请求经过网关、服务、数据库的 trace。
  3. Logs（日志 / 审计）：完整的 prompt、response、tool_call、tool_result、调用者身份、时间戳，就像 pgAudit 记录每条 SQL 和参数。

今天的目标就是建立一套面向 Agent 的可观测性与审计日志架构，让你能像监控慢查询一样监控 LLM 调用，像审计数据库访问一样审计 Agent 行为。

🧠 核心概念（10 min）

1. 为什么 Agent 的可观测性比传统微服务更难

传统微服务的可观测性面临的问题是结构化、可预测的：

  • HTTP 请求有明确的 path、method、status code、header。
  • RPC 调用有 service、endpoint、request/response schema。
  • 数据库操作有 SQL、plan、lock、duration。

但 Agent 系统引入了三个新的黑盒：

黑盒 具体表现 可观测性挑战
LLM 推理过程 模型内部如何生成 thought、选择工具、组织语言，对调用者不可见 需要记录 prompt、completion、tool_calls、reasoning_content
动态工具链 每次请求可调用的工具集合可能不同，工具由模型自主决策 需要记录可用工具列表、模型选中的工具、实际执行参数
状态ful 会话 Agent 依赖 memory、上下文窗口、多轮对话，单次输出无法解释行为 需要跨轮次 trace，把 history、retrieved docs、action 关联起来

因此，Agent 的可观测性必须在传统三大支柱之上，额外关注 LLM-specific signals：prompt token、completion token、latency（TTFT / TBT / total）、模型版本、温度参数、function call 结果、retry 次数、幻觉信号、安全触发次数等。

Agent 请求的生命周期与可观测性信号

在这张图里，LLM 调用（E）和工具执行（G）是两个最关键的观测点。前者决定了成本和延迟，后者决定了安全边界和副作用。

2. LLM Tracing：把单次调用变成可还原的链路

LLM Tracing 的核心思想是：把一次 Agent 运行拆成一棵树或 DAG，每个节点是一个 span，记录输入、输出、耗时和元数据。

一个典型的 trace 结构如下：

每个 span 应包含的关键字段：

字段 含义 示例
span_id 当前节点 ID span-7a8b9c
parent_id 父节点 ID span-1a2b3c
name span 名称 llm.chat.completions
start_time / end_time 起止时间 ISO-8601
attributes 结构化元数据 model、temperature、token 数、tool 名
events 离散事件 prompt 发送、tool 被调用、exception 发生
status 成功/失败 OK / ERROR

OpenTelemetry 的语义约定（Semantic Conventions）已经为 LLM 定义了标准属性，例如 gen_ai.system、gen_ai.request.model、gen_ai.usage.input_tokens、gen_ai.response.model 等。尽量使用这些标准字段，而不是自己发明字段名。

3. 审计日志：面向合规与安全的不可变记录

Tracing 面向的是工程排查，审计日志面向的是合规、风控、安全取证。两者可以共享底层数据，但设计目标不同。

审计日志必须回答五个问题：

  1. Who：谁发起了这次交互？用户 ID、会话 ID、设备指纹、IP。
  2. When：精确到毫秒的时间戳，包含时区。
  3. What：完整的输入输出，包括 system prompt、user prompt、assistant response、tool_calls、tool_results。
  4. Which：使用了哪些模型、哪些工具、哪些知识库、哪些参数。
  5. Why：模型为什么做出这个决策？记录推理链（chain-of-thought）或工具选择理由。

审计日志的设计原则：

原则 说明
不可抵赖 每条日志包含调用者身份签名或会话令牌，防止伪造
不可变存储 审计日志写入后不能被修改，支持 WORM（Write Once Read Many）存储或只读副本
分级留存 热数据保留 7-30 天用于排查，冷数据归档 1-7 年用于合规
敏感字段脱敏 PII、密码、密钥、信用卡号必须脱敏或加密后再落盘
可追溯关联 通过 trace_id 把审计日志与业务日志、数据库日志、网关日志串起来

4. 成本与性能监控：Agent 的”慢查询”在哪里

PostgreSQL 有 pg_stat_statements 帮我们找到最耗时的 SQL。Agent 系统也需要类似的”慢调用”监控：

  • 按模型维度：GPT-4o 的平均延迟、GPT-3.5 的平均延迟、本地模型的失败率。
  • 按工具维度：哪个工具调用最频繁？哪个工具失败率最高？哪个工具平均耗时最长？
  • 按 prompt 维度：哪些 prompt 导致输出 token 过多？哪些 prompt 触发大量 retry？
  • 按用户维度：哪些用户会话 token 消耗异常？是否存在滥用或攻击？

这些指标应该进入 Prometheus / Grafana 或你的云监控体系，并设置告警阈值，例如：

  • 单次 LLM 调用 P99 延迟 > 5s
  • 工具调用失败率 > 1%
  • 单日 token 消耗环比增长 > 50%
  • 敏感工具（如 send_email、delete_user）调用次数异常

🔗 后端桥接（3 min）

作为 PostgreSQL 后端工程师，理解 Agent 可观测性最快的办法是把它和数据库领域的成熟概念一一对应。

Agent 概念 PostgreSQL / 后端类比 说明
LLM 调用 一次 SQL 查询 有输入（prompt）、输出（completion）、执行计划（reasoning）、耗时、成本
Trace / Span pg_stat_statements 中的 queryid + calls 把多次调用聚合起来，看到耗时分布和调用频次
Tool 调用 调用存储过程或外部函数 需要参数校验、权限控制、执行日志
审计日志 pgAudit 或自研审计表 记录谁、什么时候、执行了什么、结果如何
Prompt 注入检测 SQL 注入防火墙 / prepared statement 输入先过 guardrails，再进入模型
Context 窗口 work_mem / shared_buffers 容量有限，超了会 spill（退化为 RAG 或 summary）
Retry 与 Fallback 连接池 failover / 只读副本降级 主模型失败时切到备用模型或缓存
Token 成本 查询扫描行数 × I/O 单位成本 需要按用户/会话/模型维度做成本分摊

特别值得强调的是 Trace ID 的贯穿性。在数据库运维中，一次慢查询可能涉及应用层 SQL、连接池、执行计划、锁等待、I/O 多个环节。没有统一的 request_id 或 query_id，你很难把各个环节的日志串起来。Agent 系统同理：用户的一次提问可能经过 intent 路由、RAG 检索、多次 LLM 调用、多次工具调用、记忆读写。如果每个环节各自记日志却没有统一的 trace_id，出了问题就是大海捞针。

因此，在网关层或 Agent 入口生成 trace_id，并把它注入到所有下游调用（包括数据库查询、缓存访问、LLM API、工具执行），是 Agent 可观测性的第一步。

生产化思考

这个 demo 用 SQLite 做审计存储只是为了可运行。生产环境中，建议：

  • Trace 后端：Jaeger、Zipkin、Grafana Tempo，或云厂商 APM（AWS X-Ray、GCP Cloud Trace、阿里云 ARMS）。
  • 审计日志后端：ClickHouse、BigQuery、Elasticsearch、S3 + Athena，或专门的审计数据库。
  • 指标：OpenTelemetry Metrics → Prometheus → Grafana。
  • 日志脱敏：写入前用正则或 NLP 模型识别并脱敏 PII。
  • 不可变性：审计表只授予 INSERT 权限，定期归档到对象存储。

📰 技术雷达

  1. OpenTelemetry GenAI Semantic Conventions 进入稳定版倒计时：2024 年以来，OTel 社区持续完善 LLM 的语义约定，预计 2025 年内发布稳定版，统一 gen_ai.* 属性命名。如果你是 Agent 可观测性的早期采用者，现在就应该按新规范埋点，避免未来重构。

  2. LangSmith / Langfuse / AgentOps 三足鼎立：LangSmith 适合 LangChain 生态，Langfuse 开源且对模型无关，AgentOps 聚焦 Agent 会话级别的可观测性。选型时重点看：是否支持自定义 trace、成本分摊、多租户、审计合规。

  3. OpenAI 推出实时 API 的流式 trace 标准：实时语音/流式 Agent 的 trace 和传统 request/response 不同，需要考虑音频 chunk、interruption、function call mid-stream 等新信号，相关工具链正在快速演进。

  4. 欧盟 AI Act 对高风险 AI 系统的审计要求生效：任何用于招聘、信贷、医疗、教育等领域的 AI 系统都需要保留完整审计日志，包括训练数据、模型版本、输入输出、人工干预记录。Agent 系统的设计必须提前考虑合规留存周期。

  5. PGVector 与 pgAudit 结合做 RAG 审计的新趋势：在 PostgreSQL 中同时存储向量数据、业务数据和审计日志，可以通过统一的 trace_id 把检索结果、LLM 调用、业务操作串在一张数据库里，这对后端工程师是一个天然优势。
