LLM 延迟优化与成本治理：像优化慢查询一样优化 Token 消耗

今日一句话：LLM 调用不是黑魔法，而是分布在全球数据中心的”远程存储过程”；每一个 token 都是一次 IO，每一次模型选择都是一次执行计划决策。

🚀 核心洞察（2 min）

过去三天，我们构建了 Agent 的安全护栏与可观测体系。但一个 Agent 从”能跑”到”敢上线”，还面临两个最现实的工程约束：延迟（Latency） 和 成本（Cost）。这两个指标在数据库世界里你是再熟悉不过的：

  • 慢查询会拖垮整个实例的并发能力，用户体感差，资源被少数大查询吃光。
  • 无节制的全表扫描会让 CPU 和 IO 成本指数级上升，最终反映在账单上。
  • 没有连接池和限流的系统，流量一涨就雪崩。
  • 不做读写分离，所有请求都打主库，既贵又慢。

LLM 调用把这些矛盾原样复刻了一遍，只是计量单位从”行数/执行时间”变成了”token 数/调用耗时”。作为 RDS PostgreSQL 后端工程师，你手里已经握有一半答案：索引、缓存、连接池、执行计划、读写分离、物化视图、批处理——这些概念在 LLM 系统里都有直接对应。

今天的目标，是建立一套面向生产环境的 LLM 延迟优化与成本治理框架，让你能像优化慢查询一样优化 token 消耗，像治理数据库成本一样治理模型 API 账单。

🧠 核心概念（10 min）

1. LLM 调用的延迟拆解：从”发出请求”到”看到第一个字”

传统 API 的延迟通常只有一个 response_time，但 LLM 的延迟至少可以拆成三个部分：

指标 全称 含义 数据库类比
TTFT Time To First Token 从发送请求到收到第一个 token 的时间 SQL 的 planning + 索引定位 + 首行返回时间
TBT Time Between Tokens 相邻两个 token 之间的间隔（流式输出时） 结果集逐行返回的间隔
Total Latency 总延迟 完整响应所需总时间 整条 SQL 执行到结果集全部返回

为什么 TTFT 很重要？ 因为用户看到”系统正在思考”前的空白时间，直接决定产品体验。TTFT 高通常意味着：模型大、排队长、prompt 过长导致预填充（prefill）耗时增加。

为什么 TBT 很重要？ 它反映了模型生成 throughput。TBT 高意味着每个 token 都要等很久，常见于小模型部署在弱 GPU、或高并发下资源争抢。

2. LLM 成本模型：Token 就是计费单元

LLM 的账单通常由以下因素决定：

成本来源 说明 优化杠杆
输入 token Prompt、系统提示、历史对话、RAG 检索结果 压缩 prompt、摘要历史、去重上下文、缓存
输出 token 模型生成的内容长度 限制 max_tokens、引导模型简洁回答
模型单价 GPT-4 级 > GPT-3.5 级 > 自托管小模型 模型路由、降级策略
调用次数 每次独立 API 调用都有固定开销 批处理、合并请求、减少无效重试
重试与失败 超时重试、格式错误重试、幻觉导致的多轮修正 健壮的超时策略、输出校验

把 LLM 想象成按”扫描行数 + 返回行数”计费的数据库：输入 token 是你让它读的数据量，输出 token 是它写回的结果量。模型选择则像选择不同规格的只读副本——性能越好单价越贵。

3. 延迟优化技术栈

3.1 Prompt 压缩与上下文裁剪（Prompt Compression / Pruning）

这是 LLM 优化里的”减少 SELECT *”：

  • 系统提示瘦身：不要把整个产品文档塞进 system prompt，只放当前任务需要的约束。
  • 历史对话摘要：多轮对话不要每次传全量 history，而是用滚动摘要替代早期轮次。
  • RAG 结果去重与截断：检索返回的 10 个 chunk 可能互相重复，先做去重，再按相关性截断到 top-3~5。
  • 移除无关注释：Prompt 里的空行、Markdown 装饰、示例中的冗余解释都会变成 token。

3.2 缓存：语义缓存 + 精确缓存

缓存是成本治理里 ROI 最高的手段之一。LLM 缓存分两层：

  • 精确缓存（Exact Cache）：相同 prompt 直接命中，零成本返回。适合 FAQs、固定模板。
  • 语义缓存（Semantic Cache）：用向量相似度判断”这个问题是否以前问过”。适合客服、问答场景。

3.3 模型路由与降级（Model Routing / Fallback）

不是所有任务都需要最强模型。把简单问题路由到便宜模型，复杂问题才用贵模型，就像数据库读写分离：

任务类型 路由目标 类比数据库
简单分类、意图识别 小模型 / 本地模型 读副本
复杂推理、代码生成 大模型 主库
高并发兜底 便宜模型 + 限流 只读副本 + 连接池

3.4 流式输出与增量返回（Streaming）

流式输出不会减少总 token 数，但能显著改善感知延迟。用户不需要等全部内容生成完，就像数据库游标逐行返回结果。

3.5 批处理（Batching）

OpenAI 等厂商提供 batch API，把非实时请求攒一批统一处理，通常能便宜 50%。这相当于数据库里的批量插入替代单条插入。

3.6 量化与蒸馏（Quantization & Distillation）

自托管模型时，可以用 INT8/INT4 量化降低显存占用，或用蒸馏小模型替代大模型处理高频任务。类似于数据库用 BRIN 索引替代 B-tree 索引来降低空间与维护成本。

4. 成本治理框架

延迟优化是技术问题，成本治理是组织问题。一个可持续的 LLM 系统需要：

治理手段 作用 实现方式
预算上限 防止单月账单失控 每日累计消费达到阈值后切换 cheapest 模型或拒绝
用量归因 知道钱花在哪 每次调用打标签：user_id, feature, model, session_id
配额限流 防止单用户刷爆成本 按用户/会话限制 RPM 和 token 消耗
自动降级 保证可用性 大模型失败或超时时切小模型或返回缓存
成本复盘 持续优化 每周输出 Top-N 高消费请求，分析 prompt 设计

🔗 后端桥接（3 min）

作为 PostgreSQL 后端工程师，你已经在日常工作中用过这些优化思想。下面是 LLM 系统与数据库/后端系统的一一映射：

LLM 概念 PostgreSQL / 后端类比 关键洞察
输入 token 查询扫描的数据行数 让模型读得越少，成本越低、速度越快
输出 token 结果集返回的行数 限制 max_tokens 就像加 LIMIT
系统提示 存储过程/函数定义 每次调用都要加载，尽量精简
上下文窗口 共享缓冲区 / work_mem 容量有限，超出会 spill 到慢存储
Prompt 压缩 只 SELECT 需要的列、避免 SELECT * 减少无用数据传输
语义缓存 物化视图 / 查询缓存 用空间换时间
精确缓存 结果缓存 / prepared statement 相同输入直接复用结果
模型路由 读写分离 / 主从选择 按负载与复杂度选择实例
小模型兜底 只读副本 / 缓存层 保护主库不被打爆
批处理 API INSERT ... VALUES (...), (...) 摊薄每次调用的固定开销
流式输出 游标（cursor）/ 分页 改善感知延迟，不减少总成本
TTFT Query planning + index fetch 受模型大小、排队、prompt 长度影响
TBT 结果集逐行返回间隔 受 GPU throughput 和并发影响
token 限流 connection pool / rate limiter 防止单用户/单服务耗尽资源
成本归因 pg_stat_statements 按 query 统计 没有指标就无法优化

一个特别值得记住的类比：模型选择就是执行计划选择。PostgreSQL 会根据统计信息选择走索引还是顺序扫描；LLM 系统应该根据任务复杂度、当前负载、预算约束，动态选择”执行计划”（即调用哪个模型）。

📰 技术雷达

论文与研究方向

  • Prompt Compression in the Wild: Measuring Latency, Rate and Faithfulness（arXiv, 2026）：这篇工作首次在真实生产负载上系统测量了多种 prompt 压缩方法的延迟、速率与忠实度 trade-off，指出”压缩率”和”延迟收益”并不总是正相关，选择压缩策略时需要结合具体模型与任务。阅读论文
  • Speculative Decoding 持续演进：vLLM、TensorRT-LLM、Llama.cpp 都在推进投机解码（draft-then-verify），用小模型快速生成候选 token，再由大模型一次性验证，可在保持质量的前提下显著降低 TTFT 和总延迟。
  • Long Context 成本下降：随着 128K/1M 上下文模型普及，输入 token 单价持续下探，但”上下文长度”与”实际有效利用”仍是两个不同的问题；RAG 与长上下文的选择策略成为新的研究热点。

开源项目与工具

  • LiteLLM：统一接口 + 模型路由 + 成本追踪，是生产环境接入多模型时的首选中间件。支持 fallbacks、rate limits、预算告警、用量归因。
  • vLLM：自托管场景下的高性能推理引擎，PagedAttention 架构显著提升了 GPU 利用率与并发吞吐。
  • GPTCache：专为 LLM 设计的语义缓存库，支持多种向量存储后端，可直接集成到 LangChain / LlamaIndex。
  • OpenRouter / Together AI：提供多模型聚合与价格比较，适合快速试验不同模型的性价比。
  • LangSmith / Phoenix / Helicone：LLM 可观测平台，除 trace 外还提供细粒度的成本与延迟分析面板。

工程趋势

  • Cost per Query 成为核心 SLO：越来越多的团队把”单次请求成本”和”P99 延迟”并列写入服务等级目标。
  • 模型网关（Model Gateway）兴起：在应用与模型提供商之间加一层网关，集中处理路由、缓存、限流、审计、成本归因，正在成为 LLM 生产架构的标准组件。
  • 小型专用模型替代通用大模型：针对特定任务蒸馏的小模型（如代码审查、意图分类、数据抽取）在成本和延迟上往往比通用大模型便宜一个数量级。
