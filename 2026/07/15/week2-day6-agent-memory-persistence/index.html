Agent 记忆与持久化：让 LLM 拥有“长期记忆”与“断点续跑”能力

🚀 核心洞察

作为一个 PostgreSQL 后端工程师，你每天都会和“状态”打交道：事务把一组操作打包成原子单元，WAL 保证崩溃后能恢复，MVCC 让并发访问有条不紊。切换到 AI Agent 的世界，你会发现一个有趣的对应关系：Agent 的“记忆”本质上就是状态，而“持久化”就是要把这份状态像数据库里的记录一样可靠地存下来、读出来、恢复回去。

前几篇文章我们已经聊了 Function Calling、ReAct、Plan-and-Execute、LangGraph 以及 Multi-Agent 协作。今天我们把目光转向 Agent 的“后半场”——记忆（Memory）与持久化（Persistence）。没有记忆的 Agent 只能做单轮问答；没有持久化的 Agent 一旦进程重启就“失忆”；没有 Human-in-the-loop 的 Agent 则可能在关键决策上越俎代庖。掌握这三点，才能把一个“能跑”的 Agent 升级为一个“能在生产环境长期稳定跑”的 Agent。

本文会带你从记忆的类型、持久化的工程实现、Human-in-the-loop 的断点设计，一直聊到用 LangGraph 的 Checkpointer 做可恢复工作流。读完之后，你会对“Agent 的状态管理”有一个和后端系统一一对应的清晰心智模型。

🧠 核心概念

1. 为什么 Agent 需要记忆？

一个没有记忆的 Agent，就像一台只读数据库：每次查询独立、无上下文。真实场景里，Agent 需要记住：

  • 对话上下文：用户之前说了什么、Agent 自己做了什么。
  • 中间结果：调用工具得到的返回值、子任务执行状态。
  • 用户偏好：用户喜欢的输出风格、常用的参数设置。
  • 长期知识：从过往交互中学到的 facts、规则、文档片段。

可以把 Agent 的记忆抽象成一个键值状态机：state(t+1) = f(state(t), input(t))。这里的 state 就是记忆，f 是 Agent 的推理/行动逻辑。

2. 记忆的分类：短期记忆 vs 长期记忆

类型 作用范围 典型实现 类比数据库
短期记忆 单次会话或单次任务 In-memory dict、Redis、Thread-local state 会话级临时表 / Session Context
长期记忆 跨会话、跨任务 Vector DB、关系型数据库、外部 KV 持久化表 / Index
工作记忆 当前推理链中的上下文窗口 Prompt 里的 messages 列表 当前事务的 Working Set
语义记忆 从大量交互中提取的知识 Embedding + Vector Search 向量索引

短期记忆最常见，LangChain 的 ChatMessageHistory、LangGraph 的 StateGraph 状态都属于这一类。长期记忆则需要把信息写到外存，比如 pgvector、PostgreSQL 表、Redis、SQLite 等。工作记忆受限于 LLM 上下文窗口，因此需要摘要、压缩、RAG 等机制。语义记忆则是把历史经验向量化，供未来检索。

3. 持久化与检查点（Checkpoint）

持久化解决的核心问题是：进程挂了、容器重启、用户离开后，Agent 还能不能续上？

在 LangGraph 中，持久化通过 Checkpointer 实现。每个节点执行完后，当前状态会被写到一个 checkpoint。这个 checkpoint 包含：

  • thread_id：标识一次完整的执行线程。
  • step：当前第几步。
  • state：状态字典。
  • next：下一个待执行的节点。
  • writes：上一步的写操作。

4. Human-in-the-Loop（HITL）

Human-in-the-loop 不是简单地把人加进流程，而是要在关键决策点“暂停” Agent，等人确认或修改后再继续。它的技术关键在于：

  1. Interrupt：在指定节点前中断图执行。
  2. Resume：把人的输入作为新的状态写入 checkpoint，然后继续执行。
  3. Branch：根据人的选择走不同分支。

这种设计和数据库的“两阶段提交”非常像：先 prepare，等人/系统确认，再 commit。

5. 断点恢复

断点恢复（Breakpoint Resume）是持久化的延伸。它允许 Agent 在任意 checkpoint 处停下来，之后从该点恢复，而不是从头执行。LangGraph 的 interrupt / Command(resume=...) 机制就是为此而生。对于后端工程师来说，这就像：

  • 每个节点是一组业务操作。
  • 每次 checkpoint 是一次 fsync。
  • 恢复时从最后一个 checkpoint 重放（replay）后续操作。

🔗 后端桥接

把 Agent 的状态管理和 PostgreSQL / 后端系统做对比，会非常直观：

Agent 概念 数据库 / 后端类比 说明
State（状态） 行记录 / 会话上下文 当前所有变量和上下文的快照
Checkpoint WAL / 事务日志 记录状态变更，用于崩溃恢复
Thread Session / Connection 一次独立的执行流
Interrupt 两阶段提交的 prepare 阶段 暂停等待外部确认
Resume Commit / Rollback 根据外部输入继续或回退
Human approval 审批工作流 关键节点人工审核
Memory store 表 + 索引 长期记忆需要结构化存储和检索

Embedding ≈ 行序列化：把文本、知识、历史对话编码成向量，本质上和 PostgreSQL 把复杂类型序列化进 bytea 或 JSONB 类似；不同之处在于向量还要支持相似性搜索。

Checkpoint ≈ WAL + 快照： checkpoint 不仅记录了状态，还记录了“下一步该走哪个节点”，因此恢复时不需要重新推理已完成的步骤，这和 PostgreSQL 的 checkpoint + WAL 恢复异曲同工。

Human-in-the-loop ≈ 乐观锁 + 审批流：Agent 先“预执行”到某个临界点，把结果提交给人审阅；人批准后才真正生效。如果人不批准，可以回滚到上一个 checkpoint，相当于数据库的 rollback。

🛠️ 微实战

下面用 LangGraph + SQLite checkpointer + Human-in-the-loop，做一个“费用报销审批 Agent”。

场景：Agent 收集报销信息 -> 调用工具计算金额 -> 在提交前暂停，等待人工审批 -> 人工批准后写入数据库/发送通知。

代码要点：

  1. SqliteSaver 把 checkpoint 写入 SQLite，进程重启后只要 thread_id 不变就能恢复。
  2. interrupt() 让图暂停，并把需要人审的信息返回给外层系统（如 Web 后端、IM 机器人）。
  3. Command(resume=...) 让人工输入重新注入图中，继续执行。
  4. 这个模式可以无缝接入你现有的 PostgreSQL 业务库：把 finalize 节点改成写入 expenses 表，再用 pgvector 存储历史报销的语义记忆，就能做一个“越用越懂你报销习惯”的 Agent。

📰 技术雷达

  • LangGraph 0.3 持久化能力增强：官方推荐使用 Checkpointer 接口统一内存、SQLite、PostgreSQL 等多种后端，并支持跨进程恢复。
  • LangChain Memory 模块重构：新版更强调“状态即记忆”，鼓励把长期记忆放到外部存储，而非全部塞进 Prompt。
  • OpenAI Assistants API 的 Thread & Run 模型：本身就把对话状态托管在云端，相当于内置了持久化，适合做快速原型；但企业级应用仍需考虑数据主权和审计需求。
  • PostgreSQL + pgvector 作为 Agent 记忆库：越来越多项目直接用 PG 存储 agent 状态、消息历史、向量记忆，利用其 ACID 和全文/向量检索能力，减少额外基础设施。
  • Human-in-the-loop 的 UX 研究：2025-2026 年多项研究表明，在“高风险、低置信度”任务中引入 HITL，可以把 LLM 应用的错误率降低 30% 以上，同时不显著影响整体效率。

今日小结：Agent 的记忆与持久化，是把一个“玩具”Agent 变成“生产级”Agent 的关键。把 LangGraph 的 Checkpointer 想象成数据库的 WAL + checkpoint，把 interrupt/resume 想象成两阶段提交，你就能用后端工程师熟悉的视角快速理解这套机制。下一篇文章，我们会继续深入 Agent 的工程化落地，聊聊 Agent 的错误处理、重试与降级策略。
