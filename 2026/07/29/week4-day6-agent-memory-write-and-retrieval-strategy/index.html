Agent 记忆系列（06）· 写入与检索策略：像设计数据库索引一样设计记忆系统

本篇是「Agent Memory」系列第 6 篇。前 5 篇分别讨论了：为什么无状态 LLM 会失败、记忆分类学、存储架构、CoALA 论文精读，以及近期技术雷达。今天我们聚焦记忆的写入路径与检索策略——这是把记忆从”能跑”变成”好用”的分水岭。

🚀 核心洞察：给 LLM 加一层”外置索引”

作为 PostgreSQL 后端工程师，我们习惯了这样一种世界观：

  • 数据不会全部塞进 shared_buffers，而是按热度分层（内存、SSD、对象存储）。
  • 写操作不是每次都 fsync，而是先写 WAL，再由后台进程异步刷盘。
  • 查询不是全表扫描，而是靠索引 + 统计信息 + 执行计划来快速召回。

Agent 的记忆系统完全可以套用同一套思维模型：

LLM 的上下文窗口是”共享缓冲区”，容量有限、价格昂贵；记忆存储是”磁盘”；检索策略是”执行计划”；写入策略决定了事务延迟与一致性之间的取舍。

很多初学者的 Agent 把每轮对话都完整塞进 prompt，就像数据库每次查询都执行 SEQ SCAN 全表扫描——能跑，但慢、贵、且容易溢出。真正的生产级 Agent 会把”该记住什么”、”何时写入”、”如何召回”做成三个独立优化的子系统。

今天的目标就是建立这个子系统的完整直觉，并给出一套可运行的最小实现。

🧠 核心概念

1. 记忆生命周期：从感知到使用

Agent 记忆不是”存一句话”那么简单。一个完整的记忆生命周期包含五个阶段：

  • 感知：从环境输入（用户消息、工具返回值、系统事件）中捕获原始信号。
  • 编码：把原始信号压缩成语义向量、结构化事实、摘要或情感标签。
  • 存储：根据 TTL、重要性、访问频率写入不同层级（工作记忆、短期记忆、长期记忆）。
  • 检索：在需要时，根据当前上下文从存储中召回最相关的记忆。
  • 使用：把召回结果注入 prompt 或影响工具选择。

前一篇我们重点讲了存储架构，今天我们把箭头补齐，重点看编码→存储的写入路径，以及存储→使用的检索路径。

2. 写入策略：热路径、后台与混合模式

在 Agent 内部，记忆写入大致有三种模式。它们之间的差异，本质上是在响应延迟、数据一致性、系统复杂度之间做权衡。

策略 是否阻塞主流程 一致性 延迟影响 适用场景 风险
同步写入（热路径） 是 强 高 工作记忆、短期事实 拖慢响应、级联失败
异步写入（后台） 否 最终一致 低 长期记忆总结、向量化 可能丢数据、顺序乱
混合写入 关键路径同步，其余异步 可调 中等 生产系统默认选择 需要状态机维护

2.1 同步写入：像 synchronous_commit = on

同步写入意味着 Agent 在返回给用户之前，必须先把记忆落盘。它适合那些”本轮对话立刻就要用到”的信息，例如：

  • 用户刚刚提到的名字、日期、约束条件。
  • 当前任务的状态机（已完成的步骤、下一步动作）。
  • 安全相关的拒绝理由或审计日志。

同步写入的优点是简单、一致性强；缺点是它会直接计入响应延迟。如果记忆存储是远程的（比如 Pinecone、Milvus、pgvector），一次写入可能就是几十到几百毫秒。

2.2 异步写入：像 WAL + 后台 Checkpoint

更成熟的系统会把”编码 + 落盘”放到后台任务里执行。主流程只负责把原始事件追加到一个本地队列或日志，然后立即返回。后台 worker 批量消费、总结、 embedding、写入向量库。

这种模式的好处显而易见：

  • 低延迟：用户感知不到 embedding 和远程 I/O。
  • 可批处理：一次 embedding 多个片段，摊薄成本。
  • 可重试：失败后可以丢回队列，不会阻塞主流程。

但它也引入了新问题：

  • 最终一致性：如果用户下一句就问”我刚才说了什么”，后台可能还没处理完。
  • 顺序性：多线程环境下，事件顺序可能被打乱。
  • 持久化：队列本身不能丢消息，否则记忆就消失了。

解决思路是借鉴 PostgreSQL 的 WAL：先把原始事件以追加写的方式落到本地可靠存储（SQLite、RocksDB、文件日志），再异步消费。这样即使后台 worker 崩溃，事件也能恢复。

2.3 混合写入：关键路径同步，其余异步

生产系统几乎都会选择混合模式。一个典型的策略是：

  1. 热路径同步写入：只写工作记忆（内存）和关键事实（本地 KV）。
  2. 温路径准同步：把事件追加到本地 WAL，确认落盘后再返回。
  3. 冷路径异步处理：后台 worker 读取 WAL，生成摘要、 embedding、写入向量库。

这种分层让 Agent 既能在毫秒级响应用户，又能把长期记忆慢慢沉淀到向量库中。

3. 检索触发条件：什么时候去查记忆？

写入只是第一步。更微妙的问题是：什么时候触发检索？ 检索不是免费的：它涉及向量搜索、重排序、上下文拼接，都会增加延迟和 token 消耗。

常见的触发策略有三种：

触发方式 机制 优点 缺点
显式触发 Agent 通过工具调用主动检索 精确、可控 需要模型学会”何时查”
隐式触发 每轮对话前自动检索相关记忆 简单、覆盖广 容易引入噪声、浪费 token
事件驱动 话题切换、token 阈值、用户显式要求 按需、高效 需要额外的检测逻辑

3.1 显式触发：把检索当成一个工具

让 Agent 自己决定要不要查记忆，就像让查询优化器决定走不走索引。你可以在工具列表里提供一个 search_memory(query: str) 工具，模型在需要时调用。

显式触发的优势是精确。模型只会在真正需要的时候查，不会把无关的旧对话塞进上下文。但它的前提是模型足够聪明，能判断”我现在需不需要回忆”。

3.2 隐式触发：每轮自动召回

更简单的做法是在每轮对话前，先用当前用户消息做 query，从记忆库中召回 top-k 相关片段，直接拼进 system prompt 或 user prompt。

这种方式实现简单，但有两个隐患：

  • 噪声：召回的结果可能并不相关，反而干扰模型判断。
  • 成本：每轮都查，即使本轮完全不需要历史记忆。

缓解方法是设置相关性阈值和检索预算：只有当最高相关分超过阈值，且当前上下文 token 未超过预算时才拼接。

3.3 事件驱动触发：像 PG 触发器

最高效的方案是把检索当成事件驱动的动作。例如：

  • 话题切换检测：当当前消息与上一轮的 embedding 相似度低于阈值时，触发背景记忆检索。
  • 上下文长度阈值：当当前对话 token 数超过 70% 上下文窗口时，检索早期摘要。
  • 用户显式要求：”你还记得我们上周讨论的方案吗？”
  • 工具调用前：在执行某个工具前，先检索与该工具相关的历史参数或限制。

4. 召回质量优化：从”搜得到”到”搜得准”

检索召回只是起点。真正决定记忆是否”好用”的，是召回质量。以下是几个关键优化手段。

4.1 多路召回：向量 + 关键词 + 时间衰减

单一向量召回有其局限：

  • 对专有名词、ID、数字的匹配不稳定。
  • 对”最近发生的事”没有天然偏好。
  • 对语义相近但上下文不同的片段容易混淆。

多路召回（Hybrid Retrieval）可以显著改善。常见组合：

  • 向量召回：负责语义相关。
  • 关键词召回：负责精确匹配实体、ID、术语。
  • 时间衰减：给近期记忆更高权重，符合人类”近期事件更容易回忆”的特点。

融合时可以简单加权，也可以用 learned reranker。

4.2 重排序（Reranking）

初召回的 top-k 可能包含大量”语义相关但任务无关”的片段。Reranker 的作用是做第二轮精排，把真正对当前任务有用的片段排到前面。

常用的开源 reranker 包括 BAAI/bge-reranker-base、cross-encoder/ms-marco-MiniLM-L-6-v2。在中文场景下，bge-reranker-large 表现不错。

4.3 上下文压缩与摘要

有时候召回的记忆本身很长。直接拼进 prompt 会快速耗尽上下文窗口。这时需要：

  • 摘要压缩：用一个小模型把长记忆压缩成一句话。
  • 选择性注入：只注入与当前问题相关的子片段。
  • 元信息增强：在记忆前加上”这是 2026-07-01 的对话摘要”之类的时间戳和来源，帮助模型判断可信度。

4.4 相关性阈值与动态预算

不是所有查询都需要记忆。设置一个动态阈值：

  • 如果最高相关分 < 0.6，不注入任何记忆（避免噪声）。
  • 如果当前 prompt 已经用了 60% 上下文窗口，减少记忆注入量。
  • 如果用户明确提到”记得”，降低阈值、扩大召回。

🔗 后端桥接：用 PostgreSQL 的直觉理解 Agent 记忆

作为后端工程师，理解新系统的最快方式是与熟悉的东西类比。下面这张表把 Agent 记忆概念映射到 PostgreSQL / 后端基础设施：

Agent 记忆概念 PostgreSQL / 后端类比 共同关注的问题
工作记忆（Working Memory） shared_buffers 容量小、访问快、断电即失
短期记忆（Short-term Memory） WAL / 本地日志 持久化、顺序写、用于恢复
长期记忆（Long-term Memory） 表 + 索引 容量大、支持复杂查询
向量索引 GiST / GIN / pgvector ivfflat/hnsw 近似最近邻 vs 精确搜索的权衡
同步写入 synchronous_commit = on 延迟换持久性
异步写入 synchronous_commit = off + 后台 checkpoint 性能换最终一致
混合写入 WAL + 异步刷盘 主流生产配置
检索触发器 PG 触发器 + 查询计划器 何时执行、执行什么
多路召回 组合多个索引扫描 代价模型、结果合并
Reranker 排序算子 + 代价优化 精度 vs 延迟
记忆分层 Redis + PostgreSQL + S3 热温冷数据、成本分层

一个特别重要的类比：Embedding ≈ 行序列化

在 PostgreSQL 里，一行数据有各种序列化方式：JSONB、TOAST、protobuf。Embedding 也可以理解为一种”语义序列化”——它把一段文本压缩成一个固定长度的浮点数组，使得语义相近的文本在向量空间中距离近。

但 Embedding 不是银弹：

  • 它像 JSONB 索引一样，对精确匹配不友好。
  • 它像 GiST 索引一样，是近似搜索，可能漏掉真正相关的结果。
  • 它需要维护（重新 embedding），就像索引需要 REINDEX 一样。

所以生产系统里，永远不要把向量搜索当成唯一检索手段。把它和关键词、时间、结构化过滤结合起来，才是稳妥的做法。

📰 技术雷达

1. Mem0 的进展

Mem0（前身为 EmbedChain）正在快速迭代，最近新增了 MemoryStore 的多租户隔离和自动遗忘策略。它的核心卖点是”为每个用户维护一段可进化的长期记忆”，适合客服、陪伴型 Agent。不过它的检索触发仍以隐式触发为主，精细度不如自研系统。

2. LangGraph 的 MemoryStore 与 Checkpointer

LangGraph 最近把 MemoryStore 和 Checkpointer 做了更清晰的拆分：

  • Checkpointer：负责线程/会话级别的状态持久化，类似我们说的”工作记忆”。
  • MemoryStore：负责跨会话的长期记忆，支持按 user_id、thread_id 命名空间检索。

如果你已经在用 LangGraph，建议直接阅读官方文档里关于 Store 接口的部分，避免自己重复造轮子。

3. Zep AI：面向会话的长期记忆

Zep 主打”自动从对话中提取事实、摘要和情感”，并把结果存入支持时间衰减的向量库。它的一个亮点是自动摘要压缩：当会话变长时，会把早期对话压缩成摘要，而不是完整保留。这与我们今天讨论的”上下文压缩”思路一致。

4. CoALA 论文的后续影响

在第 4 天的 CoALA 精读中我们提到，Agent 的标准架构应该区分”工作记忆”与”长期记忆”。最近几个月，越来越多的框架开始把这一区分内置到 API 设计中（LangGraph、LlamaIndex、AutoGen）。可以预期，2026 年下半年”记忆即服务”（Memory-as-a-Service）会成为一个新的细分赛道。

5. 一个值得关注的开源项目：mem0ai/mem0

GitHub 上的 mem0ai/mem0 正在尝试把记忆系统做成可插拔组件。它的 API 设计简洁：

对于快速原型非常有用，但在生产环境中仍需关注其一致性、延迟和隐私模型。

小结

今天我们完成了 Agent Memory 系列的第六块拼图：

  • 写入策略：同步写入像 fsync，异步写入像 WAL + checkpoint，生产环境用混合模式。
  • 检索触发：显式触发精确但依赖模型能力，隐式触发简单但有噪声，事件驱动触发效率最高。
  • 召回质量：多路召回、reranker、上下文压缩、动态阈值是把”搜得到”变成”搜得准”的关键。
  • 后端桥接：Agent 记忆系统本质上是一个为 LLM 设计的”外置索引 + 缓存 + 存储”分层架构。
