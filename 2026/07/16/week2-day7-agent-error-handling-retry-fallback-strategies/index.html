Agent 也会”崩”：错误处理、重试与降级策略实战

🚀 核心洞察

作为从 PostgreSQL 后端转型 AI 应用工程师的开发者，你已经非常熟悉一件事：任何依赖外部服务的系统都不可能在 100% 时间内正常运行。数据库会有连接抖动、网络会超时、主库会切换、第三方 API 会限流。我们给后端系统写的每一行生产代码，几乎都包含 try/except、retry、circuit breaker、fallback 这些模式。

但进入 AI Agent 开发后，很多人会突然忘记这些基本功。原因很微妙：LLM 的返回是”概率性”的，错误不像 HTTP 500 那样黑白分明。模型可能返回一段看起来合理但完全错误的 JSON，可能调用了一个不存在的工具，可能在推理过程中突然陷入循环，也可能因为某个工具调用超时导致整个 Agent 卡住。这些问题如果不在架构层解决，会在生产环境中以极具破坏性的方式爆发。

今天的主题是 Agent 的韧性工程（Resilience Engineering）：当 Agent 的工具调用失败、LLM 解析出错、外部 API 不可用时，我们如何让系统优雅地降级而不是直接崩溃。这和 PostgreSQL 的”高可用架构”是同一个灵魂——承认故障不可避免，用设计来容忍故障。

学完今天的内容，你应该能够：

  • 识别 Agent 系统中常见的 5 类错误模式
  • 为工具调用设计指数退避重试与抖动策略
  • 实现熔断器避免级联故障
  • 设计多层降级策略（重试降级 → 简化模型 → 静态答案 → 人工接管）
  • 在 LangGraph / 自研 Agent 框架中落地这些模式

🧠 核心概念

1. Agent 系统中的错误光谱

在后端系统中，我们通常把错误分为”可重试错误”和”不可重试错误”。Agent 系统同样需要这个分类，但它更复杂，因为 LLM 的每个输出都可能是”语义错误”。下面是 Agent 中常见的五类错误：

错误类型 典型表现 是否可重试 处理策略
工具调用失败 API 返回 500/503、网络超时、DNS 失败 是 指数退避重试 + 熔断
LLM 调用失败 Rate limit、context length exceeded、服务不可用 是 重试、切换模型、降级到本地模型
输出解析失败 JSON 损坏、缺少必填字段、幻觉出非法工具名 部分可重试 重试 + 结构化解析器 + fallback
业务逻辑错误 工具返回了错误但状态码是 200、检索结果为空 否 降级响应、人工接管
无限循环 / 资源耗尽 Agent 反复调用同一工具、token 消耗失控 否 最大步数限制、预算控制、熔断

这五类错误中，前两类和后端分布式系统几乎一致；后三类是 Agent 特有的。核心区别在于：Agent 的”错误”很多时候不是异常，而是”语义上不符合预期的输出”。这要求我们不能只依赖 try/except，还要在输出验证层做防御。

2. 重试策略：不是简单 loop

最 naive 的重试是 for i in range(3): try ... except: sleep(1)。这在生产环境中往往适得其反，因为：

  • 固定间隔会在服务恢复瞬间造成”惊群效应”
  • 不对错误类型做分类会把 4xx 也重试，浪费资源
  • 没有熔断会让一个已经过载的服务被持续打爆

全抖动（full jitter） 的意义在于：如果多个 Agent 实例同时遇到同一服务故障，固定退避会让它们在同一时刻重试，形成请求尖峰；而抖动可以把重试时间打散。AWS 的这篇经典博客《Exponential Backoff and Jitter》已经证明，full jitter 在恢复场景下的性能优于固定退避。

3. 熔断器：防止情感依赖演变成系统灾难

熔断器（Circuit Breaker）在后端微服务中非常常见。它的核心思想是：如果某个依赖的失败率达到阈值，就暂时停止调用它，避免把故障扩散到整个系统。

在 Agent 中，熔断器特别适用于以下场景：

  • 某个外部工具 API 连续失败
  • 某个 LLM 模型频繁超时
  • 某个检索服务响应极慢

4. 降级策略金字塔

重试和熔断解决的是”调用是否执行”的问题，降级解决的是”调用失败后给用户什么”的问题。一个好的降级策略应该是分层的：

各层含义：

  1. 重试层：对瞬态故障（网络抖动、限流）最有效。
  2. 模型切换层：如果 GPT-4 因为上下文过长失败，可以降级到支持更长上下文的模型，或切换到更快更便宜的模型给出简化答案。
  3. 工具简化层：如果复杂工具（如数据库查询、代码执行器）失败，可以改用更简单的工具，例如直接返回 FAQ 或预计算的摘要。
  4. 静态 fallback 层：返回一个预先准备好的安全答案，例如”这个问题我需要进一步确认，请稍后重试”。
  5. 人工接管层：把对话交给人类客服或记录到工单系统。

每一层都比上一层”损失信息”，但都比直接崩溃好。设计的艺术在于：让系统在最短的时间内回到一个对用户有用的状态。

5. 输出验证：Agent 的”schema 约束”

后端的 API 会校验请求体是否符合 JSON Schema，Agent 的 LLM 输出同样需要校验。LangChain 的 PydanticOutputParser、OpenAI 的 response_format={"type": "json_object"}、 Instructor 库，都是解决这个问题的工具。

核心思路是：不要让 LLM 的原始输出直接进入下游逻辑。先经过一个验证层，把”语义错误”转换为”可处理的异常”，再进入重试或降级路径。

验证层是重试和降级的”入口”：如果解析失败，可以把这个信息反馈给 LLM，让它重新生成（Self-Correction）；如果多次失败，则进入 fallback。

🔗 后端桥接

如果你熟悉 PostgreSQL 和后端微服务，Agent 的韧性模式可以和这些概念一一映射。

1. 重试 ≈ 数据库连接池的自动重连

PostgreSQL 的连接池（如 PgBouncer、HikariCP）在连接断开时会自动重试建立新连接。它不会立刻把异常抛给应用层，而是尝试恢复。Agent 对 LLM 或工具的重试，本质上就是”连接池级别的自我修复”。

不同点在于：数据库重试通常针对低层网络异常；Agent 重试还要覆盖”语义异常”（如输出格式错误）。

2. 熔断器 ≈ 数据库主从切换 / 只读降级

当 PostgreSQL 主库不可用时，系统可以切换到只读副本，保证查询可用但禁止写入。这就是一种”熔断 + 降级”的组合：主库的”电路”打开，应用层自动把写请求放入队列或返回”当前只读”。

Agent 中的熔断器也是一样：当某个工具连续失败，系统停止调用它，切换到备用工具或静态响应。

3. 降级响应 ≈ 缓存命中（Cache Hit）

后端系统在高负载或依赖故障时，会优先返回缓存中的数据，而不是去查数据库。Agent 的 fallback 响应就是”语义缓存”：用一个预置的安全答案替代实时生成的答案。

你可以把常见失败场景的 fallback 答案预先写入向量数据库，需要时直接检索最相似的。

4. 死信队列 ≈ PostgreSQL WAL / 审计日志

后端的失败请求会被写入死信队列（DLQ）或日志，供后续分析。Agent 的失败轨迹同样需要记录：用户输入、Agent 思考过程、工具调用记录、错误类型、最终降级路径。

LangGraph 的 checkpointing 机制天然适合做这件事——它把整个状态图持久化，你可以像回放 WAL 一样回放 Agent 的执行路径。

5. 超时与预算控制 ≈ 查询超时（statement_timeout）

PostgreSQL 有 statement_timeout 防止慢查询拖垮实例。Agent 需要类似的”token 预算”和”步数限制”，防止模型在循环中无限消耗资源。

📰 技术雷达

1. LangGraph v0.2+ 的持久化与容错增强

LangGraph 最近的版本大幅强化了 checkpointing 能力，支持把 Agent 状态持久化到 PostgreSQL、Redis、SQLite 等后端。这意味着你可以：

  • 在节点崩溃后从上一个 checkpoint 恢复
  • 实现”人工介入”节点，让人类在循环中批准或修正 Agent 行为
  • 通过持久化状态实现幂等重试

对后端工程师来说，这就像给 Agent 加了 WAL（Write-Ahead Log）。

2. OpenAI Structured Outputs

OpenAI 推出的 Structured Outputs 允许开发者强制 GPT-4o 输出严格符合 JSON Schema 的结果。这显著降低了输出解析失败率，减少了重试次数。对需要稳定工具调用的 Agent 来说，这是基础设施级别的改进。

3. 开源韧性库：Tenacity、Resilience4j、Opossum

  • Tenacity（Python）：最通用的重试库，支持多种退避策略、熔断条件、自定义重试判定。
  • Resilience4j（Java）：如果你同时维护 Java 后端和 Python Agent，可以用一致的设计语言。
  • Opossum（Node.js）：轻量级熔断器，适合前端或 Node 全栈场景。

在多语言微服务架构中，建议把重试/熔断策略作为 SRE 规范统一，而不是每个 Agent 各自实现。

4. AI 可观测性：Langfuse、Phoenix、OpenTelemetry

韧性策略不能脱离观测。最新的趋势是把 LLM 调用、工具调用、重试次数、降级路径全部通过 OpenTelemetry 语义约定导出。这样你可以在 Grafana / Datadog 中看到 Agent 的”健康度”，而不仅是延迟和 token 数。

5. 论文推荐

  • “Reliable and Efficient Software Systems with LLMs”（Google, 2025）：系统讨论了 LLM 系统的错误处理、测试和监控。
  • “Chain-of-Verification Reduces Hallucination in Large Language Models”：通过自我验证减少需要重试的语义错误。

今日小结

Agent 不是魔法，它是运行在不稳定基础设施上的软件系统。作为后端工程师，你已经有了一整套应对不稳定的工具箱：重试、熔断、降级、超时、限流、日志。今天只是把这套思维模式迁移到了 Agent 上。

记住三个关键点：

  1. 先分类错误，再决定是重试、降级还是直接失败。
  2. 重试必须带抖动和熔断，否则会把小故障放大。
  3. 降级不是失败，而是系统设计的一部分。
