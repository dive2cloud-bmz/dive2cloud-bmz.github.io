LLM Wiki：Karpathy 提出的反 RAG 知识管理范式

什么是 LLM Wiki

LLM Wiki 是 Andrej Karpathy（前 OpenAI 研究主管、Tesla AI 负责人）于 2026 年 4 月发布的一个”提示模式”（prompt pattern），以 GitHub Gist 的形式公开（gist ID 442a6bf555914893e9891c11519de94f），发布后迅速获得 5000+ Stars 和 5000+ Forks。它不是一个框架或工具，而是一种理念——用 LLM 维护的纯 Markdown 文件作为知识库，取代传统 RAG（检索增强生成）中的向量数据库 + Embedding + 分块流水线。

核心哲学用一句话概括：“Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase.”

为什么不用 RAG

传统 RAG 在查询时做综合：用户提问 → Embedding → 向量检索 TopK → 拼入 Prompt → LLM 生成。每次查询都是一次”即时编译”——结果是无状态的、概率性的、不可审计的。

LLM Wiki 在摄取时做综合：新信息进入系统时，LLM 就把它编译成结构化的 Markdown 页面存储下来。查询时不需要检索，直接加载已编译好的知识。这让知识成为一个”持久的、复利累积的制品”——知识被”编译一次，然后保持更新，而非每次查询都重新推导”。

两种范式的取舍是明确的：RAG 适合海量文档（>10M token）、频繁更新的语料、面向公众的知识库；LLM Wiki 适合个人记忆、运营手册、领域专家知识、小团队知识库——这些场景下数据量在大模型上下文窗口之内（GPT-4o 128K、Claude 200K、Gemini 1M），加载全部内容比概率检索更可靠。

三层架构

Karpathy 的设计将知识系统分为三层：

Raw Sources（原始来源）。 不可变的输入材料——文章、论文、会议记录、笔记。Agent 只读不改，将其视为”记忆的原料”。

Wiki（知识维基）。 核心层。LLM 维护的结构化 Markdown 知识库，每个主题一个文件。文件之间通过 [[page-name]] 交叉引用互联，形成知识图谱。这一层不是原始材料的复制，而是 LLM 理解后的”编译产物”。

Schema（模式定义）。 一个 AGENTS.md（或类似）文件，告诉 Agent 如何维护 Wiki——命名规范、目录结构、更新策略、质量标准、何时创建新页面、何时合并已有页面。它是”程序员的代码规范”等价物。

关键文件与操作

index.md — Wiki 的导航目录，帮助 Agent 和人类快速定位页面。Agent 在回答问题前先读这个文件，确定性地决定需要加载哪些页面（而不是靠 Embedding 相似度猜测）。

log.md — 按时间记录所有操作（摄取、查询、清理），类似 Git 的 commit log，提供完整的审计轨迹。

三种核心操作：

  • Ingest（摄取）： 新来源被处理时，Agent 识别受影响的已有页面，做局部更新而非全量重写。包含矛盾检测——如果新信息与已有认知冲突，Agent 会标记并解决。
  • Query（查询）： 读取 index.md → 确定性加载相关页面 → 基于已编译知识回答。无向量检索、无概率。
  • Lint（清理/做梦）： 定期维护操作，包括：避免重复页面、衰减过期趋势、将一次性观察与可复用知识分离、更新规范页面而非堆砌新条目、保持 index 最新。这是 Schema 中编码的”睡眠整理”规则。

为什么说它比 RAG 高效 70 倍

这个数字来自计算成本的对比：RAG 系统为每次查询运行 Embedding 推理、向量数据库查询、可能的 re-ranking，最终仅传递约 2000 token 的检索结果到 LLM（其余语料闲置在向量库中）。LLM Wiki 不需要 Embedding 基础设施，直接加载 10,000-50,000 token 的精炼知识——所有加载内容都是”已编译的高密度知识”，没有 chunk 边界切割造成的信息损失。代价是上下文窗口的 token 用量更高，但随着窗口不断增长（128K → 200K → 1M），这个代价在个人规模数据量上可以忽略。

记忆类型支持

Wiki + Schema 的组合天然覆盖多种 Agent 记忆类型：

  • 语义记忆（Semantic）：概念页面、领域知识
  • 实体记忆（Entity）：人物、公司、项目页面
  • 情景记忆（Episodic）：会议记录、事件 timeline
  • 摘要记忆（Summary）：编译后的认知总结
  • 程序性记忆（Procedural）：操作手册、工作流页面

不覆盖的是对话记忆（Conversational）和工作记忆（Working Memory），因为这两种是短期、会话内的，不需要持久化。

工具链

Karpathy 的参考实现使用：

  • Obsidian — 人类端的 IDE，提供图谱可视化和快速浏览
  • Claude Code / Codex / Gemini CLI — Agent 端的执行者
  • qmd — 本地 BM25 + 向量搜索工具（当 Wiki 规模超过单次加载上限时的辅助检索）
  • Git — 版本管理，Wiki 的每一次变更都可追溯

本地部署可用 Ollama（Qwen3 32B、Llama 3 70B 等）替代闭源模型。

适用与不适用场景

适合：个人知识管理（笔记整理、读书笔记、研究追踪）、Agent 长期记忆（偏好、习惯、项目上下文）、小团队 Playbook、领域专家知识库——数据量在数百页以内、需要高确定性和可审计性。

不适合：大规模文档检索（>10M token）、频繁全量更新的语料库、面向公众的知识服务、需要实时 Embedding 和模糊匹配的场景。

与 GBrain 的关系

GBrain 可以被看作 LLM Wiki 思想的”工程化实现”——它继承了 Markdown-in-Git 的系统设计，加上了 Postgres 混合检索（当 Wiki 规模超出单次 context 加载能力时的检索层）、自动化的类型化边提取、和可执行的技能系统。两者的哲学一脉相承：知识应该被编译后存储为人类可读的持久制品，而非每次查询时从碎片中临时拼凑。

小结

LLM Wiki 的贡献不在于任何新技术——它用的是 Markdown、Git、Obsidian 这些已存在多年的工具。它的贡献在于思维范式的转换：当大模型的 context window 足够大时，”检索”不再是必需品。你可以把知识库当作”代码”来管理——Agent 是维护者，Schema 是代码规范，Lint 是 CI/CD，Git 是版本控制。这让 AI 记忆系统的构建门槛从”需要向量数据库专家”降低到”会写 Markdown”。
