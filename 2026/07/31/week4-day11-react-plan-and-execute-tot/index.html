Agent 的规划与工具调用（02）：ReAct / Plan-and-Execute / ToT 的代码实现与选型

🚀 核心洞察：规划不是预测未来，而是为不确定性预留分支

上一篇我们把 Agent 的「规划」与「工具调用」放在一张地图里看了全景。今天我们要把地图上的三座山头挨个爬一遍：ReAct、Plan-and-Execute、Tree of Thoughts（ToT）。

这三者的区别，可以用 PostgreSQL 的执行策略来快速建立直觉：

  • ReAct 像游标式的逐行执行：每拿到一行结果，就决定下一步用哪个算子。灵活，但长链路容易短视。
  • Plan-and-Execute 像 PREPARE 后 EXECUTE：先根据当前统计信息生成完整计划，再一口气执行。稳定，但遇到计划外情况会僵化。
  • ToT 像优化器在多个候选计划间做成本估算：同时展开多条思路，评估后再选最优路径。能力强，但代价高。

作为后端工程师，你每天面对的选择题和 Agent 的规划层本质上是一样的：在信息不完整、环境会变化、成本有预算的情况下，决定「下一步做什么」。今天我们会把这三个模式写成可运行的 Python 骨架，并给出选型建议。

🧠 核心概念：三种规划模式的实现原理

1. ReAct：边想边做，单步决策

ReAct（Reasoning + Acting）来自论文 ReAct: Synergizing Reasoning and Acting in Language Models。它的核心循环只有三步：

ReAct 把推理过程显式化，让 LLM 在每次行动前都输出一段「思考」。这段思考不直接作用于外部世界，但会进入上下文，影响下一步决策。

它的优点和缺点都很明显：

维度 评价
延迟 低，每步只生成一个 Action
Token 成本 中等，但长链路上下文会膨胀
灵活性 高，能根据最新观察随时转向
可审计性 好，每一步都有 Thought 记录
长程稳定性 差，容易陷入局部最优或重复调用

ReAct 最适合工具数量不多、单步反馈明确、任务可在十几步内完成的场景，比如查数据库慢查询、调几个 API 后汇总答案。

2. Plan-and-Execute：先计划，后执行，再修正

Plan-and-Execute 把任务拆成两个阶段：

  1. Planner：根据目标生成一个步骤清单（Plan）。
  2. Executor：按顺序执行每个步骤，必要时把中间结果回传给 Planner 进行重规划。

这个模式的关键是计划与执行的解耦。Planner 可以用一个更强的模型（擅长推理但慢），Executor 可以用一个更快的模型（擅长遵循指令）。当某一步失败时，Planner 只看到当前状态，不需要重新理解整个历史。

Plan-and-Execute 适合步骤可预先拆解、目标明确、对可审计性要求高的任务，比如生成一份标准化报告、按 checklist 巡检系统。

3. Tree of Thoughts：多路径搜索，择优而行

ToT 把 LLM 的推理过程从一条链扩展成一棵树：

  • 每个节点是一个「思维状态」（当前已完成的推理）。
  • 每个分支是一次「思考步」或「候选行动」。
  • 通过评估函数（可以是另一个 LLM 调用，也可以是规则/启发式）给节点打分。
  • 使用 BFS 或 DFS 在树中搜索，找到得分最高的路径。

ToT 的强大之处在于它能主动探索多种可能性，而不是一条路走到黑。代价是 Token 消耗和延迟都会显著增加。

ToT 适合高价值、需要试错、答案质量比成本更重要的任务，比如复杂的数据分析、策略生成、代码修复方案选择。

4. 三种模式的核心差异速查

特性 ReAct Plan-and-Execute Tree of Thoughts
决策时机 每步决策 先全局计划，再局部调整 多路径并行探索后决策
上下文长度 线性增长 Plan 阶段短，执行阶段可控 随分支数指数增长，需要剪枝
容错能力 中（靠单步反馈修正） 中（靠 Replan） 高（可回退到父节点）
Token 成本 中 中低 高
实现复杂度 低 中 高
典型框架 LangChain ReAct Agent, AutoGPT LangGraph Plan-and-Execute ToT 原论文实现, LATS

🔗 后端桥接：PG 查询优化器已经做了几十年同样的事

作为 PostgreSQL 后端工程师，你不需要从零理解规划。查询优化器本身就是一个非常成熟的 Planner：

把 Agent 的规划层映射过去，会看到很多熟悉的概念：

Agent 规划概念 PostgreSQL 类比 说明
ReAct 游标 + 运行时自适应 每处理一部分数据就决定下一步，适合流式或不确定场景
Plan-and-Execute PREPARE / 生成计划树 先完整规划，再执行，强调可预测性
ToT 多候选路径 + 成本估算 优化器会考虑 SeqScan、IndexScan、BitmapScan 等多种路径，选成本最低者
Replan 运行时重新选择计划 / 自适应查询优化 当统计信息不准或数据分布变化时调整计划
评估函数（ToT） 成本模型（cost model） 用一组启发式公式给候选路径打分
工具 Schema 算子能力声明 优化器知道每个算子支持什么条件、返回什么数据

还有一个更贴近日常工作的类比：ORM / 查询构建器。你写一段业务逻辑时，ORM 会先构建一个查询计划（类似 Planner），再交给数据库执行（类似 Executor）。如果中间某个查询慢了，你会看 EXPLAIN ANALYZE（类似 ToT 的评估函数），然后决定加索引、改写 SQL 或换连接方式（类似 Replan）。

Agent 的规划层并没有发明新问题，它只是把「如何完成一个复杂目标」从结构化语言（SQL）迁移到了自然语言。你之前解决的成本估算、错误恢复、并发执行、超时熔断等问题，在这里都会再次遇到。

「最近用户反馈订单查询慢，帮我定位原因并给出优化建议。」

Agent 可调用的工具包括：

  • get_slow_queries：获取慢查询列表。

📰 技术雷达：规划与工具调用领域的新动向

  • OpenAI o1 / 推理模型：o1 系列把「思考」作为内部过程，不再像 ReAct 那样把 Thought 暴露给开发者，但核心理念一致——模型在回答前进行多步推理。对 Agent 规划层的影响是：Planner 可以变得更轻，模型本身承担了更多搜索工作。

  • Anthropic Computer Use：Claude 3.5 Sonnet 支持直接控制计算机桌面。这意味着工具不再局限于 API，而是扩展到 GUI 操作。工具调用的边界正在从「结构化函数」扩展到「任意环境交互」。

  • LangGraph v0.2 + Pregel：LangGraph 把 Agent 的状态机模型做得更接近数据库的流式执行引擎，支持中断、恢复、人机协同（human-in-the-loop）。对于需要长周期运行的 Plan-and-Execute 任务，这是重要的基础设施。

  • DSPy BootstrapFS / 优化器：DSPy 提供了自动提示优化和少样本学习机制，可以让 ReAct / Plan-and-Execute 的 Prompt 不再靠手工调优，而是像训练模型超参一样搜索最优提示组合。

  • LATS / RAP 等后续工作：ToT 之后，研究者提出了 Language Agent Tree Search（LATS）和 Reasoning via Planning（RAP），把 ToT 与强化学习、世界模型结合起来。如果你的任务需要高质量长程推理，值得关注这两个方向。

  • Prompt Caching：Anthropic 和 OpenAI 都推出了提示缓存机制，能显著降低长上下文规划任务的成本。对于 Plan-and-Execute 和 ToT 这种需要反复读取历史记录的范式，这是立竿见影的优化。

今日小结

今天我们实现了三种 Agent 规划模式：

  • ReAct：边想边做，适合短链路、高反馈密度的任务。
  • Plan-and-Execute：先计划后执行，适合可拆解、可审计的任务。
  • Tree of Thoughts：多路径搜索，适合高价值、需要试错的复杂决策。

作为后端工程师，你可以把 Agent 规划层理解为「用自然语言写的查询优化器」：核心问题仍然是成本估算、路径选择、错误恢复和并发执行。下一篇我们会把目光从「单个 Agent 怎么规划」转向「多个 Agent 怎么协作」，进入多 Agent 编排的领域。
