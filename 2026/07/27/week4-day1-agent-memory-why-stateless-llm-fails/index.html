Agent 记忆系列（01）· 为什么无状态的 LLM，走不通真实业务？

🚀 核心洞察

作为一个写了多年 PostgreSQL 后端的人，我第一次调 OpenAI API 时，第一反应是：这不就是一个更贵、更慢、更不稳定的 HTTP 服务吗？

这句半玩笑的话背后其实藏着一个非常严肃的工程事实——大语言模型（LLM）的原生调用是彻底无状态的。它不认识你昨天问过什么，不知道你上一句话是啥，甚至同一个会话里第 5 轮和第 6 轮之间，如果你不主动把历史塞回去，它也一无所知。

后端工程师听到”无状态”三个字通常是感到欣慰的，因为无状态意味着可以水平扩展。但在 Agent 场景下，无状态意味着”没有记忆”。而一个没有记忆的智能体，永远只能是一个高级的翻译机、一个功能更花哨的搜索框，绝对成不了”真正能替你干活的助理”。

Agent 记忆（Agent Memory），就是把 LLM 从”无状态请求响应”改造成”有历史、有偏好、有经验积累的持续实体”的那层关键工程。从今天起，这个博客系列会用大约 9 篇文章，把 Agent 记忆这件事讲透：从它是什么、有哪些方向，一路挖到长期记忆的发展史、当下主流方案和未来演进。

今天是全景篇第 1 篇，先解决一个最根本的问题——为什么 Agent 需要记忆？

🧠 核心概念

1. 无状态 LLM 的三大痛点

要理解 Agent 记忆的价值，最好先看清”没有记忆”到底会出什么问题。总结下来是三大痛点：

痛点一：上下文窗口是硬物理上限，”塞得进”不等于”用得好”

LLM 的上下文窗口是有限的。截至 2026 年年中，主流模型的官方上下文窗口大致是这样：

模型 官方上下文窗口
GPT-4o 128K tokens
Claude Sonnet 4.5 200K tokens
Claude Sonnet 5 / 4.6 1M tokens（默认，无需 beta header）
Gemini 1.5 Pro 1M tokens（发布时）→ 后扩展到 2M

数字很漂亮，但两个问题绕不开：其一是成本和延迟——每次都把几十万 token 塞进去，token 计费和响应时间都会失控；其二是质量——2023 年斯坦福 Nelson F. Liu 等人的经典论文 Lost in the Middle: How Language Models Use Long Contexts 证明了一个反直觉但重要的现象：即便上下文放得下，模型对开头和结尾的信息利用率显著高于中间部分，长上下文里”塞进去”和”用得上”完全是两回事。

换句话说，把所有历史一股脑塞进 prompt 从来不是长久之计。

痛点二：跨会话遗忘——每次都是”你好，请问您是？”

即使在同一次会话内可以把历史全部塞进上下文，一旦会话结束、进程重启、或者用户换设备重新打开对话框，模型就把之前的一切彻底忘光。这意味着一个用户告诉过 AI”我对花生过敏、我是纯素食者”，第二天再问它推荐食谱，它仍然可能给你端上一盘花生鸡丁。

在真正的产品里，这种”金鱼式失忆”是不可接受的。

痛点三：无法积累经验——同一个错误犯一百遍

一个真正智能的 Agent 应该能从失败中学习。比如它调工具报错、被用户纠正、被审核拒绝，下一次遇到类似场景应该改进而不是复读。但无状态 LLM 没有任何机制把”上次踩坑的教训”沉淀下来，除非你手动把这些教训重新塞进 prompt。

2. Agent 记忆的定义

综上，我给”Agent 记忆”下这样一个工程视角的定义：

Agent 记忆是围绕 LLM 构建的一整套外部状态管理机制，用于在有限的上下文窗口之外，持久化、组织、检索和更新对当前决策有用的信息，使 Agent 具备跨轮次、跨会话、跨任务的一致性和学习能力。

关键词有四个：外部状态、有限窗口之外、持久化组织检索更新、跨轮次会话任务。它同时对应了系统设计中的四种能力：存储、结构化、召回、演化。

3. Agent 记忆的三层视角

在正式进入分类之前，先给出一个覆盖全系列的三层视角图，后面每一篇都会挂在这张图上：

这个分类的学术基础来自 Sumers、Yao 等人在 2023 年提出的 Cognitive Architectures for Language Agents (CoALA)（TMLR 2024）。CoALA 把认知科学中经典的”工作记忆 / 语义记忆 / 情景记忆 / 程序记忆”框架移植到语言 Agent 上，成为如今讨论 Agent 记忆时最常引用的理论骨架。

今天先不展开各个维度，明天的 Day 2 会详细拆。你只需要记住：记忆不是一个东西，而是一组正交维度组合出的一片空间。

4. “有记忆”能带来什么？——一个具体的对照

抽象说了这么多，来看一个具体对比。同一个用户，第一次会话说过”我叫小明，我对花生过敏”。

无记忆 Agent 的第二次会话：

用户：给我推荐一份晚餐。
Agent：好的，可以试试宫保鸡丁，主要食材有鸡肉、花生……

有记忆 Agent 的第二次会话：

用户：给我推荐一份晚餐。
Agent：小明你好，考虑到你对花生过敏，我建议试试清炒虾仁配西兰花，不含任何坚果类食材……

差别不在模型能力，而在于记忆层是否被工程化地建立起来。这也是为什么 2024–2026 年，MemGPT / Letta、Mem0、Zep、LangMem 这些”专门做 Agent 记忆层”的项目会集中涌现——市场需求非常明确，而底层 LLM 并不打算自己解决这个问题。

🔗 后端桥接

对后端工程师来说，Agent 记忆的很多概念其实似曾相识。下面这张类比表可以直接迁移直觉：

后端概念 Agent 记忆中的对应 迁移直觉
HTTP 无状态请求 原生 LLM 调用 每次请求都是独立的，服务器不认识客户端
Session / Cookie 会话内的短期记忆 用外部标识符把多次请求串成一个”会话”
Redis / PostgreSQL 会话表 长期记忆存储 跨进程、跨机器、跨时间的持久化状态
连接池 上下文窗口预算管理 都是一种”有限资源的复用与调度”
数据库范式化 vs 反范式化 结构化记忆 vs 向量化记忆 结构化便于精确查询，向量化便于语义检索
缓存过期策略（LRU/TTL） 记忆的遗忘机制 都要决定”什么信息该被清除、什么该保留”
WAL / Binlog Agent 行为日志与情景记忆 事件级的完整历史，可回放、可审计
主键 / 外键 记忆之间的关联关系 让离散的记忆条目形成图结构

一个特别值得注意的类比是上下文窗口 ≈ 内存，长期记忆 ≈ 磁盘。这正是 MemGPT 论文 MemGPT: Towards LLMs as Operating Systems（Packer et al., 2023）的核心思想：把 LLM 当作 OS，用分层存储和分页调度来管理有限的”内存”（上下文）与更大的”磁盘”（外部记忆）。系列后续 Day 6 会详细拆这套架构。

如果你熟悉 PostgreSQL 的 shared_buffers / OS page cache 层级，那么 MemGPT 的设计几乎是同构的思路——不是”扩大内存”，而是”更聪明地在内存和磁盘之间搬运数据”。

📰 技术雷达

Agent 记忆是过去 18 个月里 AI 工程领域最热门的方向之一。几个必须留意的动态：

  • CoALA 框架成为共同语言（2023，TMLR 2024）：Sumers、Yao、Narasimhan、Griffiths 的 Cognitive Architectures for Language Agents 用认知科学的四类记忆重塑了 Agent 讨论范式，如今几乎所有严肃的记忆框架论文都会引用它。
  • MemGPT / Letta 把”OS 隐喻”带进 LLM（2023）：MemGPT 提出”虚拟上下文管理”，用分层存储 + function calling 让模型自己决定”哪些信息从磁盘搬进内存”。项目后来演进为 Letta，成为开源 Agent 记忆基础设施代表。
  • Mem0 带着基准数据登场（2025.04）：Mem0 论文 在 LOCOMO 对话记忆基准上给出了硬指标——相比 OpenAI 原生方案在 LLM-as-Judge 上有 26% 相对提升，相比”全上下文塞入”方案 p95 延迟降低约 91%、token 成本节省 90%+。这是”记忆层带来的量化收益”第一次被讲得比较清楚。
  • Long Context 与 Memory 之争：Claude Sonnet 4.6/5 默认 1M、Gemini 1.5 Pro 上到 2M。上下文越大，是否就不需要记忆层？Lost in the Middle 早给出否定回答——大窗口和好记忆是互补关系，不是替代。
  • “记忆即服务”生态成型：Mem0、Zep、LangMem、Cognee、MemVid 等项目并行发展，各有侧重（图谱化、时序更新、开源可控、多模态），后续 Day 3、Day 6、Day 7 会做横向对比。
