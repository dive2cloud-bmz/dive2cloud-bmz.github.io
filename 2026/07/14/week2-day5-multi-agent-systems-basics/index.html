从单兵作战到团队协作：Multi-Agent 系统基础与角色分工

一个 Agent 解决一个问题，一群 Agent 解决一个领域。

🚀 核心洞察：为什么单 Agent 不够用了？

作为后端工程师，我们早就习惯了「拆分」。当单体应用扛不住流量时，我们把它拆成微服务；当单台 PostgreSQL 的写入成为瓶颈时，我们引入读写分离和分片；当单个进程处理不过来时，我们用消息队列把任务派给多个消费者。拆分的本质不是炫技，而是让复杂度与能力边界对齐。

前几天的学习中，我们已经掌握了 Function Calling、ReAct、Plan-and-Execute、LangGraph 这些单 Agent 的「武器库」。它们足以完成很多任务：查天气、写脚本、做简单推理。但如果你让单个 Agent 独立完成「调研一个新技术领域 → 收集资料 → 撰写报告 → 同行评审 → 输出终稿」，它很快就会暴露出三个致命短板：

  1. 上下文过载：单个 LLM 的上下文窗口终究有限，塞入过多角色、工具和资料后，注意力会涣散，输出质量断崖式下降。
  2. 能力边界模糊：一个 Agent 既要当调研员、又要当写手、还要当审稿人，就像让同一个后端工程师同时写 SQL、调 Kubernetes、画前端页面，结果往往是「样样通、样样松」。
  3. 缺乏自我纠错：写完后自己审稿，容易陷入确认偏误（Confirmation Bias），看不出自己代码里的 Bug，也看不出自己文章里的漏洞。

Multi-Agent 系统的思路非常自然：让多个 Agent 分别承担不同角色，通过协作完成复杂任务。这和我们把系统拆分为订单服务、库存服务、支付服务是同一个逻辑。今天的目标，就是建立 Multi-Agent 的直觉框架，理解角色分工、通信机制和常见的协作模式。

🧠 核心概念

2.1 什么是 Multi-Agent 系统？

Multi-Agent 系统（MAS，多智能体系统）由两个或更多自主 Agent 组成，每个 Agent 拥有特定的角色、目标和可用工具，它们通过某种通信机制协作，以完成单个 Agent 难以独立完成的复杂任务。

与单 Agent 相比，Multi-Agent 的核心变化不是「模型变强了」，而是架构变清晰了：

可以把单 Agent 想象成一个全栈独立开发者，而 Multi-Agent 更像是一个敏捷小队：产品经理拆解需求、后端工程师实现接口、测试工程师找 Bug、DevOps 负责上线。每个人都在自己的专业领域内工作，通过站会、文档和 CI/CD 流水线交换信息。

2.2 常见的 Agent 角色

虽然角色命名在不同框架里略有差异，但底层职能高度一致。下面这张表总结了 Multi-Agent 系统中最常见的四种角色：

角色 职责 类比后端岗位 常用 Prompt 关键词
Planner / Supervisor 拆解任务、分配子任务、监控进度 技术负责人 / 架构师 “分解为可执行步骤”、”分配给最合适的 Agent”
Researcher / Executor 执行具体子任务，调用工具收集信息 后端开发工程师 “调用 API”、”查询数据库”、”返回结构化结果”
Writer / Synthesizer 整合信息，生成最终输出 技术文档工程师 “基于以下资料撰写”、”保持风格一致”
Critic / Reviewer 检查质量、发现错误、提出改进建议 代码评审员 / QA “找出逻辑漏洞”、”评估是否满足需求”

一个高质量的 Multi-Agent 团队通常不是四种角色全上，而是按需组合。例如：

  • 代码生成：Planner + Coder + Critic
  • 研究报告：Researcher + Writer + Critic
  • 客户服务：Router + FAQ Agent + Escalation Agent

2.3 四种经典协作模式

Multi-Agent 的协作模式，本质上回答的是「谁听谁的、谁和谁说话」这两个问题。以下是四种最常见的模式：

模式一：层级式（Hierarchical）

一个 Supervisor Agent 负责任务分发和结果汇总，其他 Worker Agent 只与 Supervisor 通信。这是最容易理解和调试的模式。

优点：结构清晰、责任明确、适合有明确阶段划分的任务。
缺点：Supervisor 容易成为瓶颈，Worker 之间无法直接共享信息。

LangGraph 的 create_supervisor 和 AutoGen 的 GroupChat 都支持这种模式。

模式二：协作式（Collaborative / Peer-to-Peer）

所有 Agent 处于平等地位，通过共享黑板（Blackboard）或消息总线交换信息。没有唯一的指挥中心。

优点：灵活性高，适合探索性、创造性的任务。
缺点：容易陷入讨论循环，收敛性差，需要明确的终止条件。

CrewAI 的默认工作流、AutoGen 的 round_robin 群聊都属于这一模式。

模式三：竞争式（Competitive）

多个 Agent 分别生成候选答案，再由一个 Judge Agent 打分并选出最优解。这种模式常见于代码生成和创意写作。

优点：通过多样化探索提升输出质量上限。
缺点：成本高、延迟大，需要设计好评分标准。

模式四：混合式（Hybrid）

真实生产环境往往是混合的：顶层是层级式 Supervisor，底层工作组内部是协作式，最后再用 Judge 做质量把关。

2.4 Agent 之间的通信机制

协作离不开通信。Multi-Agent 中常见的通信方式有三种：

方式一：消息传递（Message Passing）

每个 Agent 将输出封装成消息，发送给下一个 Agent 或广播到群聊。消息通常包含：

  • sender：发送者身份
  • recipient：接收者（可选，广播时可省略）
  • content：内容
  • metadata：附加信息，如置信度、引用来源、完成状态

方式二：共享内存（Shared Memory / Blackboard）

所有 Agent 读写同一块状态。LangGraph 的 StateGraph 就是最典型的实现：每个节点修改全局状态，其他节点可以看到更新。

这种方式和后端的共享数据库非常相似，优点是状态一致性好，缺点是如果多个 Agent 同时修改同一块数据，需要处理并发冲突。

方式三：直接调用（Direct Invocation）

一个 Agent 把另一个 Agent 当作工具调用。例如 Planner 发现需要查询数据库时，直接调用 Researcher Agent 的 run() 方法。这种方式耦合度较高，适合层级明确的场景。

2.5 冲突解决与终止条件

Multi-Agent 协作中最容易踩坑的地方，不是让 Agent 们动起来，而是让它们停下来。

常见的终止策略有：

策略 说明 适用场景
轮次限制 最多讨论 N 轮 防止群聊无限循环
共识达成 所有 Agent 投票通过 评审、决策类任务
质量阈值 Judge 打分超过阈值即终止 代码生成、方案评选
任务完成标记 某个 Agent 显式输出 FINISH 工作流类任务

冲突解决则更像分布式系统中的共识问题。简单场景可以用 Supervisor 一票否决；复杂场景可以引入投票机制或外部 Judge。一个实用的技巧是：让 Critic Agent 只提问题，让 Planner 决定是否采纳，避免多个 Agent 互相拉扯。

🔗 后端桥接：用 PostgreSQL 和微服务理解 Multi-Agent

作为从后端转型 AI 应用的工程师，我最怕的是把 AI 概念当成全新的魔法。其实 Multi-Agent 里的很多问题，我们在后端领域已经解决过很多次。

Agent ≈ 微服务

每个 Agent 有自己的职责、输入输出协议和可调用资源，就像一个微服务。Single Agent 是单体应用，Multi-Agent 是微服务架构。服务拆分带来的好处（高内聚、低耦合、可独立扩展）在 Multi-Agent 里同样成立。

消息传递 ≈ 消息队列

Agent 之间的消息，对应 Kafka 或 RabbitMQ 中的事件。我们需要考虑：消息格式（Schema）、路由策略（Topic/Routing Key）、幂等性、重试机制、死信队列。把 Agent 通信当作事件驱动架构来设计，会少踩很多坑。

共享内存 ≈ 共享数据库 / Redis

LangGraph 的 Shared State 就是共享数据库。多个 Agent 并发修改状态时，要像处理数据库事务一样考虑一致性。如果是只读共享，Redis 缓存就够了；如果需要强一致性，就要引入锁或乐观并发控制。

工具注册 ≈ 服务发现

Agent 怎么知道有哪些工具可用？这和微服务里的服务发现（Consul、Eureka、Kubernetes DNS）是一样的。你可以维护一个工具注册中心，Agent 在运行时查询并调用。

共识与冲突 ≈ 分布式共识协议

多个 Agent 争论不休时，就像分布式系统中的脑裂。简单场景用 Supervisor（类似主从架构），复杂场景用投票或外部仲裁（类似 Raft/Paxos 的 Leader 选举）。

一个 SQL 风格的类比

如果把 Multi-Agent 系统比作 PostgreSQL：

  • Supervisor 就是查询优化器，决定执行计划；
  • Worker Agent 就是执行器里的各个算子（Seq Scan、Index Scan、Join）；
  • Shared State 就是共享缓冲区（Shared Buffer），所有算子读写同一份中间结果；
  • 工具调用 就是外部表（Foreign Data Wrapper），让数据库能访问外部数据源；
  • 终止条件 就是查询执行完成或超时中断。

这个类比不是为了强行套概念，而是帮助我们借用已经成熟的后端思维，去设计更可靠的 AI 系统。

📰 技术雷达

1. OpenAI Swarm：轻量级 Multi-Agent 编排

OpenAI 在 2024 年底开源了 Swarm，一个强调「轻量、可解释、高度可控」的 Multi-Agent 框架。它的核心抽象是 Agent 和 handoffs：一个 Agent 可以把控制权交给另一个 Agent。Swarm 不适合复杂状态管理，但非常适合做客服路由、分层任务分发等场景。

2. CrewAI：角色驱动的工作流

CrewAI 是目前最受欢迎的 Multi-Agent 框架之一。它把 Agent、Task、Crew 三个概念抽象得非常清晰：Agent 是角色，Task 是任务，Crew 是团队。CrewAI 适合快速搭建研究团队、内容创作团队等角色明确的任务。

3. AutoGen v0.4：微软的 Agent 生态系统

微软 AutoGen 在 2024 年底发布了 v0.4 大版本，核心变化是从「群聊框架」升级为「模块化 Agent 运行时」。它支持异步消息、分布式 Agent、代码执行环境，适合企业级 Multi-Agent 应用。

4. Google Agent2Agent Protocol（A2A）

Google 在 2025 年推出了 A2A 协议，试图解决不同厂商 Agent 之间的互操作问题。A2A 定义了 Agent 之间的发现、协商、任务分发和能力描述标准。对于后端工程师来说，这类似于 REST/gRPC 在微服务时代做的事情：统一通信协议。

5. Anthropic Model Context Protocol（MCP）

MCP 是 Anthropic 提出的开放标准，用于统一 LLM 与外部数据源、工具的连接方式。在 Multi-Agent 场景中，MCP 可以让不同 Agent 共享同一套工具接口，降低集成成本。

6. 值得关注的研究方向

  • Multi-Agent Debate：多个 Agent 通过辩论提升推理能力，代表工作如 《Improving Factuality and Reasoning in Language Models through Multiagent Debate》（2023）。
  • Agent Society / Emergent Behavior：研究大量 Agent 交互时是否会产生涌现行为，类似多智能体强化学习中的群体智能。
  • Cost-Aware Multi-Agent：在多个 Agent 协作时优化调用成本，例如用小模型做初筛、大模型做精修。

写在最后

Multi-Agent 不是银弹。它的价值在于把复杂任务拆成可管理的子任务，让每个 Agent 在合适的边界内发挥作用。作为后端工程师，我们已经有丰富的分布式系统和微服务设计经验，这些经验可以直接迁移到 Multi-Agent 架构中：服务拆分、消息队列、共享状态、服务发现、共识协议，这些概念在 AI 时代依然有效。

今天的学习只是一个起点。明天，我们会深入一个更具体的问题：如何让多个 Agent 在共享上下文中高效协作而不互相干扰。这相当于后端里的「并发控制」和「事务隔离」，敬请期待。
