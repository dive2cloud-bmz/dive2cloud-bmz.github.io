LangGraph 基础：用状态图把 Agent 工作流工程化

🚀 核心洞察（2 分钟速览）

前面三天，我们依次走过了 Function Calling、ReAct 和 Plan-and-Execute + Reflection。你已经看到，Agent 的本质是一个“决策—执行—观察”的循环。但当这个循环里出现分支、重试、人工审批、并行调用、持久化恢复时，用简单的 while 循环来写代码会迅速失控。

想象一个真实的数据库诊断场景：

  1. 先查询慢查询日志。
  2. 如果存在超过 2 秒的查询，进入根因分析分支。
  3. 根因分析里，同时检查索引、表结构和执行计划（并行）。
  4. 如果缺少索引，自动生成索引建议并等待 DBA 审批（人工节点）。
  5. 审批通过后执行创建索引；被拒绝则记录原因并结束。
  6. 每一步都要持久化状态，以便失败后能从断点续跑。

用纯 ReAct 的线性循环表达这个流程，就像用一段没有函数的 main() 去写整个微服务：能跑，但不可维护。而 LangGraph 做的事情，就是把 Agent 的执行流程显式建模为状态图（State Graph）：节点是计算单元，边是状态流转，循环、分支、并行都可以被清晰地定义和可视化。

对于 PostgreSQL / 后端工程师来说，这并不新鲜。LangGraph 的 StateGraph 就像一个内存中的工作流引擎（Airflow / Temporal 的轻量版）加上一个LLM 驱动的决策节点。它把 Agent 从“一段脚本”提升为“一个可观测、可审计、可恢复的系统”。

今天的核心结论：ReAct 是 LangGraph 的一个特例；LangGraph 是工程化 Agent 的通用框架。

🧠 核心概念（10 分钟深入）

1. 为什么需要 LangGraph？从线性循环到图结构

我们先回顾一下 ReAct 的线性结构：

这个模型在简单任务里非常优雅，但它有几个天然的限制：

限制 表现 LangGraph 的解法
单一路径 每一步只能有一个下一步 支持条件分支、并行分支
无显式状态 状态隐含在 messages 列表里 显式定义 State 结构体
难持久化 循环中断后只能从头开始 内置 checkpointer，支持断点续跑
难插人工 无法在中途暂停等待人类输入 支持 interrupt / Human-in-the-loop
难可视化 流程藏在代码逻辑里 图结构可直接渲染为 Mermaid / Studio

LangGraph 的解决思路并不复杂：它把 Agent 的每一次“思考”或“行动”抽象为节点（Node），把状态之间的流转抽象为边（Edge），整个 Agent 就是一个有向图。关键之处在于：图里允许循环——这正是 Agent 反复推理、执行、再推理的本质。

这个图和 ReAct 循环看起来很像，但它是显式定义的。你可以在这个图里再加入分支、并行、人工审批、子图调用，而不需要重写主循环。

2. LangGraph 的四个核心抽象

LangGraph 的 API 非常克制，核心只有四个概念：

2.1 State（状态）

State 是图中流动的数据容器。它通常用 TypedDict 或 Pydantic 定义，包含 Agent 在整个执行过程中需要维护和传递的全部信息。

注意 Annotated[list, operator.add] 这个写法。它告诉 LangGraph：这个字段在多分支并行执行后，应该通过 operator.add（追加）合并，而不是直接覆盖。这类似于 PostgreSQL 里多个并行 worker 各自产生结果后汇总。

2.2 Node（节点）

节点是一个函数，接收当前 State，返回对 State 的更新。节点里可以调用 LLM、执行工具、查询数据库、调用外部 API，甚至启动另一个子图。

每个节点都是“纯函数”风格：输入 state，输出 state 的增量更新。这种设计让节点很容易被单元测试、复用和组合。

2.3 Edge（边）

边定义了节点之间的流转关系。LangGraph 支持两种边：

  • 普通边：graph.add_edge("node_a", "node_b")，固定从 A 到 B。
  • 条件边：graph.add_conditional_edges("node_a", router)，根据当前状态动态决定下一步。

3. LangGraph 执行模型：与 Airflow / Temporal 的对比

作为后端工程师，你很可能用过工作流引擎。LangGraph 和它们在设计理念上有相似之处，也有重要区别：

维度 Airflow / Temporal LangGraph
定义方式 DAG 定义任务依赖 StateGraph 定义状态和转移
节点内容 通常是独立脚本 / 函数 通常是 LLM 调用 + 工具执行
决策来源 由调度器按依赖执行 由 LLM 或规则函数动态决定
循环支持 Airflow 原生 DAG 无循环；Temporal 可写循环代码 原生支持循环边
状态持久化 依赖外部 DB / 事件存储 内置 checkpointer，支持内存 / Postgres / Redis
人工审批 需额外实现传感器或外部任务 内置 interrupt 节点
适用场景 定时 ETL、微服务编排 Agent 推理—执行循环、对话系统

一个直观的类比：Airflow 适合“今天凌晨 2 点跑报表”，LangGraph 适合“用户问了一个问题，Agent 要动态决定查什么、怎么查、查多久”。

4. 状态合并与并行：LangGraph 的“并发控制”

LangGraph 最强大的特性之一是支持并行节点。当你调用 builder.add_edge("start", ["node_a", "node_b"]) 时，LangGraph 会同时执行 A 和 B，然后在汇合点自动合并它们对 State 的更新。

但并行带来一个经典问题：如果两个节点都更新了同一个字段，以谁为准？LangGraph 的解决方案是Reducer 函数。通过在 State 定义里指定 Annotated[field_type, reducer]，你可以控制合并行为：

  • operator.add：追加，适合 messages、logs。
  • lambda x, y: y：后者覆盖前者，适合标量字段。
  • 自定义 reducer：例如合并两个字典、取最大值等。

这很像 PostgreSQL 的聚合函数：多个并行 worker 各自产生部分结果，最后通过 SUM、MAX 或自定义聚合汇总。

5. 持久化与断点续跑：生产 Agent 的必备能力

一个生产级 Agent 必须具备持久化状态的能力。原因很现实：

  • LLM 调用可能失败或超时。
  • 人工审批节点可能需要等待数小时。
  • 你需要审计 Agent 的完整执行路径。

LangGraph 通过 checkpointer 实现持久化。最简单的内存版：

如果需要跨进程/跨服务恢复状态，可以使用 Postgres 或 Redis 实现的 checkpointer。它的语义非常清晰：每个 thread_id 对应一个独立的状态快照序列，你可以随时 graph.get_state(config) 查看历史，也可以用 graph.update_state(config, {...}) 手动注入状态。

对后端工程师来说，这就是把 Agent 的“会话状态”存进了数据库，而不是存在一次性的内存变量里。

🔗 后端桥接（3 分钟 PG 类比）

LangGraph 的抽象和后端工程之间有大量精确对应关系。理解这些对应关系，能让你更快把 LangGraph 纳入已有的系统架构思维。

LangGraph 概念 PostgreSQL / 后端类比 解释
State 事务上下文 / 会话级临时表 保存跨步骤的中间结果，整个执行周期可访问
Node 存储过程或微服务中的一个 handler 接收输入、执行逻辑、返回输出
Edge 控制流语句 / 消息路由 决定下一步执行哪个节点
Conditional Edge CASE WHEN / 策略模式 根据当前状态动态选择分支
Cycle LOOP / WHILE / 重试循环 让 Agent 能够多轮推理和执行
Reducer SQL 聚合函数（SUM/MAX/自定义聚合） 合并并行节点对同一字段的更新
Checkpointer 事务日志 / WAL / 审计表 持久化状态，支持回滚和断点续跑
Thread ID 会话 ID / 工单号 唯一标识一次完整的执行会话
Interrupt 人工审批工作流中的“挂起”节点 暂停执行，等待外部事件触发继续

一个特别贴切的类比：LangGraph 的 StateGraph 就像 PostgreSQL 的执行计划树。

PostgreSQL 优化器会把一条 SQL 解析成一棵由节点（Seq Scan、Index Scan、Hash Join、Aggregate）组成的计划树。每个节点接收子节点的输出，处理后返回给父节点。计划树可以包含循环（例如 Nested Loop），也可以并行执行（Parallel Seq Scan）。

LangGraph 的图也是一样：节点是计算单元，边是数据流，循环和并行都被显式表达。区别在于 PostgreSQL 的计划树由优化器基于统计信息生成，而 LangGraph 的图由开发者定义，节点内部可以调用 LLM 做动态决策。

另一个类比：Checkpointer 就像 PostgreSQL 的 WAL（Write-Ahead Log）。每次状态变更都被记录，系统崩溃后可以从最近一个检查点恢复，而不是从头开始执行。对于长周期、需要人工审批的 Agent 任务来说，这是从“玩具”走向“生产”的分水岭。

📰 技术雷达

行业动态

  • LangGraph 0.2 / 0.3 演进：LangGraph 在 2025 年持续迭代，引入了更简洁的 StateGraph API、改进的 checkpointer 接口以及对长线程（long-running thread）更好的支持。LangGraph Cloud 和 LangGraph Studio 的推出，让 Agent 的调试和部署更接近传统后端服务的可观测性体验。
  • LangGraph Studio：一个可视化 Agent 执行流的工具，可以查看每一步的状态快照、消息历史和分支路径。对于习惯了 Grafana / Jaeger 的后端工程师来说，这种可观测性是生产落地的前提。
  • Human-in-the-loop 标准化：越来越多的企业级 Agent 要求“人在回路”能力，特别是在金融、医疗、数据库变更等高风险场景。LangGraph 的 interrupt 机制正在成为这一领域的参考实现。
  • MCP（Model Context Protocol）与 LangGraph 的整合：通过 MCP Server 把数据库、文件系统、API 等工具标准化暴露出来，LangGraph 负责编排这些工具的执行流。这种“标准工具 + 灵活编排”的分层架构，很可能是未来 Agent 系统的主流形态。

论文推荐

  • LangGraph: Building Stateful, Multi-Agent Applications with LLMs（LangChain 团队技术博客与文档）：系统介绍了 StateGraph 的设计理念，包括状态合并、持久化、人工审批等核心机制。
  • ReAct: Synergizing Reasoning and Acting in Language Models（Yao et al., 2022）：LangGraph 里很多节点设计都延续了 ReAct 的推理—行动循环思想。
  • LLM Powered Autonomous Agents（Lil’Log, 2023）：一篇高引用的综述，从宏观视角理解 Agent 的规划、记忆、工具使用与多 Agent 协作。
  • Workflows for Controlling Generative AI（多个工业界实践报告，2024-2025）：讨论在真实业务中如何用状态机和工作流引擎管理 LLM 的非确定性输出。

开源项目

  • LangGraph（github.com/langchain-ai/langgraph）：构建有状态、多 Agent 应用的核心框架，支持 Python 和 JavaScript。
  • LangGraph Cloud（langchain.com/langgraph/cloud）：托管式 LangGraph 运行环境，提供持久化、流式输出、Human-in-the-loop 等企业级能力。
  • AutoGen（github.com/microsoft/autogen）：微软的多 Agent 对话框架，适合角色扮演式的 Agent 团队协作。
  • CrewAI（github.com/joaomdmoura/crewai）：面向角色的多 Agent 编排框架，可以用类似 LangGraph 的思路定义任务流。
  • Temporal（github.com/temporalio/temporal）：如果你已经在后端使用 Temporal 编排工作流，可以思考如何把 LLM 决策节点嵌入 Temporal 的 workflow 中，与 LangGraph 形成互补。

今日小结

今天我们完成了 Agent Orchestration 的第四块拼图：

  • LangGraph 把 Agent 从线性循环升级为显式状态图，让分支、并行、循环、人工审批都能被清晰定义。
  • State、Node、Edge、Reducer、Checkpointer 是五个核心抽象，分别对应后端工程师熟悉的状态上下文、处理函数、控制流、聚合函数和持久化日志。
  • LangGraph 不是替代 LLM，而是更好地编排 LLM：它让 LLM 的“不确定性”被限制在节点内部，而节点之间的流转是确定、可观测、可审计的。

对于后端工程师，记住这三点就够了：

  • State ≈ 事务上下文 + 临时表：跨步骤共享数据。
  • Node ≈ Handler / 存储过程：封装具体计算。
  • Graph ≈ 工作流引擎：编排执行顺序、分支、循环和持久化。

明天我们将继续 Agent Orchestration 的下一环：多 Agent 系统（Multi-Agent）——当单个 Agent 无法完成复杂任务时，如何让多个 Agent 分工协作、互相调用。
