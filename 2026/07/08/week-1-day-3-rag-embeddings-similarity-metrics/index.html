从向量到语义：Embedding如何桥接文本与检索

🚀 核心洞察（2分钟）

如果你做过后端或 PostgreSQL，应该对“索引决定查询天花板”这句话有肌肉记忆：B-tree 让等值查询从 O(n) 降到 O(log n)，GIN 让全文检索变得可用，BRIN 让时序数据扫描成本骤降。进入大模型时代，Embedding 就是把这种“结构化索引”的能力延伸到语义空间的关键技术。它把一段文本、一张图片甚至一段代码，压缩成一个低维稠密向量，让机器可以用距离来度量“意思有多近”。

对 PG/Backend 工程师来说，RAG 系统的检索质量并不首先取决于用了多大的 LLM，而是取决于两件事：第一，Embedding 模型能否把语义相似的文本映射到相邻的向量；第二，相似度度量是否准确地表达了这种相邻关系。选错了 Embedding 模型，就像给字符串列建了 Hash 索引却要做 LIKE '%keyword%' 查询——语法上跑得通，效果上全跑偏。选错了相似度度量，就像用了不合适的操作符去走索引，召回结果会系统性偏差。

昨天的文章已经聊了 Chunking 如何决定“切多少、怎么切”。今天我们把镜头对准 Chunk 进入向量库之前的最后一道关卡：Embedding 与相似度。核心结论可以一句话概括：先让“意思相近”这件事被正确地度量和索引，再谈 Prompt 工程、重排策略和模型选择。

🧠 核心概念（10分钟）

1. 稠密向量 vs 稀疏向量

文本进入计算机的第一种表示通常是离散的：一个词对应一个编号，一个文档对应一个词袋。稀疏向量的典型代表是 TF-IDF 和 BM25。它们把文档表示成一个高维但大部分为零的向量，每一维对应词表里的一个词，权重表示该词在文档中的重要性。优点是解释性强，对精确匹配友好；缺点是天然无法捕捉同义词、语义改写和上下文含义。

稠密向量（Dense Embedding）则完全不同。它通常只有 384、768、1024 或 3072 维，但每一维都有实际数值。这些数值没有人类可直接解读的含义，向量之间的距离却能刻画语义关系。稠密向量的强项是召回语义相关的结果，即使关键词并不重叠。

维度 稀疏向量（TF-IDF / BM25） 稠密向量（Embedding）
向量维度 词表大小（万级甚至百万级） 384 / 768 / 1024 / 3072
可解释性 每维对应一个词，直观 每维无显式含义
同义词/改写 无法处理 天然接近
长尾词/新词 容易过拟合或零命中 依赖模型泛化能力
存储与索引 倒排索引高度可压缩 需专用向量数据库或扩展
典型场景 关键词检索、合规匹配 语义检索、RAG 召回

生产环境里，两者的边界正在模糊。以 BGE-M3 为代表的模型可以同时输出稠密向量和稀疏向量，再用一个权重把两者的分数融合起来。这就好比 PostgreSQL 里把 B-tree 等值查询和 GIN 全文检索 union 起来：既保留精确匹配的可控性，又获得语义召回的泛化性。

2. 主流嵌入模型与选型

2026 年的 Embedding 模型百花齐放，但选型逻辑和后端选数据库索引非常相似：没有绝对最强，只有最贴合业务。下面是常见模型的定位与取舍。

模型 维度 语言/场景 关键特点
OpenAI text-embedding-3-small 1536 多语言 成本低、API 即插即用，支持 dimensions 参数截断
OpenAI text-embedding-3-large 3072 多语言 效果稳定，但价格与延迟都更高
Cohere Embed v3/v4 1024 多语言 支持 binary/int8 量化，对多语言长文档友好
BGE-M3 (BAAI) 1024 100+ 语言 同时输出稠密+稀疏+多向量，开源可自部署
BGE-large-zh-v1.5 1024 中文 中文场景经典选择，512 token 上限
E5 (Microsoft) 768/1024 英文为主 基于监督对比学习，检索任务表现强
GTE (Alibaba) 768/1024 中英文 在中文长文本检索上有不错性价比
Jina Embeddings v3 1024 多语言 支持 8k 上下文，API/本地均可

选模型时要问自己四个问题：

  1. 数据语言是什么？ 中文文档优先用 BGE-M3、BGE-large-zh、GTE 或 Qwen3-Embedding；英文文档可选范围更广，E5、GTE、OpenAI 都不错。
  2. 平均文档长度是多少？ 模型有最大 token 限制，超出会被截断。长文档需要考虑上下文窗口更大的模型，或者先做更细粒度的 Chunking。
  3. 对延迟和成本有多敏感？ API 模型按 token 计费，自部署开源模型需要 GPU/CPU 资源。日均百万级文档时，自部署通常更便宜。
  4. 向量是否已经归一化？ 这会直接影响你后面选余弦还是点积。sentence-transformers 系列大多已经做了 L2 归一化，OpenAI 的 text-embedding-3 默认不归一化。

3. 相似度度量：余弦、点积与欧氏距离

拿到两个向量后，怎么判断它们“像不像”？生产环境里最常用的有三种度量方式，理解它们的物理意义比盲目调参更重要。

余弦相似度（Cosine Similarity） 只看方向，不看长度：

它的取值范围在 -1 到 1 之间，语义检索通常落在 0.6 到 0.95 之间。余弦适合模型输出向量模长不一致的场景，例如 OpenAI 的 text-embedding-3 系列。对这类向量，如果直接用点积，长文本会因为模长更大而获得不公平的优势。

点积（Dot Product） 同时考虑方向和模长：

如果 Embedding 模型在训练时已经做了 L2 归一化，那么点积和余弦是等价的，因为：

但在某些场景下，长文档的向量模长更大，点积会天然偏向长文本。这可能正是你想要的——比如你想让信息更完整的文档排在前面。也可能不是你想要的——比如你想找的是一句精确的定义，而不是一篇长篇大论。

欧氏距离（Euclidean Distance） 强调向量终点之间的绝对距离：

当向量已经归一化到单位球面上时，欧氏距离和余弦相似度是单调关系，可以互换。实际工程中，优先用余弦；如果向量已经 L2 归一化，点积计算效率更高，因为省掉了两次除法。

4. 向量归一化、维度灾难与聚类边界

归一化 是最容易被忽略但影响巨大的细节。L2 归一化把一个向量缩放到单位长度：

归一化后，点积直接等于余弦，向量数据库里很多索引也只支持固定距离函数。例如 pgvector 的 vector_cosine_ops 就是基于余弦距离的运算符族。如果你插入了未归一化的向量却走了 cosine 索引，结果在数学上仍然正确，但会多计算一次模长；如果你在应用层自己做了归一化，再使用点积索引，通常能换来更快的查询速度。

维度灾难（Curse of Dimensionality） 是高维向量检索的隐形敌人。随着维度增加，数据点之间的距离对比度会下降，所有点看起来都差不多远。这会导致近似最近邻（ANN）索引的召回率下降。缓解方法包括：

  • 选择合适维度的模型，不盲目追求高维；
  • 使用 Matryoshka 表示学习，训练时让模型学会“可截断”的向量，用 256 维甚至 128 维也能保持较高精度；
  • 在索引层面使用 HNSW、IVFFlat 等 ANN 算法，用可接受的精度损失换取数量级的速度提升。

聚类边界 是语义检索的另一个陷阱。Embedding 空间往往不是均匀分布的，而是按主题聚成簇。查询向量如果落在两个簇的边界上，最近邻可能会“跳过”真正相关的文档，落在同一簇内但语义偏差的结果上。这就像数据库查询里，按一个列排序却漏掉了跨分区的相关行。解决办法包括 hybrid search、rerank，以及针对性地微调 Embedding。

🔗 后端桥接（3分钟）

把 Embedding 映射回你熟悉的 PG/Backend 世界，会有三条非常清晰的类比。

第一，Embedding 是“语义 B+ 树”。 传统数据库用 B+ 树把 WHERE id = ? 的等值查询从 O(n) 降到 O(log n)；GIN 索引把 WHERE text @@ to_tsquery(...) 的全文检索变得可用。Embedding 则是把“语义相似”这种原本无法索引的查询，通过学习到的向量映射，变成在向量空间里的最近邻搜索。

第二，相似度度量是索引的“操作符”。 在 PostgreSQL 里，你会根据查询类型选择 =、<@、@@ 或 <->。在向量检索里，你要根据向量特性选择余弦、点积或欧氏距离。选错了操作符，索引仍然会被使用，但结果会系统性偏差。

第三，ANN 索引是“带精度的分区扫描”。 HNSW 和 IVFFlat 都不是精确 kNN，而是用可接受的召回率损失换取数量级的速度提升。它们就像数据库里把大表按 hash 分区、再在每个分区内做局部扫描。pgvector 让你可以直接在 PostgreSQL 里体验这套机制。

📰 技术雷达：最新AI动态

Embedding 领域在 2025-2026 年有几个值得持续跟踪的方向：

  • MTEB 排行榜仍是选型参考，但不是唯一标准。榜单上的高分模型未必在你的业务数据上表现最好，建议用自己的 query-doc 对做召回率 benchmark。排行榜地址可参考 Hugging Face MTEB Leaderboard。
  • Matryoshka 表示学习正在普及。这种训练目标让模型输出“可截断”的向量，你可以在推理时只取前 256、128 甚至 64 维，显著降低存储和计算成本，而精度损失可控。OpenAI text-embedding-3 的 dimensions 参数就是这一思想的工程化。
  • 多模态 Embedding 进入实用阶段。除了文本，CLIP、Cohere 的多模态模型以及 Google 的 Gemini Embedding 已经支持图像、视频甚至 PDF 的统一向量表示，跨模态检索正在成为 RAG 的新战场。
  • Late Interaction 与 ColBERT。与单向量 Embedding 不同，ColBERT 类模型为每个 token 生成一个向量，通过延迟交互计算细粒度相关性，在需要精确匹配短语的检索任务中表现优异，但存储和计算成本更高。
  • 领域微调仍是最后一公里。通用 Embedding 在垂直领域往往不如一个轻量微调模型。用对比学习（InfoNCE / Triplet Loss）在自己的 query-positive-negative 三元组上微调，通常能换来 10%-30% 的召回率提升。

小结

Embedding 和相似度度量是 RAG 检索的底座。作为 PG/Backend 背景的工程师，你可以把它理解为一门新的“索引技术”：Embedding 模型负责把文本映射成可索引的向量，相似度度量定义了索引的操作符，向量数据库里的 ANN 索引则决定了查询成本与召回率之间的 trade-off。

选模型时不要只看 MTEB 分数，要结合语言、上下文长度、成本、是否归一化等因素。做检索时要清楚自己用的是余弦、点积还是欧氏距离，并理解它们对向量模长的不同态度。最后，一定要用真实数据做 benchmark，因为 leaderboard 上的冠军，未必是你业务里的最优解。
