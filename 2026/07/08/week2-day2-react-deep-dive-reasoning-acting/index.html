ReAct 深度解析：当 LLM 学会“先想后做”

核心洞察（2 分钟速览）

昨天我们聊到了 Function Calling——它让大语言模型（LLM）从“只会说话”变成了“可以打电话”的系统。但仅有电话簿是不够的：一个真正有用的 AI Agent，必须像一名经验丰富的 DBA 那样，在面对复杂问题时能够 先思考、再行动、观察结果、再调整。

想象一个真实的排查场景：线上告警“订单查询接口 RT 飙升”。一个优秀的后端工程师不会立刻改索引，而是会按下面的循环推进：

  1. 思考（Thought）：”最近有没有发布变更？慢查询日志里有没有异常？”
  2. 行动（Action）：打开 Grafana 看 QPS / P99，再查 pg_stat_statements。
  3. 观察（Observation）：发现某条 SELECT * FROM orders WHERE user_id = $1 的调用次数暴涨。
  4. 再思考：”user_id 上有没有索引？表有多大？是不是走了全表扫描？”
  5. 再行动：查 pg_indexes、跑 EXPLAIN ANALYZE。
  6. ……直到定位根因。

ReAct（Reasoning + Acting）正是把这个人类工程师的“推理—行动”循环形式化地搬到了 LLM 上。它要求模型在每一步都显式地输出：

  • Thought：我现在知道什么、下一步该做什么、为什么。
  • Action：我要调用哪个工具，参数是什么。
  • Observation：工具返回了什么新信息。

这和 Function Calling 的区别在于：Function Calling 只定义了“能打什么电话”，而 ReAct 定义了“打完电话之后如何根据反馈继续思考”。对于 PostgreSQL 后端工程师来说，它就像把一次性的 SELECT 升级成了一个带循环、带分支、带回滚的复杂运维脚本。

核心概念（10 分钟深入）

1. 为什么需要 ReAct？

在 ReAct 出现之前，提升 LLM 能力的两大主流路线分别是：

  • Chain-of-Thought（CoT）：让模型把推理过程显式写出来，例如“先算 12 × 13，再除以 4……”。它提升了复杂推理能力，但模型只能“空想”，不能查询外部世界。
  • 工具调用（Tool Use / Action）：让模型可以调用搜索引擎、数据库、计算器等外部工具，但模型往往缺乏对“为什么要调用这个工具”的显式规划，容易在多步任务中迷失。

ReAct 把两者交织在一起，形成了一个 推理指导行动、行动反哺推理 的闭环。论文实验表明，这种结合不仅让模型在 HotpotQA 等问答任务上表现更好，也大幅降低了“幻觉”——因为模型必须根据工具返回的真实观察来修正推理，而不是凭空编造。

范式 是否有显式推理 是否使用外部工具 典型场景 主要短板
标准 Prompt 否 否 简单问答 无法做多步推理
CoT 是 否 数学、逻辑题 无外部事实校验，易幻觉
纯 Action 否 是 查天气、调用 API 缺少全局规划，易重复/死循环
ReAct 是 是 复杂 Agent 任务 对 Prompt 和工具设计要求高
Plan-and-Execute 先规划再执行 是 长程任务 计划僵化，遇到异常需重规划
Reflexion 是 + 自我反思 是 编程、多轮优化 需要额外反馈信号

  1. Thought 是对当前状态的“元认知”。好的 Thought 会包含：
    • 对问题的拆解（sub-goal）
    • 对上一步观察的解读
    • 下一步行动的理由
  2. Action 是结构化的工具调用。它通常写成 tool_name[arg1=value1, arg2=value2]，或用 JSON Schema 通过 Function Calling 输出。
  3. Observation 是环境对 Action 的反馈。它必须由外部系统真实返回，不能由模型自己编。

这种把“心里想的”和“手上做的”分开的做法，带来了三个好处：

  • 可解释性：你能看到模型为什么出错。
  • 可调试性：如果 Action 参数错了，可以单独修复工具或 Prompt。
  • 可复用性：同样的 Thought/Action 格式可以迁移到不同任务。

3. ReAct 的架构图

记忆（Memory）是这个循环的“临时表”。每一次 Thought、Action、Observation 都会被追加到上下文里，让 LLM 在下一步能看到完整的历史。记忆设计直接决定了 Agent 能走多远：

  • 短记忆：最近 N 轮对话，适合简单任务。
  • 长记忆：完整的执行 trace，适合审计和错误回溯。
  • 结构化记忆：把关键结论抽取成键值对（例如 当前怀疑对象: orders.user_id），避免上下文过长。

5. ReAct 的常见失败模式与应对

ReAct 不是银弹。在生产环境里，你会遇到这些问题：

失败模式 表现 后端工程师视角的解法
推理幻觉 Thought 里说“我已经查到表名”，但其实还没查 在 Prompt 里强制要求“没有 Observation 不能下结论”；加校验器
行动死循环 反复调用同一个工具，参数不变 设置 max_steps；记录已执行 action，Prompt 里禁止重复
Observation 噪声 工具返回大量无关信息，模型被淹没 对 Observation 做摘要/结构化；像 SQL 一样只返回必要列
工具参数错误 JSON 参数缺字段或类型不对 用 JSON Schema + 服务端校验，像 PG 的类型系统一样严格
长上下文遗忘 多轮后模型忘记最初目标 在 Memory 里保留任务目标；必要时做总结压缩

后端桥接（3 分钟 PG 类比）

把 ReAct 映射到 PostgreSQL / 后端世界，你会发现几乎每个概念都似曾相识：

AI Agent / ReAct PostgreSQL / 后端类比 解释
Thought（推理） EXPLAIN 生成的执行计划 先分析“要怎么干”，再真正执行
Action（行动） 具体的执行节点（Seq Scan、Index Scan、Nested Loop） 根据计划选择并执行某个操作
Observation（观察） EXPLAIN ANALYZE 返回的实际行数、耗时 真实执行结果反过来验证计划是否最优
Memory（记忆） 会话级临时表 / work_mem 在多步之间保存中间状态
Tool Registry pg_proc 系统表 注册可用函数及其签名
max_steps statement_timeout 防止无限执行的安全阀
Reflection（反思） 查询计划缓存失效与重新规划 发现计划不准时，基于统计信息重新生成计划
ReAct 循环 BEGIN ... SAVEPOINT ... ROLLBACK TO ... COMMIT 某步失败时回滚到检查点，换策略继续

一个特别有趣的类比：ReAct 里的 Thought 就像查询优化器。PostgreSQL 的优化器会基于统计信息生成多个候选计划，并估算成本，然后选择最优路径。ReAct 里的 LLM 也是在每一步基于当前观察，评估“下一步做什么成本最低、收益最大”。区别在于 PG 优化器用的是成本模型，LLM 用的是预训练知识 + 上下文推理。

另一个类比：Observation 的格式必须稳定。如果你给 PG 的函数返回一个不稳定的数据类型，调用方会崩溃；同样，如果 Agent 的工具返回格式时而是 Markdown、时而是 JSON，LLM 的下一步推理就会乱套。因此，定义工具输出 Schema 和定义数据库返回类型一样重要。

技术雷达

行业动态

  • OpenAI Agents SDK & Responses API：OpenAI 在 2025 年推出了面向 Agent 的 SDK，内置 web_search、file_search、computer_use 等工具，并把 ReAct 风格的循环封装成 Agent 类。它把“推理—行动—观察”的样板代码进一步抽象，让后端工程师可以更关注工具实现而不是循环控制。
  • Model Context Protocol（MCP）：Anthropic 推动的开放协议，试图把“工具描述、调用、返回”标准化。对于 PostgreSQL 后端来说，这就像给 AI Agent 定义了一套统一的 SQL/REST 接口规范，未来可能用 MCP Server 直接暴露数据库元数据和查询工具。
  • LangGraph 的 StateGraph：LangChain 团队把 ReAct 从线性循环升级为有向图。节点可以是 Thought、Action、Human-in-the-loop；边可以是条件分支、并行路由、循环回退。对于熟悉 Airflow / Temporal 的后端工程师，这种图结构更容易扩展和审计。

论文推荐

  • ReAct: Synergizing Reasoning and Acting in Language Models（Yao et al., 2022）：ReAct 范式的奠基论文，详细比较了 ReAct、CoT、Act-only 在问答、决策任务上的表现。见 arXiv:2210.03629。
  • Reflexion: Self-Reflective Agents with Verbal Reinforcement Learning（Shinn et al., 2023）：在 ReAct 基础上加入“失败后的语言反思”，让 Agent 能根据错误反馈改进策略。
  • Language Agent Tree Search Unifies Reasoning, Acting, and Planning（Zhou et al., 2023，LATS）：把 ReAct 的单一路径扩展成树搜索，用蒙特卡洛树搜索（MCTS）探索多条推理—行动路径，适合高价值但高成本的复杂任务。

开源项目

  • LangGraph（github.com/langchain-ai/langgraph）：把 ReAct 循环建模为状态图，支持持久化、人工审批、并行分支，是构建生产级 Agent 的首选框架之一。
  • Microsoft AutoGen（github.com/microsoft/autogen）：多 Agent 对话编排框架，支持 ReAct 风格的多轮工具调用和代码执行，适合“分析师 + 执行者 + 审核者”的团队协作模式。
  • CrewAI（github.com/joaomdmoura/crewai）：面向角色的多 Agent 框架，可以用 ReAct 模式定义每个角色的工作流，快速搭建研究、内容生成、运维诊断等场景。
  • smolagents（huggingface.co/smolagents）：Hugging Face 推出的极简 Agent 库，强调“代码即行动”（Code Agent），把 Action 从 JSON 函数调用扩展为 Python 代码片段，进一步模糊了“推理”和“执行”的边界。

今日小结

ReAct 让 LLM 从“单次回答”进化到“多轮推理—行动”循环。它的核心不是更复杂的模型，而是 显式地把思考过程、工具调用和环境观察结构化，让 Agent 像一名资深 DBA 一样步步为营。

对于后端工程师，记住这三个对应关系就够了：

  • Thought ≈ 执行计划 / EXPLAIN：先想清楚再动手。
  • Action ≈ SQL/函数调用：根据计划执行具体操作。
  • Observation ≈ 执行结果 / ANALYZE：用真实反馈修正下一步。

明天我们将继续 Agent Orchestration 的下一环：Plan-and-Execute 与 Reflection——当任务越来越长，Agent 该如何先制定全局计划、再在失败时自我反思和重规划。
