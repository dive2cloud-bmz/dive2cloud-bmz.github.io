Plan-and-Execute 与 Reflection：让 Agent 学会‘先定计划、再复盘纠错’

🚀 核心洞察（2 分钟速览）

前两天的学习中，我们见证了 Function Calling 如何让 LLM 拥有“双手”，也见证了 ReAct 如何让 LLM 在每一步都“先想后做、观察反馈、再调整”。但当你把 Agent 放到更复杂的真实任务里时，会迅速遇到一个天花板：ReAct 是“短视”的。

想象你要完成一次大型 PostgreSQL 分库分表迁移：

  1. 评估当前表结构和数据量。
  2. 设计新库的分片键和索引策略。
  3. 编写双写逻辑和一致性校验脚本。
  4. 制定灰度切换和回滚方案。
  5. 执行迁移并监控延迟与数据一致性。

如果让纯 ReAct Agent 来做，它很可能在第 3 步才发现第 1 步的评估不够充分，然后被迫“走一步看一步”地反复回退。就像一个没有预先画好架构图的工程师，边写代码边重构，效率极低。

Plan-and-Execute 要解决的就是这个问题：它让 Agent 先制定全局计划，再按计划执行，而不是每一步都临时决定下一步。而 Reflection（反思/自省）则让 Agent 在执行计划的过程中，不断检查自己的计划是否合理、执行是否到位、结果是否达标，一旦发现偏差就重新规划。

用后端工程师熟悉的话来概括：

  • ReAct ≈ 一个灵活的 while 循环，适合短链路、工具调用密集的任务。
  • Plan-and-Execute ≈ 一份详细的 SOP/工单/项目计划，适合多步骤、长周期、需要全局协调的任务。
  • Reflection ≈ Code Review + 线上复盘会，让 Agent 自己给自己挑错并改进。

今天我们要把这三者串起来，构建一个既有全局规划、又能自我纠错的 Agent。

这种“贪心”策略在以下场景会出问题：

场景 ReAct 的问题 Plan-and-Execute 的优势
多步骤迁移 早期选择的分片键可能让后期索引设计困难 先全局评估，再一次性制定方案
数据分析报告 反复查询不同表，最终发现维度不统一 先确定指标口径和表关联，再分批查询

并不是说 ReAct 不好，而是它的设计假设是“环境反馈密集、任务步数有限”。当任务需要提前规避后续风险时，就需要显式的规划层。

2. Plan-and-Execute：把 Agent 变成“项目经理”

Plan-and-Execute 架构最早由 LangChain 团队系统化提出，其核心思想是把 Agent 拆成两个角色：

  • Planner（规划器）：接收用户目标，输出一个可执行的计划列表。
  • Executor（执行器）：按照计划逐项执行，必要时调用工具。

它的标准执行流程是：

  1. Planning：把目标拆解成若干子任务（Sub-tasks）。
  2. Execution：逐个完成子任务，可以用 ReAct、Function Calling 或纯代码实现。
  3. Re-planning：如果执行中发现原计划不可行，Planner 重新生成后续计划。

这种分层架构和后端开发中的 编排系统 非常相似。比如 Apache DolphinScheduler 或 Temporal：你先定义 DAG（工作流），然后调度器按依赖执行每个节点，失败时支持重跑、跳过或重新编排。

3. Reflection：给 Agent 装上“自省能力”

Reflection 是一种让 Agent 对自身行为进行评价和修正的机制。它通常发生在三个时机：

  • 行动后反思（Action-level Reflection）：每次工具调用后，检查返回是否满足预期。
  • 子任务后反思（Task-level Reflection）：完成一个子任务后，评估是否达成目标。
  • 全局反思（Global Reflection）：整个计划执行完毕后，总结成功经验和失败教训。

这里的关键设计决策包括：

  • 计划粒度：太粗则失去指导意义，太细则 Planner 负担过重。一般建议每个子任务能在 1-3 次工具调用内完成。
  • 重规划触发条件：可以是执行失败、结果置信度低、用户反馈、或者主动定期重评估。
  • 反思形式：可以是简单的 Pass/Fail，也可以是结构化的评分 + 改进建议。
  • 记忆持久化：短期记忆保存在当前对话上下文，长期记忆可以写入向量数据库或键值存储。

5. 三种范式的对比

范式 核心思想 适合任务 主要短板
ReAct 每步都推理+行动+观察 工具密集、步数少的任务 长程任务容易局部最优、反复回退
Plan-and-Execute 先全局规划，再分步执行 多步骤、可预先拆解的任务 计划僵化，遇到意外需重规划
Plan-and-Execute + Reflection 规划+执行+反思+重规划 复杂、动态、长周期任务 实现复杂，延迟和 Token 成本高

一句话总结：ReAct 像即兴演讲，Plan-and-Execute 像按稿演讲，Reflection 像演讲后的复盘和改稿。

🔗 后端桥接（3 分钟 PG 类比）

作为 PostgreSQL / 后端工程师，你已经在日常工作中大量使用过 Plan-and-Execute + Reflection 的思想，只是没有这样命名。

AI Agent 概念 PostgreSQL / 后端类比 解释
Planner 数据库迁移前的 方案设计文档 / 评审会 先拆解任务、评估风险、确定依赖，再动手执行
Executor 调度系统 / 工作流引擎（DolphinScheduler / Temporal / Airflow） 按 DAG 节点逐个执行，处理依赖和并发
计划步骤队列 消息队列 / 任务表（如 pending_jobs） 维护待执行步骤，支持入队、出队、重试
Re-planning 线上变更失败后的 回滚 + 重新评审 当原计划走不通时，暂停执行、修改方案再继续
Reflection Code Review + Postmortem 复盘 检查执行结果是否达标，总结经验写入文档
Memory Redis / PG 会话状态 / 审计日志表 保存中间结果和历史反思，供后续任务参考
Evaluator 单元测试 + 监控告警 用客观指标判断执行是否成功

一个特别贴切的类比：PostgreSQL 查询优化器本身就在做 Plan-and-Execute + Reflection。

  1. Planning：优化器基于统计信息生成多个候选执行计划，估算成本，选择最优计划（Planner）。
  2. Execution：执行器按照计划扫描索引、做 JOIN、聚合（Executor）。
  3. Reflection / Re-planning：如果运行时统计信息严重不准（例如 EXPLAIN ANALYZE 发现实际行数远多于估计），PostgreSQL 会重新收集统计信息、更新计划缓存，下一次生成更优计划。

再比如你做过的 数据库迁移：

  • 先写迁移方案文档（Planner）。
  • 按步骤执行：备份、建表、导数、双写、切流、校验（Executor）。
  • 每一步都检查监控指标，发现数据不一致就回滚并重做方案（Reflection + Re-planning）。
  • 把这次迁移的经验写成 SOP，下次类似迁移直接复用（Memory）。

你看，Plan-and-Execute + Reflection 并不是玄学，而是把人类工程师已经验证过的工作方法搬到了 Agent 上。

📰 技术雷达

行业动态

  • LangGraph 的 Plan-and-Execute 示例：LangChain 官方提供了 plan-and-execute 参考实现，展示了如何把 ReAct Executor 嵌入到更大的规划图中。对于熟悉工作流引擎的后端工程师来说，LangGraph 的 StateGraph 是最接近生产落地的 Agent 框架之一。
  • OpenAI 的 Structured Outputs：2024 年底 OpenAI 推出了更严格的结构化输出能力，让 Planner 生成 JSON 格式的计划变得更可靠。这意味着 Agent 的计划步骤可以被精确解析，而不再依赖脆弱的字符串匹配。
  • Anthropic 的 Model Context Protocol（MCP）：MCP 正在推动 Agent 工具生态标准化。未来一个 PostgreSQL MCP Server 可能直接暴露 describe_table、check_index、explain_query 等工具，Agent 只需按标准协议调用。
  • Google DeepMind 的 AlphaEvolve：将 LLM 作为进化算法的变异算子，用于发现更优的数学和算法解。这可以看作是 Plan-and-Execute + Reflection 在科学研究领域的极端形态——计划是候选解，执行是验证，反思是评估和选择。

论文推荐

  • Plan-and-Solve Prompting: Improving Zero-Shot Chain-of-Thought Reasoning by Large Language Models（Wang et al., 2023）：提出了“先计划再求解”的提示工程范式，是 Plan-and-Execute 在 Prompt 层面的先驱。
  • Reflexion: Self-Reflective Agents with Verbal Reinforcement Learning（Shinn et al., 2023）：系统化了 Reflection 机制，通过语言形式的自我反思提升 Agent 在多轮任务中的表现。见 arXiv:2303.11366。
  • Language Agent Tree Search Unifies Reasoning, Acting, and Planning（Zhou et al., 2024，LATS）：把 ReAct 扩展为树搜索，支持多条规划路径的探索和反思，适合高价值复杂决策。
  • Adaptive In-Context Learning for LLMs with Retrieval and Planning（2024-2025 多篇）：探讨如何让 Agent 在规划中动态检索外部知识，减少因知识缺失导致的计划失败。

开源项目

  • LangGraph（github.com/langchain-ai/langgraph）：把 Plan-and-Execute 建模为状态图，内置持久化、断点续跑、人工审批，是构建生产级 Agent 的核心框架。
  • AutoGen（github.com/microsoft/autogen）：微软开源的多 Agent 对话框架，支持规划器、执行器、评估器等多种角色协作。
  • CrewAI（github.com/joaomdmoura/crewai）：面向角色的多 Agent 编排框架，可以用 Plan-and-Execute 模式定义团队工作流。
  • MetaGPT（github.com/geekan/MetaGPT）：将软件开发流程 SOP 化，让多个 Agent 分别扮演产品经理、架构师、工程师、测试，适合复杂代码生成任务。
  • smolagents（huggingface.co/smolagents）：Hugging Face 的极简 Agent 库，支持 Code Agent 和 Tool Calling Agent，适合快速原型验证。

今日小结

今天我们完成了 Agent Orchestration 的第三块拼图：

  • Plan-and-Execute 让 Agent 从“走一步看一步”升级为“先定全局计划，再分步执行”。
  • Reflection 让 Agent 在执行过程中主动评估自己，发现偏差就重新规划。
  • 两者结合，Agent 才能胜任像数据库迁移、复杂数据分析、长程代码生成这样的真实工程任务。

对于后端工程师，记住这三个对应关系：

  • Planner ≈ 方案设计文档 / 评审会：先想清楚再动手。
  • Executor ≈ 调度系统 / DAG 工作流：按依赖执行每个步骤。
  • Reflection ≈ Code Review + Postmortem：失败不是终点，而是改进计划的输入。

明天我们将继续 Agent Orchestration 的下一环：LangGraph 基础——把 Agent 的规划和执行建模为状态图，让复杂 Agent 具备可视化、可持久化、可审计的工程能力。
