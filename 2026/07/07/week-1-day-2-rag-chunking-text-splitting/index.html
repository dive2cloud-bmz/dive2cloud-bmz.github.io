W1D2 RAG文本分块：切块大小如何决定检索天花板

🚀 核心洞察（2分钟）

如果你做过 PostgreSQL 或任何关系型数据库的调优，你一定听过一句话：“page size 不是越大越好，也不是越小越好，而是要匹配工作负载的访问模式。” 在 RAG 中，文本分块（Text Splitting / Chunking）扮演的正是这个角色。它决定了检索系统一次能拿到多少上下文，也决定了嵌入向量对语义的概括精度。

很多从后端转 AI 的工程师会下意识觉得：”把文档切得越碎，检索越精准。” 这和早年认为 “数据库索引字段越细越好” 的误区如出一辙。实际上， chunk 过小会导致单条上下文丢失主语和背景，LLM 拿到后根本没法回答；chunk 过大则会让向量被稀释，检索时把不相关的大段文本召回回来，既浪费 token 又降低答案质量。

我们不妨把一次 RAG 查询想象成一次数据库查询：用户的 question 是 SQL，向量检索是索引扫描，召回的 chunks 是命中的行，LLM 则是最终的聚合计算。如果 chunk 设计得不合理，就像表的数据分布和索引选择性不匹配——索引扫描返回了大量无关行，聚合阶段不得不做额外过滤，整体性能和质量都会下降。

核心结论：分块不是切得越碎越好，而是在语义完整性与检索粒度之间找平衡。好的分块策略能让 RAG 系统拥有更高的 “查询计划” 质量，直接决定回答的上限。

🧠 核心概念（10分钟）

1. 固定长度分块（Fixed-Length Chunking）

固定长度分块是最直观的策略：按字符数或 token 数把文本切成等长的小块，通常配合 overlap（重叠）来保留跨边界信息。它的核心参数是 chunk_size 和 chunk_overlap，前者决定每块最大长度，后者决定相邻块之间共享多少内容。

优点：实现简单、可预测、容易做并发和批量处理。因为每块长度固定，你可以很容易地估算向量库的存储成本和检索延迟。

缺点：完全无视语义边界，可能把一句话拦腰截断，也可能把两个无关的句子硬塞进同一个 chunk。在后端视角下，这有点像按字节强制切分日志文件，速度快但可读性差。更严重的是，如果问题恰好落在被截断的边界上，检索会同时漏掉两边的关键信息。

2. 递归字符分块（Recursive Character Text Splitting）

LangChain 的 RecursiveCharacterTextSplitter 是目前社区最常用的分块器。它维护一个分隔符优先级列表（如 \n\n、\n、 、空字符），先尝试按大粒度切分，如果某段还超过 chunk_size，再递归地用更细的分隔符继续切，直到所有 chunk 都满足长度限制。

这个策略像编译器里的递归下降解析：先按段落分，不行再按句子分，再不行按词分。它在 “保持结构” 和 “控制长度” 之间取得了不错的平衡，是生产环境中最稳妥的 baseline。对于中文文档，建议把 。、；、： 等标点也放进 separators，这样切出来的 chunk 边界会更自然。

不过它仍然是一种 “长度优先” 的策略：当文档某一段特别长时，即使语义上应该继续细分，它也会优先满足长度限制。因此在处理代码、表格、长列表时，仍可能出现边界不理想的情况。

3. 语义分块（Semantic Chunking）

语义分块的核心思想是：切分位置应该放在语义变化的地方。如果相邻两句话在向量空间中的距离突然变大，说明这里可能是一个主题切换点，适合作为切分边界。

一种常见做法是：先把文档按句子切分，然后滑动窗口计算相邻句子的嵌入相似度，当相似度低于阈值时进行切分。LangChain 的 SemanticChunker 已经把这套逻辑封装好了。

语义分块的优点是边界自然，召回的内容通常更完整。例如，一篇讲 “订单系统” 的文档，如果前一段讲创建订单、后一段讲退款流程，语义分块会自然地把它们分开。而固定长度分块很可能把这两段混在一个 chunk 里，导致向量表示被 “平均” 掉，检索时难以命中。

缺点是每次分块都要调用嵌入模型，成本高、延迟大，而且阈值选择对效果影响显著。阈值太低会导致 chunk 过大，阈值太高会导致 chunk 过碎。它更适合对质量要求高、文档量不大的场景，或者作为离线预处理步骤。

4. Agentic 动态分块（Agentic Dynamic Chunking）

这是更前沿的思路：不再用单一静态策略切分全部文档，而是让模型或规则引擎根据文档类型、问题模式、检索阶段动态选择分块方式。

例如：

  • 代码文档可能按函数或类切分，每个 chunk 是一个可独立理解的逻辑单元。
  • 产品说明书按章节切分，保留标题层级作为元数据。
  • FAQ 按问答对切分，确保问题和答案不被拆散。
  • 检索阶段也可以先用大粒度 chunk（如整节）做粗排，再用小粒度 chunk（如段落）做精排。

这种 “分层索引” 的思路与数据库中的二级索引非常相似。它不是一种具体的算法，而是一种工程理念：让分块策略适应数据，而不是让数据适应分块策略。

下面是一张四种策略的对比表，方便你快速选择：

策略 切分依据 优点 缺点 适用场景
固定长度 字符/ token 数 简单、快速、可预测 无视语义边界 原型验证、非结构化文本
递归字符 分隔符优先级 + 长度 兼顾结构与长度 仍可能截断长语义单元 通用 baseline、Markdown 文档
语义分块 向量相似度变化 边界自然、召回完整 成本高、阈值难调 高质量知识库、离线处理
Agentic 动态 文档类型 + 查询阶段 最贴合实际数据 实现复杂、需要规则维护 企业级知识库、多文档类型

🔗 后端桥接（3分钟）

作为有 PostgreSQL / Backend 背景的工程师，你可以把 RAG 的分块策略类比成熟悉的数据库概念。这种类比不是为了硬套概念，而是为了帮助你快速建立直觉，并在调优时有明确的抓手。

RAG 分块 数据库概念 对应影响
Chunk size PostgreSQL block_size / page size 决定一次 I/O 能读取多少有效信息
Overlap WAL / 预写日志的边界保留 防止跨页事务丢失上下文
向量嵌入 B-tree / GiST / GIN 索引 决定查询时如何定位候选行
语义分块 按语义域分区（partitioning） 把相关数据物理上放在一起，减少跨区扫描
Agentic 动态分块 查询优化器的 plan selection 根据查询类型选择不同的扫描路径
多粒度分块 聚簇索引 + 二级索引 粗粒度召回 + 细粒度精排

一个特别值得品的类比是 page size。PostgreSQL 默认 page size 是 8KB，这不是拍脑袋定的：太小会导致每个 tuple 的元数据开销占比升高，索引层级变深；太大则浪费缓存，单次 I/O 读到的无效字节变多。RAG 的 chunk size 同理。OpenAI 的 text-embedding-3 系列对长文本的嵌入效果会随长度增加而 “稀释”，而 LLM 的上下文窗口虽然越来越大，但过长的上下文会带来 “lost in the middle” 问题，即模型容易忽略中间内容。

另一个类比是 查询计划（Query Plan）。后端调优时会看 EXPLAIN ANALYZE，RAG 调优时也应该看 “检索-生成链路”：召回的 chunk 是否包含答案？Top-K 中无关 chunk 占比多少？答案是否被截断？这些指标就是 RAG 的 “执行计划”。一个好的 DBA 不会只看单次查询快慢，而是看整体工作负载；同样，一个好的 RAG 工程师也不会只看单次回答好坏，而是看整个检索策略对各类问题的平均表现。

还有一个容易被忽视的细节是 overlap。在后端系统中，WAL 和 checkpoint 的边界设计要保证事务的持久性和可恢复性；在 RAG 中，overlap 要保证跨 chunk 边界的语义不被切断。overlap 过小，关键信息可能被拆成两半；overlap 过大，不同 chunk 之间的冗余度升高，向量库体积膨胀。通常 overlap 取 chunk_size 的 10% 到 20% 是一个合理的起点。

🛠️ 微实战（5分钟）

目标：用 LangChain 实现 3 种分块器，对比同一长文档在不同策略下的检索命中率与答案完整性。

做什么

准备一篇约 2000 字的技术文档（可以是公司内部的 API 文档、设计文档或开源项目的 README），分别用以下三种策略切分并构建向量检索：

  1. 固定长度分块（CharacterTextSplitter）
  2. 递归字符分块（RecursiveCharacterTextSplitter）
  3. 语义分块（SemanticChunker）

建议选择结构相对清晰的 Markdown 文档，这样递归分块和语义分块的优势更容易体现出来。

怎么做

步骤 1：加载文档

步骤 2：定义三种分块器

步骤 3：切分并建立向量库

步骤 4：用同一批问题做检索对比

步骤 5：让 LLM 基于召回内容生成答案

验证标准

  1. Chunk 数量合理：三种策略的 chunk 数差异不应超过 50%。如果语义分块产生的 chunk 数只有固定分块的 1/3，说明阈值太激进，丢失了很多细节。
  2. Top-1 命中率：对每个问题，检查召回的第一条 chunk 是否包含可直接回答该问题的信息。建议至少 70% 的问题命中。
  3. 答案完整性：把 Top-3 chunk 拼成 prompt 让 LLM 回答，对比三种策略下答案是否完整、是否出现 “hallucination”（幻觉）。
  4. 边界干净度：抽样检查 chunk 边界，递归分块应尽量避免在句子中间截断；语义分块应在主题切换处断开。
  5. 成本与延迟：记录每种策略的分块耗时、向量库大小、单次检索延迟。语义分块通常最贵，要确保质量提升值得额外成本。

记录结果后，选出在你文档类型上表现最好的策略作为默认 baseline，并保留其他策略作为对比基线。不要只看单一指标，要综合考虑命中率、完整性和成本。

📰 技术雷达

  1. Late Chunking：由 Jina AI 提出。它先让嵌入模型读取整段长文本获得全局上下文，然后再对 token 级别的表示做池化得到 chunk 向量。这样每个 chunk 的嵌入都带有上下文信息，解决了传统 “先切后嵌” 导致 chunk 语义孤立的问题。对于需要保留长距离依赖的文档，Late Chunking 是一个值得关注的方向。

  2. 上下文感知分块（Context-Aware Chunking）：一些新框架开始把文档结构（标题、列表、表格、代码块）显式编码进 chunk 元数据。检索时不仅看文本相似度，还看结构相似度，使 FAQ、API 文档、论文等结构化内容的召回更稳定。例如，Unstructured 和 LlamaParse 已经能输出带结构标签的 chunk。

  3. 多粒度分块 + 重排序（Multi-Granularity + Rerank）：先用大粒度 chunk（如整节）做粗召回，再用小粒度 chunk（如段落）做精排。配合 ColBERT、BGE-Reranker 等重排模型，可以在保持召回率的同时显著提升答案精确度。这种方法的代价是系统复杂度增加，但在企业级 RAG 中越来越常见。

  4. Long-Context Embedding Models：OpenAI 的 text-embedding-3-large、voyage-3 以及国内的 BGE-M3 等模型都在提升长文本嵌入质量。未来 chunk size 的选择可能会更宽松，但 “语义边界” 仍然是核心。嵌入模型能处理的上下文越长，不意味着 chunk 就应该越大，而是意味着我们可以更从容地保留上下文信息。

  5. Document-Level Embedding 与 Hierarchical Retrieval：不再把文档简单展平成 chunk 列表，而是保留文档、章节、段落、句子等多级结构。检索时先定位相关文档，再定位相关章节，最后定位具体句子。这与数据库中的多级索引思想一脉相承，是复杂知识库的可扩展方向。

小结

文本分块是 RAG pipeline 中最容易被低估的环节，却也是最容易通过调优获得收益的地方。从后端视角看，它本质上是在做 “存储布局” 和 “索引粒度” 的权衡。固定长度分块像顺序 I/O，递归分块像按页读取，语义分块像按语义域分区，Agentic 动态分块则像查询优化器的自适应计划。

一个容易犯的错误是把分块当成一次性的配置。实际上，随着文档类型、用户问题、嵌入模型和 LLM 的变化，最优的分块策略也会变化。建议你建立一套可重复的评估流程：定义标准问题集、记录命中率、定期对比不同策略、根据结果调整参数。

从今天开始，把 “分块策略” 当作一个可实验的调参维度，而不是一次性写死的常量。用微实战里的三步法跑起来，找到适合你数据和问题的 sweet spot，这才是从后端工程师进阶为 AI 工程师的关键一步。
