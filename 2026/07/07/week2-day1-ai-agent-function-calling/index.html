AI Agent 入门与 Function Calling：从被动检索到主动决策

核心洞察（2 分钟速览）

过去一周我们完成了 RAG 的核心链路——从 Embedding、Chunking、向量数据库到检索与重排序，再到最终的 RAG 评估。这套系统的本质是”被动响应”：用户提问，系统检索，返回答案。但如果你仔细观察真实世界的工作流，你会发现一个关键缺失——系统不会主动行动。

想象一下：你问一个数据库管理员”最近有没有慢查询？”，他不仅告诉你有，还会主动打开监控面板、定位问题 SQL、生成优化建议、甚至直接提交一个索引变更。这就是从”被动检索”到”主动决策”的跃迁——也正是 AI Agent 要解决的核心问题。

作为后端工程师，你已经构建了无数”接收请求 → 查询数据库 → 返回结果”的服务。AI Agent 的本质，就是在这个链路中增加一个”决策循环”：感知环境 → 推理下一步 → 执行动作 → 观察结果 → 再推理。而 Function Calling 就是让大语言模型（LLM）从”只会说”变成”能做事”的关键机制。

用 PostgreSQL 来类比：RAG 就像一个只读的 SELECT 查询——输入确定，输出确定。而 AI Agent 就像一个存储过程（Stored Procedure）——它可以根据中间结果决定走哪个分支、调用哪个子函数、是否需要循环重试。Function Calling 就是这个存储过程中的 EXECUTE 语句。

核心概念（10 分钟深入）

什么是 AI Agent？

AI Agent（智能体）是一个能够自主感知环境、做出决策并执行动作的系统。与传统的”一问一答”式 LLM 交互不同，Agent 具备以下核心能力：

特性 传统 LLM 调用 AI Agent
交互模式 单轮问答 多轮决策循环
工具使用 无 可调用外部工具
状态管理 无状态 维护内部状态
错误处理 返回错误 自动重试/换策略
规划能力 无 可分解复杂任务
类比 SELECT 查询 存储过程 / 状态机

ReAct 模式：推理与行动的交织

目前最主流的 Agent 架构是 ReAct（Reasoning + Acting）模式。它的核心思想是让 LLM 在每一步都先”思考”（Thought），再”行动”（Action），然后”观察”（Observation），如此循环直到得出最终答案。

这个循环和后端开发中的 重试机制 非常相似。想想你写过的数据库连接池：获取连接 → 执行 SQL → 如果失败则重试 → 直到成功或超时。Agent 的 ReAct 循环本质上就是一个”智能重试”——它不只是简单重复，而是每次都会根据上一次的观察结果调整策略。

Function Calling：让 LLM 结构化地调用工具

Function Calling 是 OpenAI 在 GPT 系列中引入的机制，它允许你向 LLM 描述一组”函数”（工具），LLM 在需要时以结构化的 JSON 格式输出要调用的函数名和参数。

后端桥接（3 分钟 PG 类比）

作为后端工程师，你会发现 AI Agent 的每个概念都有精确的后端对应：

AI Agent 概念 后端 / PostgreSQL 类比 解释
Function Calling EXECUTE function_name(args) LLM 输出函数名+参数，类似存储过程调用
Tool 注册表 pg_proc 系统表 注册可用函数及其签名，供运行时查找
ReAct 循环 带重试的事务块 BEGIN → 执行 → 检查 → 失败则 ROLLBACK 重试
Agent 状态 会话级临时表 / 事务上下文 在多步推理中维护中间结果
工具返回结果 RETURN QUERY / REFCURSOR 函数执行结果返回给调用方继续处理
max_steps 限制 statement_timeout 防止无限循环的安全阀
LLM 的 tool_choice 查询优化器的 JOIN 策略选择 由系统自主决定使用哪个执行路径
多工具并行调用 parallel_worker 并行查询 多个工具同时执行，结果汇总后继续推理

一个特别有趣的类比：Function Calling 的 JSON Schema 定义，本质上就是 PostgreSQL 函数的 CREATE FUNCTION 声明。你定义函数名、参数类型、是否必填——这和你在 PG 里写 CREATE FUNCTION query_slow_queries(threshold_ms integer, limit integer DEFAULT 10) 是一模一样的。

另一个值得注意的对应：Agent 的 错误恢复能力（工具调用失败后 LLM 会换策略重试）就像 PostgreSQL 的 SAVEPOINT 机制——在事务中设置检查点，如果某步失败就回滚到检查点换个方式继续，而不是整个事务从头来过。

关键观察

注意 Agent 的”智能”体现在哪里：它不是按固定顺序调用工具，而是根据上一步的结果动态决定下一步做什么。如果没查到慢查询，它就不会调用索引建议工具。如果查到了多条，它可能针对最严重的那条去查文档。这种动态决策能力，就是 Agent 和传统 pipeline 的本质区别。

技术雷达

行业动态

  • OpenAI Assistants API 已经支持内置的代码解释器、文件搜索和 Function Calling，让构建 Agent 的门槛进一步降低。值得关注的是它的 code_interpreter 工具——Agent 可以动态写代码并执行，不再局限于预定义的函数。

  • LangChain 的 AgentExecutor 正在被新的 LangGraph 取代。LangGraph 用有向图来定义 Agent 的工作流，比 ReAct 的线性循环更灵活，支持并行分支、条件跳转和人工审批节点。对于后端工程师来说，这就像从简单的 while 循环升级到了 DAG 任务调度器（类似 Airflow）。

论文推荐

  • ReAct: Synergizing Reasoning and Acting in Language Models（Yao et al., 2023）——ReAct 模式的原始论文，清晰展示了”推理+行动”循环如何显著提升 LLM 的任务完成能力。

  • Toolformer: Language Models Can Teach Themselves to Use Tools（Schick et al., 2023）——展示了 LLM 可以自主学习何时以及如何使用外部工具，比人工标注的工具调用效果更好。

开源项目

  • CrewAI（github.com/joaomdmoura/crewai）：多 Agent 协作框架，可以定义多个角色（Agent）组成团队，每个角色有自己的工具集和职责。适合构建复杂工作流，比如”分析师 Agent + 执行者 Agent + 审核者 Agent”。

  • AutoGen（github.com/microsoft/autogen）：微软开源的多 Agent 对话框架，支持 Agent 之间自动对话、代码执行和人机协作。它的”群聊”模式特别有趣——多个 Agent 在一个对话中协作，像极了我们后端的微服务编排。
