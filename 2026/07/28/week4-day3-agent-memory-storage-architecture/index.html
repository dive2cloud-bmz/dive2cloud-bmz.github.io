Agent 记忆系列（03）· 存储架构与选型：上下文拼接、向量库、知识图谱与 KV

🚀 核心洞察

前两篇我们厘清了 Agent 为什么需要记忆，也拿到了一张“时间跨度 × 认知类型 × 生命周期”的三维分类地图。今天进入工程落地层：这些不同类别的记忆，到底该放在哪种存储里？

作为 RDS PostgreSQL 后端工程师，我对“数据该放哪”有本能的敏感。真实业务里从来没有 silver bullet：热数据进 Redis、结构化数据进关系库、搜索日志进 Elasticsearch、图关系进图数据库——这叫 polyglot persistence。Agent 记忆也一样：工作记忆像连接级会话状态，长期语义记忆像一张带语义索引的宽表，情景记忆像时序日志，知识图谱像外键关系图，KV 记忆像 Redis 缓存。

今天的核心洞察是：Agent 记忆系统本质上是多种存储介质的组合检索层，而不是一个单一的“向量数据库”。 选对承载介质，再设计好“写入 → 存储 → 检索 → 巩固/遗忘”的流水线，才是可落地的长期记忆。

🧠 核心概念

1. 上下文拼接：最朴素的“工作记忆”

没有任何外部存储时，Agent 能依赖的只有当前上下文窗口。把历史对话直接拼进 Prompt，是最先被想到、也最容易踩坑的方案。

做法：把 system prompt + 历史 messages + 当前 user input 直接送给 LLM。

问题：

  • Token 天花板：上下文越长，模型能用于真正推理的有效注意力越少，长上下文还会显著增加延迟和成本。
  • 信号淹没：无关的历史会让模型抓不住重点，尤其是多轮之后。
  • 隐私/合规风险：把全部对话历史反复上传，可能触碰数据安全边界。

优化方向：滑动窗口、摘要压缩、Truncation 策略、选择性重放。下面是一个滑动窗口 + 摘要的最小示例：

2. 向量库记忆：语义近邻检索

把记忆文本变成向量，按语义相似度检索，是当前 Agent 记忆最常见的长期记忆形态。它的核心假设是：与当前查询语义相近的历史信息，最应该被召回参与决策。

适用场景：

  • 过往对话片段的语义检索
  • 用户偏好、成功案例、失败教训的 recall
  • 多轮任务中跨会话找回相关上下文

代表工具：pgvector、Chroma、Milvus、Qdrant、Weaviate、Pinecone。

架构流程：

关键工程决策：

  • Embedding 模型选型：OpenAI text-embedding-3-small 便宜够用；若对中文要求高，可考虑 BGE-M3、Jina Embeddings v3。
  • 索引算法：HNSW（速度优先、召回高）、IVFFlat（内存优先）、暴力扫描（数据量极小）。
  • 分段粒度：按整轮对话、按句子、按主题块存储，召回质量差异很大。
  • 元数据过滤：会话 ID、用户 ID、时间范围等标量过滤能显著降低向量搜索空间。

3. 知识图谱记忆：关系型长期记忆

向量库擅长“语义相似”，但弱于“关系推理”。当 Agent 需要回答“我上周提到的那个同事是谁的下属？”“这个需求依赖哪几个系统？”这类多跳问题时，知识图谱是更好的载体。

核心抽象：实体（Entity）- 关系（Relation）- 实体（Entity）三元组，例如 (张三, 工作于, PostgreSQL团队)。

优势：

  • 关系可解释、可更新、可冲突检测
  • 支持多跳推理，适合复杂业务规则
  • 能显式表达“事实”而非“相似文本”

代表工具：Neo4j、NetworkX、Cognee、GraphRAG（Microsoft）。

4. KV 记忆：结构化快捷存取

有些记忆不需要语义检索，只需要精确读写。例如：用户姓名、API Key、偏好语言、当前任务状态、待办清单。这类数据用 KV 存储最合适。

KV 记忆 ≈ 带作用域的键值缓存。它强调：

  • 低延迟：O(1) 读写
  • 强一致性：读到的就是最新值
  • 结构化：JSON / 标量 / 数组

代表工具：Redis、DynamoDB、PostgreSQL JSONB、Etcd。

KV 记忆常被低估。很多 Agent 系统明明只需要“记住用户姓什么”，却硬生生把整段自我介绍 embedding 进向量库，每次检索都触发一次相似度计算。识别出“需要精确查询” vs “需要语义检索”的记忆，是设计高效记忆系统的第一步。

5. 混合架构：为记忆分层

真实系统不会只选一种介质，而是根据记忆的认知类型和访问模式分层组合。下面是一个常见的分层模型：

各层职责：

  • 工作记忆：只放当前决策必须的信息，生命周期一次 LLM 调用。
  • KV / 缓存层：放高置信度、频繁读写的结构化事实，如用户 profile、任务状态。
  • 向量库：放需要语义检索的情景记忆，如历史对话、成功案例。
  • 知识图谱：放实体关系密集、需要多跳推理的语义记忆。
  • 程序记忆：一般落地为 system prompt、tool schema、few-shot 示例库。

6. 把主流框架标定到地图

有了上面的分层，我们就可以把 Day 2 提到的几个框架定位清楚：

框架 核心载体 记忆类型侧重 典型使用模式
MemGPT 上下文分层（主上下文 / 外部上下文） 工作记忆 + 长期记忆分页 显式管理 LLM 上下文窗口，像 OS 换页
Mem0 向量库 + 图/结构化元数据 语义 + 情景记忆 用户级长期记忆，跨会话 recall
Zep 向量库 + 时序知识图谱 情景 + 语义记忆 会话总结、实体提取、自动过期
LangMem 与 LangGraph 集成的记忆层 情景记忆为主 在 LangGraph 节点中显式存取记忆
Cognee 知识图谱为核心 语义记忆 面向多跳推理的长期知识库

这张表的价值在于：不要问“哪个记忆框架最好”，而要问“我的记忆以哪种类型为主”。 如果你的 Agent 主要做客服回访，情景记忆用向量库就够了；如果是医疗问诊或复杂 B2B 销售，知识图谱 + KV 可能更关键。

🔗 后端桥接

把 Agent 记忆的各个组件映射到后端工程师熟悉的概念，会立刻降低学习成本：

Agent 记忆概念 后端/PostgreSQL 类比 关键相似点
上下文窗口 TCP 连接缓冲区 / HTTP Session 生命周期绑定一次请求/会话，容量有限
Embedding 行的规范化向量表示 / JSON 序列化 把非结构化对象转成可检索、可比较的固定维度表示
向量索引 PostgreSQL GIN / GiST / pgvector HNSW 在高维空间做近似最近邻搜索，本质是索引结构
向量库 Elasticsearch / 全文检索库 以相似度为核心查询语义，元数据过滤辅助
知识图谱 外键关系图 / 图数据库 显式关系、多跳 join、可冲突检测
KV 记忆 Redis / 物化视图 精确读写、低延迟、适合热数据
混合记忆架构 Polyglot Persistence / CQRS 不同数据形态用不同存储，读写模型分离
记忆巩固/遗忘 Vacuum / TTL / 数据治理 清理过期、重复、低价值数据，防止系统腐烂

一个特别值得 PostgreSQL 工程师兴奋的点是：pgvector 让关系库本身就具备向量存储能力。 你不需要为了 Agent 记忆单独引入一套向量数据库，可以把 JSONB 标量字段、VECTOR 向量字段、普通 B-tree 索引放在同一张表里，用 SQL 一次完成过滤 + 相似度排序。这对已经拥有 RDS PostgreSQL 基础设施的团队来说，是降低复杂度的绝佳路径。

📰 技术雷达

  • Mem0：开源 Agent 记忆层，近期在记忆更新、冲突合并和多用户隔离上有较多迭代。它的设计哲学是“为每个用户维护一个长期记忆向量空间”，适合需要跨会话记住用户偏好的 C 端应用。
  • LangMem：LangChain 官方推出的记忆原语，强调与 LangGraph 的深度集成。最新方向是把记忆读写变成 LangGraph 节点中的显式操作，而不是隐式中间件。
  • Cognee：主打“知识图谱即记忆”的开源项目，支持从对话中自动抽取实体关系并构建可查询图谱。适合需要复杂关系推理的 B2B Agent。
  • Zep： continues to emphasize time-aware memory extraction，自动把对话提炼成事实、总结和情感标签，并支持 TTL 和遗忘策略。
  • OpenAI ChatGPT Memory / Anthropic Context Caching：大厂产品侧都在做“长期记忆 + 长上下文缓存”，说明记忆正在成为 LLM 应用的核心差异化能力。
  • 论文关注：CoALA（Cognitive Architectures for Language Agents）仍是理解 Agent 记忆的理论基础；MemGPT 论文对“上下文即内存”的 OS 隐喻有精彩论述；GraphRAG 论文则展示了知识图谱在检索增强中的优势。
