RAG 分块不是切字符串，而是切语义边界

发布日期:   2026-07-18

本周话题：分块策略与语义边界。对从 PG/Backend 转 AI 的工程师来说，RAG pipeline 里最值得先吃透的往往不是模型选型，而是“怎么切文档”。

🚀 核心洞察（2 分钟）

分块质量决定检索天花板——再好的嵌入模型也无法弥合被切断的语义单元；合适的分块策略能让检索准确率提升一个量级。

这句话听起来像一句正确的废话，直到你真正在生产环境排过 RAG 的检索 case。很多团队花了大量时间调 embedding 模型、换 reranker、调 top-k，最后发现：检索失败的根本原因是“答案被切断了”。用户问的是一个跨段落的问题，而固定 256 token 的切块把关键推理链拦腰斩断，模型永远找不回完整上下文。

从 PG/Backend 的视角来看，分块其实和后端系统设计里的“边界划分”是同一类问题。API 拆得太粗，一个接口干十件事，调用方没法复用；拆得太细，十个接口拼一个业务，网络往返和事务成本爆炸。PostgreSQL 的 TOAST 机制也类似：大字段不会和无条件的行内数据混放，而是按阈值拆出去存，查询时再按指针召回。分块不是“把文本变短”，而是“在保留语义完整性的前提下，定义可被独立检索和召回的最小信息单元”。

因此，RAG 分块的第一性原理不是“长度”，而是“语义边界”。一个好的块应该满足：

  1. 内部自洽：块内只围绕一个主题或一个事实展开；
  2. 边界清晰：块与块之间尽量落在段落、列表、章节或逻辑转换点；
  3. 可独立召回：单独被检索出来时，仍然能回答某类问题，不依赖前后文的隐性信息。

记住这个结论，剩下的所有策略都只是在这三条约束下的工程权衡。

🧠 核心概念（10 分钟）

1. 固定长度 vs 语义分块

最直觉的做法是固定长度分块：按字符数或 token 数，每 N 个切一刀。实现简单、可预测、向量化批次规整，是 demo 阶段的最爱。但它的隐患也最直接：

  • 切断语义：一句话或一个步骤被拆到两个块，单独检索时意义不完整；
  • 污染主题：同一块里混合了多个话题，embedding 的“重心”被稀释；
  • 丢失结构：表格、代码块、列表被打断，格式信息丢失。

相比之下，语义分块会尝试在“有意义的位置”下刀。常见做法包括：

  • 按段落（\n\n）或标题切分；
  • 按文档结构（Markdown 标题、HTML 标签、PDF 章节）切分；
  • 用聚类或 embedding 相似度检测主题转换点，再下刀。

2. 重叠窗口与上下文保留

即使按语义边界切分，块与块之间也可能存在依赖关系。比如前一段定义了术语，后一段才展开应用。如果术语刚好落在边界上，问答时就会因为缺少定义而答错。

滑动窗口（overlap）就是用来缓解这个问题的。它的思想很简单：相邻两个块共享一部分 token，让关键信息至少完整出现在其中一个块里。

重叠窗口不是越大越好。它是一把双刃剑：

  • 优点：保留跨边界信息，提高召回率；
  • 缺点：增加冗余、提高存储和索引成本、可能让同一个答案在多个块里重复出现，影响 reranker 的区分度。

工程上通常会把 overlap 控制在块大小的 10%–25%。如果下游任务是代码检索或长文档问答，overlap 可以略大；如果只是做摘要或关键词检索，overlap 可以缩小甚至为零。

3. 递归 / 层次分块

递归分块（Recursive Chunking）是 LangChain 里 RecursiveCharacterTextSplitter 的核心思想：优先用高优先级的分隔符切分（如章节、段落），如果切出来的子块还太长，再用次级分隔符继续切（如句子、逗号），直到满足长度限制。

这种策略的好处是“结构优先，长度兜底”。它不像固定长度那样粗暴，也不像纯语义分块那样难以控制上限。可以用一棵树来理解：

4. 面向下游任务的块大小

块大小没有银弹，取决于你准备用它回答什么问题：

下游任务 推荐粒度 原因
事实性问答 128–512 token 问题通常指向单个事实，小块命中率高
摘要、聚合 1024–2048 token 需要看到更多上下文才能生成连贯摘要
代码检索 函数/类级别 代码的语义单元是函数，不是字符数
多跳推理 层次块 + 父级召回 需要在多个片段之间建立关系

一个常被忽视的细节是：embedding 模型也有最佳输入长度。例如 text-embedding-3-small 支持 8191 token，但过长的输入会让后面的 token 被压缩，表征质量下降。很多开源 embedding 模型在 256–512 token 附近表现最稳定。选块大小时，要把“任务需求”和“模型特性”一起看。

🔗 后端桥接（3 分钟）

把 RAG 分块映射到后端和 PostgreSQL 的概念，会让很多设计选择变得自然。

1. 分块 ≈ 微服务里的领域边界划分

太粗的块像一个“万能服务”，什么都做，调用者（这里是 LLM）无法精准获取所需信息；太细的块像过度拆分的微服务，每次回答都要检索十几个块，延迟和噪声都上升。好的分块和好的微服务一样：高内聚、低耦合、接口（即块内容）自描述。

2. 分块 ≈ PostgreSQL TOAST 与索引粒度

PostgreSQL 中，超过 2KB 的变长字段会被 TOAST 机制拆出主表，按 chunk 存储，查询时根据行内指针按需召回。RAG 里的文档分块本质上也是同一逻辑：把大文档拆成可索引、可召回的物理单元。不同之处在于，TOAST 的拆分对用户透明，而 RAG 的分块策略直接影响检索语义。

3. 重叠窗口 ≈ 数据库的 read-ahead / 缓存行

重叠窗口相当于在块之间预读一部分上下文，避免边界处信息断裂。它和 PG 的 prefetch、操作系统的缓存行对齐一样，都是用少量冗余换访问连续性。

4. 层次分块 ≈ B+ 树索引

小块是叶子节点，负责精确定位；父级章节是中间节点，负责提供上下文范围。检索时从小块入手，再向上溯源，和 B+ 树“先定位叶子、再范围扫描”的思路异曲同工。

理解这些类比之后，你在设计 RAG 存储时会更自觉地考虑：块大小、overlap、父级引用、元数据字段、索引策略——这些其实都是后端工程师每天都在打交道的问题。

🛠️ 微实战（5 分钟）

任务：用 Python 对同一篇长文档分别做 固定 256 token 分块、递归分块、语义分块，统计每类策略下“块内主题一致性”，并可视化块边界。

做什么：给每个 chunk 用 embedding 模型生成向量，再计算 chunk 内部句子的两两余弦相似度均值。

验证标准：打印三种策略的平均一致性分数，semantic ≥ recursive ≥ fixed 即为合理。

做什么：用 matplotlib 把每个 chunk 在原文中的起止位置画成条形图。

验证标准：固定分块的条形均匀但可能切断标题；语义分块的条形与 Markdown 标题对齐；递归分块介于两者之间。

步骤 5：写一句结论

做什么：根据一致性分数和可视化结果，回答“这篇文档应该用哪种策略”。

📰 技术雷达

分块领域正在从“静态切分”向“上下文感知切分”演进，值得持续关注以下方向：

  1. Late Chunking（上下文增强分块）
    传统做法是先切块再 embedding，导致每个 chunk 失去全局上下文。Late Chunking 先让模型看到完整文档获取上下文感知表示，再在表示层按位置切分。Jina AI 的 jina-embeddings-v3 和类似研究已经展示了这种方式在长文档检索上的优势。

  2. 多模态分块
    随着多模态 RAG 兴起，文档不再是纯文本。图文交错、幻灯片、PDF 里的表格与图片都需要统一的“语义块”抽象。未来分块器需要同时理解文本、布局、图像区域，甚至语音片段的边界。

  3. 面向 Agent 长上下文记忆的动态分块
    Agent 的工作记忆需要支持动态增删。新的研究在探索“按事件边界切分记忆”、“按重要性压缩历史”、“根据当前任务按需重构 chunk”等方向。分块从预处理步骤变成运行时策略。

  4. 可学习分块（Learned Chunking）
    用小型模型或奖励信号直接预测“最佳切分点”，让分块本身成为一个可优化环节。这会把 RAG pipeline 的优化空间从“选模型”扩展到“学制边界”。

小结

RAG 分块的本质不是把长文本变短，而是定义可被独立检索的语义单元。固定长度分块适合快速验证，语义分块适合强结构文档，递归分块是工程上的折中默认方案，层次分块则为复杂推理提供父子上下文。 overlap、块大小、下游任务、embedding 模型特性，四个变量需要一起调优。

对后端工程师来说，这整个问题都可以翻译成熟悉的语言：边界划分、索引粒度、冗余与一致性权衡、分层存储。掌握这套思维之后，你不需要记住每一种 chunking 库的参数，也能根据业务特点设计出合理的分块策略。
