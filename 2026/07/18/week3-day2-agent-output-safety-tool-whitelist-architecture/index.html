Agent 输出安全与工具调用白名单架构：把 LLM 装进最小权限沙箱

今日一句话：LLM 的输出不是静态文本，而是可能被执行的代码；Agent 的工具不是函数，而是权限。后端工程师设计 API 时怎么防注入和越权，设计 Agent 时就要用同样的思路做白名单与校验。

🚀 核心洞察（2 min）

昨天的课程让我们看到，Prompt Injection 可以把一个”乖巧”的客服 Agent 变成攻击者的提权工具。但 Prompt Injection 只是入口，真正的危害发生在两个后续阶段：

  1. Agent 的输出被下游系统直接执行（例如拼进 SQL、渲染到前端、写进 Shell）。
  2. Agent 调用了本不该调用的工具，例如把内部数据发邮件、删除用户、调用支付接口。

作为 RDS PostgreSQL 后端工程师，你对这两种风险应该有肌肉记忆：

  • 任何从外部进入系统的数据，必须先校验再使用，不能直接拼进 SQL、HTML、命令行。
  • 任何敏感操作，必须基于最小权限原则，应用账号不能是 superuser，更不能让前端用户决定执行哪个存储过程。
  • 任何跨边界调用，必须记录审计日志，以便事后追踪和复盘。

Agent 系统把这三个原则全部复现了一次，只是攻击面和防御面从”结构化数据”扩展到了”自然语言”和”工具调用意图”。今天的目标就是建立一套输出安全与工具调用白名单架构，让 Agent 的输出和行为都像数据库角色一样，被显式授权、严格校验、可审计。

🧠 核心概念（10 min）

1. 为什么 Agent 的输出比传统 API 响应更危险

传统 REST API 的响应通常有明确的 schema：字段名、类型、取值范围都是预先定义的，前端或下游服务按契约消费。但 LLM 的输出是概率性自然语言，即使要求 JSON，也可能出现：

  • 字段缺失或类型错误。
  • 包含 Markdown、HTML、JavaScript、SQL 片段。
  • 泄露系统提示、用户隐私或内部数据。
  • 在间接注入场景下，输出被攻击者操控，进而误导用户或触发下游漏洞。

OWASP LLM Top 10 中专门有一项 LLM02: Insecure Output Handling，指的就是：模型输出未经充分审查就被传递给下游组件，导致 XSS、SSRF、权限提升、远程代码执行等二次攻击。

输出处理链的典型风险点

可以看到，输出安全不是单一检查点，而是一条链。任何一个环节失守，都会把自然语言里的恶意 payload 传导到具体的技术栈漏洞。

2. 工具调用白名单：默认拒绝，最小权限

在 Agent 架构中，工具（Tool / Function）是 LLM 与外部世界交互的接口。设计工具时最常见的错误是：

  • 工具能力过大：一个 run_sql(query: str) 就等于把数据库超级权限交给模型。
  • 工具注册无边界：任何被定义的函数都会被 LLM 看到并可能调用。
  • 工具调用无审批：敏感操作一旦模型决定执行就立即执行。

正确的做法是采用 白名单架构（Whitelist / Allowlist Architecture）：

原则 说明 反例 正例
默认拒绝 不在白名单里的工具，即使被定义也不能被当前 Agent 调用 所有工具默认对 Agent 可见 每次调用前检查 tool_name in allowed_tools
最小权限 每个工具只做一件事，参数范围受限 run_sql(sql: str) get_order_status(order_id: str)
上下文感知 不同会话、不同用户、不同任务拥有不同的工具集 所有会话共享同一套工具 根据用户角色动态生成工具列表
敏感操作审批 高权限工具调用需要二次确认或人工审批 模型直接调用 send_email 敏感工具触发 human-in-the-loop 节点
审计记录 每一次工具调用的输入、输出、调用者、时间都被记录 只记录最终回复 记录完整 tool_call 与 tool_result

3. 结构化输出：用 Schema 把”自然语言”变成”数据”

要让输出可校验，第一步是让输出有结构。现代 LLM 支持多种结构化输出方式：

  • OpenAI JSON mode / Structured Outputs：强制模型输出合法 JSON，且可指定 schema。
  • Anthropic tool use：通过工具调用返回结构化结果。
  • Instructor / LangChain PydanticOutputParser：在应用层做 schema 校验和重试。
  • JSON Schema + 自定义校验器：最通用，不依赖特定 SDK。

结构化输出不仅可以防止格式错误，还能把”内容安全”问题转化为”schema 校验”问题。例如：

4. 输出过滤与内容安全层

结构化输出之后，还需要对具体内容做安全过滤。常见维度包括：

维度 风险 检测方法
PII 泄露 输出中包含手机号、身份证、信用卡号 正则 + NER 模型
敏感词/系统提示泄露 输出包含 “system prompt”、”忽略前文” 等 关键字匹配 + 相似度检测
代码注入 输出包含 <script>、DROP TABLE、rm -rf 语法特征匹配
有害内容 仇恨、暴力、自残、色情 内容审核 API
幻觉事实 输出与检索结果不符 事实校验 / citation 检查

在生产环境中，这些内容过滤器通常以 sidecar 或 独立服务 的形式存在，而不是内嵌在每个 Agent 里。这样便于复用、升级和独立审计。

5. 工具调用策略引擎

工具调用不应该只由 LLM 决定。一个健壮的 Agent 架构会在 LLM 和真实工具之间插入一个策略引擎（Policy Engine），它的职责包括：

策略引擎的关键判定逻辑：

  1. 工具可见性：当前会话是否有权看到这个工具？
  2. 参数合法性：参数是否符合 schema？是否在允许范围内？
  3. 业务规则：例如退款金额是否超过阈值？邮件收件人是否在白名单域？
  4. 敏感操作审批：是否需要 human-in-the-loop？
  5. 频率与预算：该工具是否被调用过多次？是否超过 token / 成本预算？
  6. 结果可返回性：工具结果是否包含敏感信息，需要脱敏后才能返回给 LLM？

6. Human-in-the-Loop：最后一道防线

再强的自动防御也可能被绕过。对于高敏感操作，必须引入人机确认。常见模式：

  • 显式确认：系统问用户”你确定要发送这封邮件吗？”，用户回复”确认”后才执行。
  • 中断节点（LangGraph interrupt）：在工作流中插入一个需要人类批准的节点。
  • 影子模式（Shadow Mode）：先模拟执行，把结果展示给人类审批，再真正提交。
  • 审批矩阵：不同操作需要不同级别的人员审批，例如普通客服只能查询，主管才能退款。

这和后端系统中的”审批流”或”两阶段提交”是同构的：先锁定资源或准备操作，再等待最终确认，最后提交或回滚。

1. LLM 输出 ≈ 用户上传的 CSV / 动态 SQL

PostgreSQL 后端不会信任前端传来的字符串，更不会把它直接拼进 SQL。你会用参数化查询、转义、白名单枚举来处理。LLM 输出同样需要这种处理，因为它的内容来源不可控（可能包含间接注入）。

4. 人机确认 ≈ 两阶段提交（2PC）

分布式事务里，2PC 先让各参与者准备，再统一提交。人机确认也是类似的：

  1. Prepare 阶段：Agent 生成拟执行的操作（工具名 + 参数），但不真正执行。
  2. Vote 阶段：人类用户审批或拒绝。
  3. Commit / Abort 阶段：根据投票结果执行或回滚。

在 LangGraph 等框架中，这就是 interrupt + Command(resume=...) 的模式。

5. 审计日志 ≈ PostgreSQL 审计扩展（pgaudit）

PostgreSQL 的 pgaudit 可以记录所有 DDL、DML 和权限变更。Agent 系统也需要记录：

  • 完整 messages（系统提示 + 用户输入 + 历史上下文）。
  • LLM 输出原文。
  • 工具调用请求与结果。
  • 策略引擎的每一次判定（允许 / 拒绝 / 需审批）。
  • 最终返回给用户的内容。

这些日志是事后溯源、合规审计和安全红队的关键数据。

📰 技术雷达

论文与标准

  • OWASP LLM Top 10 2025：LLM02 Insecure Output Handling 和 LLM06 Sensitive Information Disclosure 都与今日主题直接相关，强调输出过滤与最小权限。
  • NIST AI RMF 1.1：建议把”输出可解释性”和”权限边界”作为 AI 系统治理的核心控制点。
  • “Prompt Injection and Insecure Output Handling in LLM Applications”（2025）：系统比较了输入侧与输出侧防御的失效模式，指出输出侧过滤往往被忽视但同样关键。

开源项目与工具

  • LLM Guard（laiyer-ai/llm-guard）：支持输入/输出扫描、PII 脱敏、Prompt Injection 检测，可部署为 sidecar，适合替换示例中的手工过滤器。
  • NeMo Guardrails（NVIDIA）：通过 YAML 定义 rails，可限制主题、过滤输出、执行事实检查，适合构建声明式安全策略。
  • Guardrails AI：基于 Pydantic 的结构化输出校验框架，可自动修复不符合 schema 的 LLM 输出。
  • Instructor：在 OpenAI/Anthropic 之上封装 Pydantic 校验，把”结构化输出”变成工程常态。
  • Presidio（Microsoft）：开源 PII 检测与脱敏库，适合集成到输出过滤链路。

行业动态

  • 2025 年起，主流 Agent 托管平台（LangGraph Platform、OpenAI Agents SDK、Claude for Work）陆续内置工具调用审批流和输出审计日志，敏感操作默认需要 human-in-the-loop。
  • Anthropic 在《Building effective agents》中提出 “least-privilege tool design”：每个工具只做一件事，Agent 只能看到当前任务需要的工具。
  • 国内大模型平台推出”输出安全检测” API，可检测 PII、敏感词、代码注入，进一步降低自建过滤成本。

下一步学习建议

  1. 用 LLM Guard 或 NeMo Guardrails 替换示例中的手工内容过滤器，体验生产级策略配置。
  2. 在 LangGraph 中把 PolicyEngine 实现为一个独立节点，结合 interrupt 实现真正的人机确认工作流。
  3. 学习 JSON Schema 与 OpenAI Structured Outputs，把 Agent 的所有输出都纳入 schema 约束。

今日小结

  • Agent 的输出是代码：它可能被渲染、执行、转发，因此必须像处理用户输入一样处理 LLM 输出。
  • 工具调用需要白名单：默认拒绝、按角色授权、敏感操作审批，是和 PostgreSQL 权限模型同构的安全设计。
  • 输出安全是链式防御：结构化输出 → schema 校验 → 内容过滤 → HTML 转义 → 审计日志，缺一不可。
  • 人机确认不是用户体验负担：对于高敏感操作，它是把不可控风险转化为可控流程的必要设计。
