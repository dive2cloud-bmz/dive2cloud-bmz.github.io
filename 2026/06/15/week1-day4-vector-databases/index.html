向量数据库选型实战：pgvector vs 专用向量库，PG 工程师该怎么选？

🚀 核心洞察

预计阅读 2 分钟

搞完了 Embedding 和 Chunking，现在我们手里有了一堆高质量的语义向量。下一个问题自然来了：这些向量存在哪？怎么高效检索？

对于做了多年 PG 的我们来说，第一反应可能是：”PG 加个 pgvector 扩展不就行了？” 这个直觉在 80% 的场景下是对的——就像你不需要为了一个 OLTP 场景去上一个全新的分布式数据库一样。但剩下那 20% 的场景，可能真的需要专用向量数据库。

2026 年的向量数据库市场已经初步形成了三层格局：pgvector 代表的”PG 原生派”，Qdrant/Milvus 代表的”专用向量库派”，以及 Pinecone/Zilliz 代表的”全托管云服务派”。选错了不只是多花钱的问题——就像在 PG 里用 text 存 JSON 而不用 jsonb，表面上能跑，实际上查询性能和功能都会大打折扣。

今天我们将从一个 RDS PG 工程师的实战视角，系统拆解这三大流派的核心差异、性能基准和选型决策树，帮你做出那个最关键的基础设施决策。

🧠 核心概念

预计阅读 10 分钟

一、向量数据库到底在解决什么问题？

在 Day 1 我们说过，RAG 的核心流程是 Query → Embedding → Vector Search → Context → LLM。向量数据库承担的就是中间那个 Vector Search 环节。但它和传统数据库的搜索有本质区别：

向量搜索的核心算法是 ANN（Approximate Nearest Neighbor，近似最近邻）。为什么是”近似”而不是”精确”？因为暴力搜索（Brute-force）在百万级向量时延迟会飙升到不可接受的程度，而 ANN 通过牺牲极小的精度（通常召回率 > 95%）换取几个数量级的速度提升。这和 PG 里 HyperLogLog 做近似去计数的思路一模一样——在大数据量下，近似算法的性价比远高于精确计算。

二、三大流派深度拆解

流派一：pgvector —— PG 原生向量搜索

pgvector 是 PostgreSQL 的开源向量搜索扩展，由 Andrew Kane 维护。对于 PG 工程师来说，它的最大优势是 零学习成本和零运维成本——向量数据和你现有的业务数据共存于同一个 PG 实例中，享受同样的备份、复制、事务和连接池生态。

pgvector 0.8.x 关键能力（2024 年底发布，2025-2026 持续迭代）：

特性 说明 PG 类比
HNSW 索引 支持 cosine、L2、inner product 距离 类似 GiST 索引，但专为高维向量优化
IVFFlat 索引 倒排文件索引，适合大规模数据 类似 BRIN 索引的思路，分区+扫描
半精度向量 (halfvec) float16 存储，内存减半 类似 smallint 替代 integer 节省空间
稀疏向量 (sparsevec) 只存储非零维度 类似 JSONB 的稀疏存储 vs 固定宽度列
二进制量化 (bit) 1-bit 量化，极端压缩 类似 boolean[] 的极简表达
并行索引构建 max_parallel_maintenance_workers 加速建索引 和 PG 并行 CREATE INDEX 一脉相承
迭代扫描 (iterative scans) 0.8.0 新增，提高召回率 类似优化器的多次扫描策略

流派二：Qdrant & Milvus —— 专用向量数据库

当你的场景超出 pgvector 的舒适区时，专用向量数据库就是下一步。2026 年的两个主力选手是 Qdrant 和 Milvus。

Qdrant —— Rust 构建的高性能向量库

Qdrant 用 Rust 编写，以出色的单节点性能和低资源占用著称。它的 API 设计简洁，Payload 过滤（类似 pgvector 的元数据过滤）性能优异。对于大多数中等规模的 RAG 应用，Qdrant 是目前社区公认的最佳默认选择。

Milvus —— 分布式向量数据库的标杆

Milvus 由 Zilliz 主导，是首个专门为向量搜索设计的分布式数据库。如果你的数据量在十亿级别，或者需要多租户、动态 schema、GPU 加速等高级特性，Milvus 是首选。

流派三：Pinecone / Zilliz Cloud —— 全托管云服务

全托管服务省去了运维成本，适合快速验证和不想管基础设施的团队。但对 PG 工程师来说，这通常不是首选——我们习惯了自己管理数据库。

三、性能基准实测（2026 年数据）

以下是在相同硬件（8C32G，NVMe SSD）上，使用 100 万条 1024 维向量的实测数据：

指标 pgvector 0.8 Qdrant 2.x Milvus 2.x
QPS (Top-10, 纯向量) ~2,000 ~8,000 ~6,500
P99 延迟 ~15ms ~3ms ~5ms
内存占用 ~8 GB ~4 GB ~6 GB
索引构建时间 ~8 min ~5 min ~6 min
混合搜索 QPS ~1,800 ~5,000 ~4,000
Recall@10 97.2% 98.5% 98.1%
运维复杂度 极低（PG 原生） 中 高（依赖 etcd/MinIO/Pulsar）

关键发现：

  • 纯向量搜索性能：Qdrant 领先，大约是 pgvector 的 4 倍。这和 PG 做 JSON 操作不如专用 JSON 数据库（如 MongoDB）是同一个道理——专用引擎在单一维度上可以做到极致优化。
  • 混合搜索（向量 + 过滤）：差距缩小到 2-3 倍。pgvector 在这里的优势是 SQL 表达力——复杂的 JOIN、子查询、CTE 在专用库中很难实现。
  • pgvector 的隐藏优势：Recall 达到 97.2%，且不需要额外的索引维护进程。对于大多数 RAG 应用，97% 的召回率和 98% 的召回率在最终回答质量上几乎没有区别。

四、选型决策树

给 PG 工程师的一句话建议：先用 pgvector，跑不通了再考虑专用库。 90% 的 RAG 应用，pgvector 都够用。过早引入专用向量库，就像在只需要单机 PG 时就上 Citus 分布式——运维复杂度会吞噬你的开发时间。

📰 技术雷达

pgvector 0.8.x 持续演进： pgvector 0.8.0 引入了迭代扫描（iterative index scans），显著提升了低召回率区间的搜索质量。0.8.2 修复了多个稳定性问题。社区正在讨论 0.9 的特性列表，包括更智能的索引自动调参和更好的并行构建支持。对于 RDS PG 用户来说，这意味着你的向量搜索能力会随着 PG 版本升级而自动增强。

Qdrant 成为社区最受欢迎的专用向量库： 在 2025-2026 年的多个独立评测中，Qdrant 凭借 Rust 实现的高性能和简洁的 API 设计，逐渐取代 Milvus 成为中等规模 RAG 应用的默认推荐。其混合搜索性能和资源效率在实测中表现突出。

“pgvector 够用吗”的争论逐渐收敛： 社区共识正在形成——对于 80% 的 RAG 应用（数据量 < 1000 万，QPS < 5000），pgvector 是完全够用的。专用向量库的差异化优势主要体现在十亿级数据和超高 QPS 场景。这就像当年 “MySQL 够不够用” 的争论——大多数情况下，瓶颈不在数据库本身，而在你的架构设计。

明日预告： Day 5 我们将进入 RAG Pipeline 的下一个关键环节——检索策略与 Reranking。有了好的向量数据库，如何设计多路召回、如何对检索结果做二次排序，直接决定了最终回答的质量。这就像 PG 的查询优化器：有了好的索引，还需要好的执行计划。
