Chunking 策略深度指南：从固定切分到语义感知切分

🚀 核心洞察

预计阅读 2 分钟

昨天我们搞定了 Embedding 模型的选型，现在有了”语义指纹”的能力。但有一个问题被很多人低估了：你打算把什么文本喂给 Embedding 模型？一整篇 5000 字的文档？还是一句话？

答案显然是——都不行。太长的文本会超出 Embedding 模型的最大 Token 限制（BGE-M3 是 8192 tokens，Qwen3-Embedding 是 32768 tokens），就算不超限，一段包含多个主题的长文本生成的向量也会”模糊”——就像你把 PG 里 10 个不同表的数据塞进同一个 JSONB 列，然后指望用一个 GIN 索引精确检索到任何一条记录一样不现实。

太短的文本呢？一句话的语义信息太少，向量缺乏足够的上下文来区分相近概念。”PG 性能调优”如果只取”性能”两个字，你根本无法区分它在说数据库、网络还是 CPU。

这就是 Chunking（文本切分）要解决的问题。Chunking 是 RAG pipeline 中最容易被忽视、但对最终回答质量影响最大的环节。在 2024-2025 年的大量实践中，一个共识已经形成：RAG 回答质量的瓶颈，80% 在 Chunking，而不是在 Embedding 或 LLM 上。 这就好比 PG 查询性能的最大瓶颈往往不是 CPU 或内存，而是你的表结构和索引设计。

今天我们将从 PG 工程师的视角，系统拆解五种主流 Chunking 策略，实测它们在不同文档类型下的表现，并给出选型决策树和生产级的实现代码。

🧠 核心概念

预计阅读 10 分钟

一、为什么 Chunking 这么重要？

在深入具体策略之前，先理解 Chunking 质量对 RAG 的级联影响。

Chunking 需要同时优化三个相互矛盾的目标：

目标 含义 冲突
语义完整性 每个 Chunk 应该是一个完整的语义单元 与粒度冲突
合理粒度 Chunk 大小适中，向量表示精确 与完整性冲突
上下文连贯 相邻 Chunk 之间有上下文关联 与独立性冲突

这和 PG 表分区的设计哲学惊人地一致——分区太大则查询无法有效裁剪，分区太小则跨分区查询开销大，分区之间需要有明确的边界定义。

二、五种主流 Chunking 策略详解

策略一：固定长度切分（Fixed-size Chunking）

最朴素的策略：按固定字符数或 Token 数切分，相邻块之间保留一定重叠。

优点： 实现极其简单，Chunk 大小均匀，适合处理格式统一的纯文本。

缺点： 完全不考虑语义边界。一个完整的句子、一个函数定义、一个 SQL 查询都可能在中间被切断。这在技术文档中尤其致命——想象一个 CREATE TABLE 语句被切成两半，每一半都失去了意义。

PG 类比： 就像用 LIMIT 100 OFFSET N 做分页——简单粗暴，但完全不管数据的逻辑边界。

策略二：递归字符切分（Recursive Character Splitting）

这是目前使用最广泛的策略，也是 LangChain 的默认推荐。核心思想是按优先级递归尝试不同的分隔符：先按段落分，太大则按句子分，再大则按子句分。

注意：每个 Chunk 都是一个完整的语义段落，没有在句子中间被切断。

优点： 实现简单、效果好、适用面广。是大多数场景的默认首选。

缺点： 无法理解文档的深层结构（如 HTML 标签层级、Markdown 标题层级），对于代码块、表格等特殊结构处理不好。

PG 类比： 就像 PG 的 pg_partman 分区管理——按时间范围自动分区，逻辑清晰，但无法理解数据内容的语义差异。

策略三：文档结构感知切分（Structure-aware Chunking）

针对有明确结构的文档（Markdown、HTML、PDF 章节），利用文档本身的结构信息来指导切分。

优点： 完美保留文档的逻辑结构，每个 Chunk 有明确的”归属”（属于哪个章节），检索时可以利用元数据做精确过滤。

缺点： 只适用于有明确结构的文档。对于纯文本、聊天记录、日志等无结构文档无能为力。

PG 类比： 这就是 PG 的逻辑分区（Declarative Partitioning）。你按业务含义定义分区键（如按时间、按地区），查询时优化器可以精确裁剪到目标分区。结构感知切分就是用文档的标题层级作为”分区键”。

策略四：语义感知切分（Semantic Chunking）

2025-2026 年最前沿的策略。核心思想是：不依赖字符或结构特征，而是通过计算相邻句子的语义相似度，在语义发生”跳变”的地方切分。

优点： 真正理解文本语义，切分质量最高。尤其适合长段落、主题多变的文档（如技术博客、研究论文）。

缺点： 计算成本高——需要先对所有句子做 Embedding，切分速度比递归切分慢 10-50 倍。对于实时索引场景可能成为瓶颈。

PG 类比： 这就像 PG 的自适应查询优化——不是用固定规则，而是根据实际数据分布（语义相似度分布）来动态决定”在哪里切分最优”。threshold_percentile 参数就像 PG 的 random_page_cost，调高则更倾向于顺序扫描（大块），调低则更倾向于索引扫描（小块）。

策略五：Agent 驱动的智能切分（Agentic Chunking）

2026 年最前沿的方向。利用 LLM 的理解能力来决定切分策略——让 AI 来”阅读”文档并决定最佳的切分方式。

优点： 切分质量最高，能理解文档的深层含义和逻辑关系，甚至能识别代码示例、表格等复杂结构。

缺点： 成本最高（每次切分都需要 LLM 调用），速度慢，不适合大规模批量处理。适合对质量要求极高的场景（如法规文档、医学文献）。

三、五种策略对比

生产环境的最佳实践：结构感知 + 递归字符的混合策略。 先用 MarkdownHeaderTextSplitter 按标题结构切分，对过长的章节再用 RecursiveCharacterTextSplitter 细分。这个组合在 90% 的场景中都能取得最好的效果。

Overlap 的作用： 重叠部分确保相邻 Chunk 之间的上下文连贯性。没有重叠，一个跨 Chunk 边界的概念会丢失一半上下文。重叠比例通常设为 chunk_size 的 10%-15%。

PG 类比： chunk_size 就像 PG 的 effective_cache_size——设太小则缓存命中率低（检索精度差），设太大则单个 Chunk 内噪声太多（向量表示模糊）。chunk_overlap 就像 WAL 的 checkpoint 间隔——太小浪费空间，太大则故障恢复时可能丢失上下文。

📰 技术雷达

2026 年 6 月 Chunking 领域最新动态：

LlamaIndex 推出 ContextualChunking。 2026 年 5 月，LlamaIndex 发布了 ContextualChunking 功能，在每个 Chunk 前自动附加一段”上下文摘要”，描述该 Chunk 在原文中的位置和上下文关系。这解决了传统 Chunking 最大的痛点——Chunk 被检索出来后，失去了在原文中的”来龙去脉”。实现方式是对每个 Chunk 调用一次轻量级 LLM 来生成上下文描述，成本可控。

LangChain 的 SemanticChunker 正式进入稳定版。 此前作为实验功能的 SemanticChunker 在 langchain-experimental 中已经过 6 个月的迭代，现已移入 langchain-text-splitters 主包。新版本支持自定义 Embedding 模型和多种阈值计算策略（百分位数、标准差、梯度检测），开箱即用。

Chunking 可视化调试工具兴起。 2026 年的开发者工具生态中出现了多个 Chunking 可视化工具，可以在 Web UI 中直观地看到文档的切分结果、每个 Chunk 的向量分布、以及检索时的命中情况。这对调试 Chunking 参数非常有帮助。其中 ChunkViz 和 LlamaCloud 的 Chunking Debugger 最受社区欢迎。

“Chunkless RAG” 方向的探索。 一些研究团队开始探索跳过 Chunking 阶段，直接对整篇文档生成 Embedding（利用超长上下文 Embedding 模型如 Qwen3-Embedding-8B 的 32K token 窗口），在检索时再做细粒度的段落定位。这种”先粗后细”的两阶段检索在特定场景下表现优异，但计算成本仍然较高，尚未进入生产实践。
