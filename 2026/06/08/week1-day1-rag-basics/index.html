🚀 核心洞察

预计阅读 2 分钟

做了这么多年 RDS PostgreSQL，我们其实一直在做”检索”——用户给一个查询条件，我们在 B+Tree 或 GIN 索引里找到匹配的行，返回结果。这件事我们闭着眼睛都能做。

但 AI 时代的”检索”变了。传统数据库做的是精确匹配（WHERE name = 'foo'）或者模糊匹配（WHERE name LIKE '%foo%'），而 RAG（Retrieval-Augmented Generation，检索增强生成）要做的是语义匹配——用户问”怎么让数据库跑得更快”，你需要能匹配到一篇标题叫”PostgreSQL 性能调优实战”的文档，哪怕它们没有一个共同的关键词。

这就像从 B-Tree 索引进化到了”意义索引”。我们做 PG 的人，对索引、查询优化、数据分片这些东西早已烂熟于心，这些知识在 RAG 的世界里不仅没有作废，反而是最核心的竞争力。RAG 的本质就是：把 LLM 不擅长的事情（精确记忆海量知识），交给它最擅长的搭档——一个擅长语义检索的数据库。

今天开始，我们用 26 周的时间，从一个 PG 工程师的视角，系统走完 AI 应用工程师的转型之路。第一站：理解 RAG 到底在干什么。

🧠 核心概念

预计阅读 10 分钟

RAG 是什么？一句话版本

RAG 是一种架构模式：先从外部知识库中检索相关信息，再将检索结果作为上下文喂给大语言模型（LLM）来生成回答。

这个模式解决的是 LLM 的三个核心痛点：

  1. 知识截止问题：LLM 的训练数据有截止日期，RAG 可以注入最新知识
  2. 幻觉问题：LLM 会”编造”事实，RAG 提供真实来源作为约束
  3. 领域知识问题：通用 LLM 不知道你的公司内部文档，RAG 让它”看到”

RAG 的完整 Pipeline

一个生产级 RAG 系统分为两个阶段：离线索引阶段和在线查询阶段。

概念一：Embeddings（嵌入向量）

这是整个 RAG 的基石。Embedding 的本质是：把一段文本变成一个高维向量（比如 768 维或 1536 维），使得语义相近的文本在向量空间中距离相近。

你可以把它想象成给每段文本计算一个”语义指纹”。”PG 性能调优”和”数据库运行很慢怎么办”这两句话，关键词完全不同，但 Embedding 模型能理解它们在说同一件事，所以生成的向量会非常接近。

PG 工程师的直觉映射： Embedding 就像是给每行数据建了一个”语义 GIN 索引”。传统索引基于精确值匹配，而向量索引基于语义距离匹配。pgvector 扩展就是直接在 PG 里支持这种”语义索引”。

概念二：Chunking（文本切分）

你不能把一整本书塞进 LLM 的上下文窗口。即使上下文窗口够大，把无关信息全部塞进去也会”稀释”模型对关键信息的注意力（这叫”Lost in the Middle”问题）。所以你需要把文档切成合理大小的块（Chunk）。

PG 工程师的直觉映射： Chunking 就像是表分区（Table Partitioning）。你不会把全表扫描的结果都返回给应用，而是按逻辑分区让查询只扫描相关的分区。Chunking 做的是同一件事：让检索只在最相关的”语义分区”里搜索。chunk_size 和 chunk_overlap 的选择，就像选择分区键和分区粒度一样，需要根据实际数据特征调优。

概念三：Vector Database（向量数据库）

Embedding 生成的向量需要存在某个地方，并且支持高效的近邻搜索（ANN, Approximate Nearest Neighbor）。这就是向量数据库的工作。

目前主流的选择：

方案 特点 适用场景
pgvector (PG扩展) 直接在 PG 中使用，支持 HNSW/IVFFlat 索引 已有 PG 基础设施、数据量 < 百万级
Pinecone 全托管 SaaS，零运维 快速上线、不想管基础设施
Milvus 开源专用向量库，支持十亿级向量 大规模、高性能场景
Chroma 轻量嵌入式，类似 SQLite 的定位 开发测试、小规模应用
Qdrant Rust 编写，性能优秀，过滤能力强 需要复杂过滤条件

作为一个 PG 工程师，最自然的选择是 pgvector——你可以直接在熟悉的 PostgreSQL 里完成向量存储和检索，不需要引入新的基础设施。

PG 工程师的直觉映射： 向量数据库的 ANN 索引（HNSW、IVFFlat）本质上就是 PG 里的 GiST/GIN 索引的”表亲”。HNSW（Hierarchical Navigable Small World）是一种多层跳表 + 近邻图的结构，你可以把它想象成：先用粗粒度的”分区索引”快速定位到大致区域，再用细粒度的”局部索引”精确定位最近邻。和 PG 的 B-Tree 多层结构思路一致，只是距离度量从”等于/大于/小于”变成了”余弦距离/欧氏距离”。

概念四：检索与重排序（Retrieval & Reranking）

实际生产中，一次检索往往不够。向量检索擅长语义匹配但可能漏掉精确关键词匹配，而关键词检索（BM25）擅长精确匹配但不懂语义。所以现代 RAG 通常使用混合检索 + 重排序的两阶段策略：

🔗 后端桥接

预计阅读 3 分钟

作为 PG 工程师，你已经拥有理解 RAG 所需的全部心智模型。下面这张对照表可以帮你快速建立映射：

RAG 概念 PG / 后端等价概念 核心思想
Embedding 函数索引 / 表达式索引 把原始数据变换成一种更适合检索的形式
Chunking 表分区 / 分库分表 将大数据集切分为可管理的单元
Vector DB PG + pgvector 扩展 存储向量并支持近邻查询的数据库
HNSW 索引 GiST / SP-GiST 索引 层次化空间索引，用跳层加速搜索
混合检索 多索引 BitmapOr/BitmapAnd 多路检索结果合并取最优
Reranking EXPLAIN ANALYZE + 代价模型 对候选结果重新评估排序
Context Window shared_buffers / work_mem 有限的”工作空间”，需要精心管理
Prompt Engineering SQL 查询优化 同样的数据，不同的”问法”效果天差地别

特别值得展开说的是 pgvector 的定位。很多团队在引入 RAG 时，会纠结”要不要上一个专门的向量数据库”。其实如果你的数据量在百万级以下（绝大多数企业内部知识库都在这个量级），pgvector 完全够用。你不需要学习新的查询语言、不需要运维新的中间件、不需要处理数据同步问题。就像你不会为了一个简单查询去额外部署一个搜索引擎一样。

Step 6：混合检索（向量 + 全文 RRF 融合）

向量检索擅长语义但漏关键词，全文检索擅长精确词但不懂同义。生产级 RAG 用 RRF（Reciprocal Rank Fusion） 把两路结果融合：

公式 1/(60+rank) 中的 60 是 RRF 论文推荐的平滑常数。这条 SQL 的精妙之处在于：整个融合排序逻辑全在 PG 内部完成，应用层只需要传一个向量和一个查询字符串。

验证标准：执行结果里能看到 vec_score=0 但 txt_score>0 或反之的行——这正是融合的价值（一路漏召另一路捞回）。Day 5 会专门展开两路融合 + Reranker 的进阶玩法。

Step 7：在线查询（query.py 接 LLM）

验证标准：回答中明确提到 “MVCC”、”dead tuple”、”VACUUM”，不出现 chunk 里没说过的细节（比如不会编造 “VACUUM 默认每 5 分钟跑一次”）。

踩坑速查表（实测整理）

跑完上面 8 步，下面这些坑我都踩过一遍，列出来给后来人省时间：

报错 / 现象 真实原因 修复
text search configuration "chinese" does not exist RDS 没装 zhparser 或没建 chinese 配置 CREATE EXTENSION zhparser + CREATE TEXT SEARCH CONFIGURATION chinese (PARSER=zhparser)
duplicate key ... pg_ts_config_cfgname_index chinese 配置已存在，重复 CREATE 直接跳过，去 Step 2 验证 to_tsvector('chinese', '...') 能用即可
relation "kb_fulltext_idx" already exists 索引已存在，重复 CREATE 同上，\d+ knowledge_base 看一眼定义符不符合预期
GIN 索引建出来是 'simple'::regconfig 早期 fallback 留下的 DROP INDEX kb_fulltext_idx; CREATE ... 'chinese' ... 重建
ModuleNotFoundError: No module named 'psycopg2' / 'langchain_text_splitters' Python 包没装 pip install psycopg2-binary langchain-text-splitters
connection refused 连 RDS 白名单加了公网 IP 但 ECS 走的是私网 RDS 白名单加 ECS 的私网 IP
向量 dim 不是 1024 调 embedding 时漏传 dimension=1024 text-embedding-v3 默认输出 1536 维，必须显式指定
LLM 还在编造主从复制方案 prompt 约束力不够 prompt 加 “任何参考资料外的信息都视为编造“ 这句硬话

📰 技术雷达

2026 年 6 月 RAG 领域最新动态：

多模态 RAG 成为标配。 2026 年的 RAG 系统已经全面超越纯文本检索，主流框架支持对图像、代码、音频转录甚至技术图纸进行跨模态语义检索。这意味着你的知识库不再局限于文档，数据库的 schema 图、架构设计图都可以被索引和检索。

自适应检索（Adaptive Retrieval）兴起。 新一代 RAG 系统能根据查询意图动态调整检索策略——事实核查类查询自动切换到精确匹配模式，开放性问题则使用宽泛的语义搜索。这种”查询感知”的检索策略显著提升了回答质量。

Self-Querying 架构普及。 借助 LLM 的 Function Calling 能力，RAG 系统能自动将复杂的用户问题拆解为多个结构化子查询。例如”找出所有 2024 年之后发布的、涉及性能优化的 PG 内部文档”会被分解为时间过滤 + 主题匹配两个子任务。

混合检索 + RAG-Fusion 成为生产标准。 单纯依赖向量检索或关键词检索的方案已被淘汰。2026 年的落地方案普遍采用 BM25 + 向量 + RRF 融合 + Cross-Encoder 重排序的四阶段 pipeline，在长尾查询和边缘场景下表现远超单一检索方式。
