检索策略与 Reranking：为什么你的 RAG 回答了"错误"的正确答案？

🚀 核心洞察

预计阅读 2 分钟

Day 4 我们搞定了向量数据库的选型。现在你有了一个跑着 pgvector 的 PG 实例，里面存满了高质量的 Embedding 向量。按理说 RAG 应该能工作了——把问题向量化，用 <=> 算余弦距离，取 Top-K，喂给 LLM，完事。

但你很快会发现一个问题：很多时候，向量检索返回的 Top-K 里，真正相关的内容可能排在第 6、第 7 位，被挡在了 Top-5 的门外。 或者反过来，向量检索找到了语义相近的内容，但漏掉了包含精确关键词的关键段落——就像用户搜 pg_stat_activity 这个具体视图名，向量检索可能返回一堆”PG 监控概述”的泛泛内容，而真正包含 pg_stat_activity 字段说明的文档块却因为语义不够”突出”而排名靠后。

这个问题的根源在于：单一检索策略天然存在盲区。 向量检索擅长语义匹配但不懂精确关键词，关键词检索擅长精确匹配但不懂语义。这就像 PG 里你不可能只用一种索引类型应对所有查询——B-Tree 适合等值和范围，GIN 适合全文搜索和数组，GiST 适合空间数据。你需要的是多路召回 + 智能重排序，让不同的检索策略互相补位。

今天我们进入 RAG Pipeline 中最直接影响回答质量的环节——检索策略与 Reranking。如果把 Day 1-4 的工作比作”把数据准备好”，那今天就是”把数据用好”的关键一步。

三、BM25 关键词检索——向量检索的”互补搭档”

BM25（Best Matching 25）是信息检索领域经典的排序算法，你可以把它理解为”升级版的 TF-IDF”。它的核心思想很简单：一个文档和查询的相关性取决于——查询中的关键词在文档中出现的频率（TF）、以及这些关键词在整个语料库中的稀有程度（IDF）。

BM25 和向量检索的能力互补关系：

维度 向量检索 BM25 关键词检索
匹配方式 语义相似（”PG 跑得慢” ≈ “PostgreSQL 性能优化”） 精确词匹配（”pg_stat_activity” 必须出现）
优势场景 同义词、近义词、模糊语义查询 专有名词、代码片段、函数名、错误信息
盲区 无法区分包含相同语义但不同实体的文档 同义词、不同表述方式会漏检
索引类型 HNSW / IVFFlat 倒排索引（和 PG 的 GIN 索引原理相同）
查询延迟 ~5-15ms ~1-5ms

这就像 PG 里的 GiST 索引和 GIN 索引——GiST 擅长空间邻近查询，GIN 擅长全文精确匹配。你不会用 GiST 去搜一个具体的关键词，也不会用 GIN 去做空间搜索。BM25 和向量检索的关系完全一样。

四、结果融合：RRF（Reciprocal Rank Fusion）

有了多路检索的结果，下一个问题是：怎么把不同检索器返回的排名合并成一个统一排名？

直接按分数合并行不通——向量检索返回的是余弦相似度（0-1），BM25 返回的是 BM25 分数（可能是 0-20），两者的量纲完全不同。这就像你不能直接把 EXPLAIN 的 cost 值和实际执行时间相加一样。

RRF（Reciprocal Rank Fusion） 是解决这个问题最优雅的方案。它的思路极其简洁：不看分数，只看排名。

RRF 的优势在于它对异常值和量纲差异完全不敏感——不管你的检索器返回的是余弦相似度、BM25 分数还是其他任何评分，RRF 都只看排名。这使得你可以轻松地加入第三路、第四路检索器（比如元数据过滤、时间衰减等），而不需要担心分数归一化的问题。

五、Reranking——检索结果的”精排优化器”

经过多路召回和 RRF 融合后，你得到了一个质量不错的 Top-30 候选列表。但这个列表仍然有改进空间：

  1. 多路召回是”独立打分”——每个检索器独立评估每个文档和查询的相关性，没有综合所有信号
  2. 向量检索用的是 Bi-Encoder——查询和文档分别编码再算距离，缺乏深度交互
  3. RRF 只看排名不看内容——丢失了文档和查询之间的细粒度匹配信息

Reranker（重排序模型） 要做的就是对这 30 个候选做一次”精排”，用一个更精确但更慢的模型来重新评估每个候选和查询的相关性。

主流 Reranker 模型推荐（2026 年）：

模型 类型 中文支持 延迟（单次） 推荐场景
BGE-Reranker-v2-M3 开源 Cross-Encoder 极强 ~50ms 自部署首选，和 BGE-M3 配套
Cohere Rerank v3 商业 API 良好 ~100ms（网络延迟） 不想管模型部署
Jina Reranker v2 开源 Cross-Encoder 良好 ~40ms 轻量级场景
Qwen3-Reranker-0.6B 开源 LLM-based 极强 ~80ms 需要可解释的 reranking 理由
BGE-Reranker-v2-Gemma 开源 LLM-based 良好 ~120ms 需要 listwise 排序

对于中文 RAG 场景，BGE-M3（Embedding）+ BGE-Reranker-v2-M3（Reranking） 是目前社区公认的黄金组合——同一个系列模型，语义空间对齐度高，配合效果最佳。

六、进阶检索技巧

技巧一：HyDE（Hypothetical Document Embeddings）

HyDE 解决了一个经典问题：用户的查询和文档的表述方式往往不在同一个”语义空间”。 用户问”怎么让数据库跑得更快”，但文档写的是”PostgreSQL 查询性能优化策略”。虽然语义相近，但向量距离可能不够近。

HyDE 的思路很巧妙：先让 LLM 生成一个”假想的回答文档”，再用这个假想文档的向量去检索。 因为假想文档和真实文档的表述方式更接近，所以检索效果往往更好。

HyDE 在以下场景效果显著：技术问答（用户口语化 vs 文档专业化）、跨语言检索（中文查询 → 英文文档）、模糊意图查询（”那个什么来着…”）。

技巧三：Parent Document Retriever（父文档检索）

有时候，被检索出来的 Chunk 只是一个大段落的片段，缺乏完整上下文。Parent Document Retriever 的策略是：用小 Chunk 做精确检索，但返回它所属的大 Chunk（或完整段落）给 LLM。

📰 技术雷达

2026 年 6 月检索与 Reranking 领域最新动态：

ColBERT v3 成为 Reranking 的新标杆。 2026 年初发布的 ColBERT v3 采用了”延迟交互”（Late Interaction）架构，兼具 Bi-Encoder 的速度和 Cross-Encoder 的精度。它在每个 Token 级别做交互而不是整个文档级别，在保持精排质量的同时，速度比传统 Cross-Encoder 快 5-10 倍。对于高 QPS 的 RAG 系统，ColBERT v3 正在取代 Cross-Encoder 成为 Reranking 的默认选择。

PG 16 的全文搜索增强。 PostgreSQL 16 对 to_tsvector 和 ts_rank 做了显著的性能优化，中文分词支持也得到了改善。结合 pgvector 的混合索引能力，PG 原生实现混合检索的性能差距正在缩小。在百万级文档的测试中，PG 原生方案的查询延迟已经可以和 Elasticsearch 相媲美。

RAG Fusion 框架的标准化。 2026 年的 LangChain 和 LlamaIndex 都将混合检索 + RRF + Reranking 的 Pipeline 抽象为标准组件。LangChain 的 EnsembleRetriever 和 LlamaIndex 的 RouterQueryEngine 都内置了这一最佳实践，开发者只需要配置检索器和 Reranker 即可。但对于 PG 工程师来说，直接在 SQL 层实现这一 Pipeline 仍然具有独特优势——你可以利用 PG 的查询优化器、并行执行和事务一致性来保证检索的可靠性和可观测性。

“Adaptive Retrieval” 自适应检索成为趋势。 2026 年的前沿实践是根据查询类型动态选择检索策略：包含专有名词的查询自动加大 BM25 权重，开放式问题加大向量检索权重，多轮对话查询启用 Multi-Query 扩展。这种”查询感知”的策略比固定权重的混合检索在复杂场景下表现更好。
