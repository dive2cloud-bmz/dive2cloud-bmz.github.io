Embedding 深度剖析：为你的数据选对嵌入模型

🚀 核心洞察

预计阅读 2 分钟

昨天我们说 Embedding 是给每段文本算一个”语义指纹”。但问题来了：这个”指纹”好不好用，完全取决于你选了什么模型。这就好比你在 PG 里选索引类型——B-Tree 适合等值和范围查询，GIN 适合全文搜索和数组，GiST 适合空间数据。选错索引类型，查询性能可以差 100 倍。Embedding 模型的选择也是同样的道理。

更关键的是，中文场景有中文场景的坑。英文世界的 SOTA 模型搬到中文上未必好使，就像你不能用英文的 tsvector 配置去做中文全文检索一样。2026 年的 Embedding 模型百花齐放，OpenAI、BGE、Cohere、Jina、Voyage AI、Qwen 各有千秋。今天我们就来系统拆解：这些模型到底差在哪，中文场景该怎么选，以及作为 PG 工程师，你可以通过哪些 PG 原生的方式来评估和管理 Embedding。

🧠 核心概念

预计阅读 10 分钟

一、Embedding 模型的四个关键维度

选型之前，先搞清楚评估一个 Embedding 模型需要看哪些指标。类比 PG 选索引的思路：

评估维度 含义 PG 类比
维度数 (Dimensions) 向量的长度，越大表达力越强但存储/计算成本越高 索引列的宽度和类型大小
最大 Token 数 单次输入的最大长度，超出会被截断 索引列的 varchar(n) 长度限制
语义质量 (MTEB Score) 在标准 benchmark 上的综合得分 索引命中率和查询计划的代价估算
推理成本 API 价格或自部署资源消耗 索引维护成本（写入放大、空间占用）

二、2026 年主流模型横评

下面这张表，是我结合 MTEB（Massive Text Embedding Benchmark）最新数据和实际测试整理的：

几个关键发现：

1. 中文场景，BGE-M3 和 Qwen3-Embedding 是当前的最佳选择。 BGE-M3 由智源研究院（BAAI）出品，专门针对多语言优化，支持 100+ 语言，中文表现极强。Qwen3-Embedding 是阿里 2026 年开源的新秀，0.6B 的小模型在 MTEB 多语言榜单上已经超越了 BGE-M3，8B 版本更是目前开源模型中的 SOTA。

2. OpenAI 的模型在中文上并非最优。 text-embedding-3-large 虽然维度高达 3072，但其中文语义理解能力不如专门优化过的中文模型。维度高不等于效果好，这就像 PG 里一个 8 列的复合索引不一定比精心设计的单列索引更快。

3. 成本差距巨大。 自部署开源模型（BGE-M3、Qwen3-Embedding）在长期运行中成本远低于 API 调用。如果你每天要处理百万级文档块，自部署可以节省 90% 以上的 Embedding 开支。

四、中文 Embedding 的特殊挑战

中文和英文在 Embedding 层面有几个关键差异，直接影响模型选型：

1. 分词问题。 英文按空格天然分词，中文没有空格分隔。”PostgreSQL性能调优”是一个词还是三个词？不同的分词器（Tokenizer）会产生完全不同的结果。BGE-M3 使用 XLM-RoBERTa 的 tokenizer，对中文分词质量很高；Qwen3-Embedding 使用阿里的 Qwen Tokenizer，中文字符的压缩比更优（同样的中文文本，token 数更少）。

2. 语义密度差异。 中文的信息密度高于英文——同样含义的文本，中文字符数通常更少，但每个字符承载的信息更多。这意味着中文 Embedding 需要更高的”语义分辨率”来区分相近的概念。比如”数据库死锁”和”数据库死信”只差一个字，但含义完全不同。

3. 领域术语混用。 技术文档中大量中英文混用的情况，如”用 pgvector 做 ANN search”。模型需要同时理解中英文术语，并且知道”ANN search”和”近似最近邻搜索”是同一个概念。BGE-M3 的多语言训练在这方面表现优异。

五、选型决策树

PG 工程师的推荐方案： 对于大多数中文 RAG 场景，我推荐 BGE-M3 + pgvector 的组合。BGE-M3 输出 1024 维向量，中文效果优秀，自部署零 API 成本；pgvector 存储和检索，不需要引入新的基础设施。这个组合就像 PG + 合理索引就能解决 90% 的查询问题一样，简单、可靠、可维护。

六、维度选择：不是越大越好

一个常见的误区是”维度越高越好”。实际上，维度增加带来的边际收益会快速递减，而存储和计算成本线性增长。

输出：

1024 维是中文场景的甜点区间——在语义质量和性能成本之间取得了最佳平衡。这也是 BGE-M3 和 Qwen3-Embedding-0.6B 都选择 1024 维的原因。

PG 工程师的直觉映射： 维度选择就像选择 varchar(n) 的长度。设得太小可能存不下需要的信息，设得太大则浪费存储空间、拖慢索引扫描。1024 维之于中文 Embedding，就像 255 之于大多数 varchar 场景——足够用，且性能友好。

📰 技术雷达

2026 年 6 月 Embedding 领域最新动态：

Qwen3-Embedding 系列强势登场。 阿里在 2026 年 5 月开源了 Qwen3-Embedding 系列，包括 0.6B 和 8B 两个规格。0.6B 的小模型在 MTEB 多语言榜单上已经超越了此前中文领域最强的 BGE-M3，且支持 32K 的超长上下文窗口。这意味着你可以在单个 Chunk 里放更多内容，减少 Chunking 带来的语义割裂。对于 GPU 资源有限的团队，0.6B 版本的性价比极高。

Matryoshka Representation Learning 成为新标准。 OpenAI 和 Jina 等模型开始支持”套娃表示”——同一个模型输出的向量可以截断到不同维度使用。比如 3072 维的向量可以安全地截断到 1536 维甚至 768 维，性能损失可控。这对存储敏感的场景非常友好——可以先用全维度做高精度检索，再用截断维度做快速预筛。

稀疏-稠密混合 Embedding 兴起。 BGE-M3 开创的”一个模型同时输出稠密向量和稀疏向量”的范式正在被更多模型采纳。稠密向量负责语义匹配，稀疏向量负责精确关键词匹配，两者互补。在 pgvector 中存储稠密向量 + 在 PG 的 GIN 索引中存储稀疏向量，可以实现完整的混合检索，完全不需要额外的搜索引擎。
